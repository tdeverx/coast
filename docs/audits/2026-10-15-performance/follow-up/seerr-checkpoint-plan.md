# Seerr request traversal checkpoint plan

The existing scan stores every seen remote request ID in memory, performs a local lookup per item and never yields to queued work. Persisting that growing set into one JSON snapshot after every 100-item page would serialize about 390 MB over a 100,000-item scan (excluding PostgreSQL TOAST/WAL). It would introduce a new quadratic write cost.

Proposed smallest durable change: add nullable `observed_scan_id uuid` to existing `media_requests`. A queued traversal retains only a random scan ID, page offset and bounded phase/keyset cursors in its existing job checkpoint. In each page's existing guarded transaction, resolve local identities together, apply necessary positive changes and stamp those observed requests with the scan ID. Advance the checkpoint after page effects commit. The retained-request phase keyset-pages records not observed in this scan; missing upstream records are still confirmed individually, and only an authoritative 404 permits cancellation. Conflict reconciliation also checkpoints bounded pages. Final account freshness is published only after completion.

This requires one deliberate scan-marker update per observed request per scan. It avoids a new table, an ever-growing checkpoint/snapshot or an extra detail API call for every unchanged request. It must not change a request's visible update time merely for the scan marker. Existing user/instance/account-generation/lease and linked-server permission checks remain authoritative. A resumed attempt keeps the same scan ID; replacement account generations cannot publish its effects. Direct interactive invocations retain their complete-return contract.

Verification must cover six or more remote pages yielding/resuming without replay, a complete page followed by an empty page, a volatile/partial list, confirmed 404 versus retryable errors for absent records, local conflict edits, account/lease replacement, final freshness and per-page batched lookup/marker counts. Database migration and tests run only in disposable databases for this task; no dev/live migration or provider call is authorized here.
