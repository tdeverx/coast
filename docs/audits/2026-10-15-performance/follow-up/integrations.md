### INT-F1 — P2, high confidence: Seerr maintenance never cooperatively yields and still performs a serial lookup per request

**Trigger:** unchanged Seerr accounts with multiple request pages; worse when a new request needs TMDB hydration or retained local requests need individual remote confirmation.

**Owner/evidence:** `src/lib/providers/seerr/requests.server.ts:357-488`. The remote traversal at lines 363-429 permits 1,001 full pages of 100 before throwing, but has no durable cursor or `jobCheckpoint`. Each item performs the local SELECT at lines 369-379. The final retained-history read at lines 431-434 and conflict read at lines 449-458 have no page limit; missing entries issue serial `requestDetails` calls at lines 435-447. `seerr.sync` is a maintenance/service traversal (`src/lib/providers/tasks.ts:24,29`), so `src/lib/server/queue/index.ts:280-281` holds its service traversal and account locks for the entire handler. The worker heartbeat makes a healthy, long scan retain ownership rather than reach the normal five-boundary/ten-second handoff.

**Measured current work:** compiled actual `refreshRequests` with deterministic adapter/SQL boundaries, all remote requests already present and unchanged:

| Requests | Provider list calls | Local request SELECTs (including final retained list) | Guarded transactions | Checkpoints | Changed-state writes/notifications |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 | 2 | 101 | 6 | 0 | 0 / 0 |
| 1,000 | 11 | 1,001 | 24 | 0 | 0 / 0 |

One final connection freshness write remains in both cases. This measures executed operations, not actual PostgreSQL rows/WAL or provider latency. Injected `assertSeerrAccount` does not model its additional five account/policy reads plus lease check. The actual function is source-confirmed to keep that correct generation/lease guard on personal writes; do not remove it.

**Smallest shared repair:** extend `refreshRequests` itself, using the existing `providerJobSnapshots` owner for its job/account-scoped observation census and the existing `jobExecution`/checkpoint/yield contracts. Retain `{phase,nextOffset,seenExternalIds,knownThrough,conflictThrough}` (or equivalent bounded data) with account generation; advance a remote page only after its positive effects commit. Batch the page's existing local request lookup, preserving exact user/instance/external-ID scoping. Keyset-page retained local requests and conflicts; checkpoint after committed pages and safe item boundaries when metadata/provider work has already consumed ten seconds.

A complete absence census is **not authoritative cancellation evidence here**: the current code correctly confirms each missing request by `requestDetails` and only 404 cancels. Keep that rule. A durable seen census is required only to preserve the existing efficient behavior of *not* individually re-fetching requests that the completed list already observed. The smallest no-new-table implementation can reuse `providerJobSnapshots`; do not put an arbitrarily growing seen-ID array into the 256-KiB enqueue payload, or replace it with one new remote detail call per retained request. Enforce the existing upstream page cap on snapshot cardinality, and measure cumulative snapshot serialization/writes; do not silently truncate. Cursoring positive idempotent pages alone is safe; cancellation phase must start after the completed list and still individually confirm.

**Focused acceptance:** 1/6/11 page fixture yields at five committed boundaries, resumes without replaying completed pages/effects, and permits another account on the service to progress. Unchanged pages use one batched identity query per page, not N. Simulate crash/retry at page commit; partial/truncated/filtered list; last page exactly 100; a retained absent request returning success/404/429/500; changed account and linked Jellyfin generation; lease replacement; local conflict edits; ten-second expiry midway through a page. Verify complete states/notifications and final freshness publication only on completion. Root owns disposable DB verification.

### INT-F2 — P2, high confidence: Trakt list export re-matches complete lists quadratically

**Trigger:** exporting/reordering an existing list with hundreds or thousands of members, even when desired and remote ordered identities already agree.

**Owner/evidence:** `src/lib/sync/trakt-lists.server.ts:149-198`. After fetching the list, every remote record scans `desired.some` at lines 173-185; every desired record scans `remote.find` at lines 188-195. Both compare up to four provider aliases. `exportIdentity` is also called once per local item at line 153, an additional linear DB round-trip slope, not included in the quadratic finding's count. `TraktAdapter.listItems` at `src/lib/providers/trakt/adapter.server.ts:187-192` aggregates pages with a 10,000-page ceiling; that ceiling does not make a thousand-entry double nested scan cheap.

**Measured current work:** compiled actual `exportTraktListToAdapter`, exact matching same-order movie lists. Instrumented provider-ID property reads count production matching operations; SQL/provider/identity boundaries are injected.

| Desired/remote members | Identity property reads | `traktEntry` calls | `exportIdentity` calls | Add-list/reorder calls |
| --- | ---: | ---: | ---: | ---: |
| 100 / 100 | 40,400 | 5,150 | 100 | 1 / 1 |
| 1,000 / 1,000 | 4,004,000 | 501,500 | 1,000 | 1 / 1 |

Complete returned local IDs and rank lengths are asserted. No removals occur in this identical fixture. A 10x input produces approximately 100x matching work. This is an actual control-flow operation measurement, not production CPU/latency or DB cost.

**Smallest shared repair:** within `exportTraktListToAdapter`, build an index keyed by `(kind, provider, String(externalId))` once for desired membership, and one for remote matches. Preserve the current ANY-shared-alias matching rule. For rank resolution, `remote.find` currently returns the first remote record in remote order across all matching aliases, so retain remote ordinal and choose the minimum ordinal across a desired entry's alias hits. Simply preferring a fixed provider would change behavior when aliases disagree. Preserve mixed kind isolation, duplicate/ambiguous aliases, missing IDs, output order and incomplete-rank error. No new cache, scheduler or framework is needed. A shared batch identity resolver can remove the per-item `exportIdentity` SQL slope if measured, without changing its season/episode parent identity contract.

**Focused acceptance:** exact old/new output oracle on generated 0/100/1,000-member lists; mixed movie/show/season/episode entries; provider ID 0/null/string-vs-number; multiple aliases hitting different records; duplicate aliases and remote rank IDs; extra remote members removed; missing desired identities retain error. Assert matching work grows O(total aliases), while added/removed identities and complete final rank are equivalent. Do not “fix” this by truncating list membership or skipping required reconciliation/delivery.
