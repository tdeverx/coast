## Confirmed residual defects

### PF-F1 — Administrator broadcast still performs redundant per-recipient policy/settings reads

**P2; high confidence for work count and unbounded recipient materialization; production latency unmeasured.** This was a lower-priority candidate in the first report, now reproduced against the repaired request-local configuration implementation; it is not a claim that PERF-19 failed for ordinary requests.

- `src/lib/server/notifications/index.ts:20–22`: `notify` always defaults its database to `getSql()` and calls `getConfig(database)`, which deliberately bypasses the request snapshot for any explicit connection.
- `src/lib/server/notifications/index.ts:89–97`: `broadcast` selects every enabled user ID, then serially invokes `notify` once per recipient.
- `src/lib/server/config.ts:106–111`: explicit connections correctly remain fresh; changing this shared contract to hide broadcast's cost would weaken transaction correctness.

**Trigger and observed slope:** actual `broadcast`, `notify`, `getConfig` and `withRequestConfig` source, synthetic SQL boundary, enabled users with normal settings. All users were delivered. At 1/10/100 recipients, respectively, it executes **4/31/301 SQL operations**: one complete user scan plus N settings policy reads, N user-settings reads and N notification inserts. Running inside a request scope does not reduce this. The complete recipient array and request duration scale with all enabled users. This is avoidable read/round-trip amplification; N resulting notification writes are required behavior.

**Smallest shared repair:** keep notification level/silencing/locked-level selection owned by notifications; use a set-based administrator notification insert from enabled users with one policy read, or bounded settings-page/batch inserts using the same extracted policy decision helper. A new durable broadcast subsystem is unnecessary merely to remove these redundant reads. Preserve explicit `notify(..., transaction)` freshness and the current source-key/retry behavior. If batching is chosen, document the page/write bound and preserve complete delivery/count semantics rather than limiting recipients.

**Focused acceptance:** 0/1/100/250 enabled recipients plus disabled users; silent/persistent/normal preferences, administrator `allowNotificationSilencing` off, locked silent messages, absent/deleted recipients. Compare exact target IDs/levels/body/locked fields and count, not only totals. Assert constant policy reads, bounded recipient projection/batches, and unchanged explicit-transaction settings behavior. Coordinator should decide whether this candidate warrants immediate implementation for expected installation size; no measured production overload is asserted.

### PF-F2 — Disk budget does not bound completed artwork buffers waiting for cache writes

**P2; high confidence for retained waiting work; medium confidence for real-world impact.** This is distinct from the already repaired provider queue: its capacity ends when a buffered response has been consumed, before local cache persistence completes.

- `src/lib/server/storage/image-cache.server.ts:9–14,60–77`: `put` captures the complete `Uint8Array` inside an uncapped serial promise tail. Disk-byte/file/free-space admission happens only after the operation reaches the head.
- `src/lib/providers/server-artwork.server.ts:6,18–30`: distinct-key pending downloads have no artwork bound and remain pending until `cache.put` finishes; each retains its fetched image body.
- Production consumers: `src/lib/providers/artwork.server.ts:60–67` and `src/lib/music/artwork.server.ts:23–32`, each using bounded provider responses of up to 10 MiB.
- Contrast/preserved positive pattern: `src/lib/providers/tmdb/artwork.server.ts:57–72` admits at most four pending unique downloads and keeps that slot through cache persistence.

**Trigger and observed bound:** current actual `serverArtwork` plus actual `createImageCache` source; fake filesystem has missing reads, generous space and a held first `writeFile`; fake download returns a valid 12-byte WebP fixture. Concurrent 4/16/64 unique-key bursts complete **4/16/64 downloads**, start **one disk write**, and leave **4/16/64 HTTP promises unsettled** until the gate releases. All 64 eventually complete/write after release. The cache's 1 GiB/10,000-file durable budget does not impose a pending-buffer budget. Real provider admission caps still bound work *while inside the fetch lane*; this probe deliberately isolates the later disk queue and does not claim a reproduced production OOM or measure RSS. Larger allowed response bodies and a slow/full/failing volume are the relevant growth inputs.

**Smallest shared repair:** add non-waiting admission for pending cache-put bytes/operations in the shared image cache *before* adding closures to the serial tail. The existing `put(): boolean` contract already allows declining optional persistence, so callers can deliver the downloaded artwork when this local budget is full. Keep correct disk admission, temporary-file cleanup and LRU accounting; do not create a second provider scheduler or raise provider concurrency. This directly bounds retained cache buffers without dropping authorised artwork. A shared caller-level limit could supplement it if justified, but must use existing local saturation/fallback semantics rather than another unbounded wait list. The precise pending-byte policy should be chosen/documented by the coordinator.

**Focused acceptance:** hold the first actual cache write, enqueue images on both sides of a stated byte/operation bound, assert later puts decline immediately and admitted retained bytes plateau; release/fail the write and prove admission credit fully recovers. Verify both TMDB and Jellyfin deliver image bytes when persistence declines, repeated keys deduplicate, abort/error cleanup leaves no temp files, and existing disk restoration/LRU tests pass. Verify no database transaction is retained during optional persistence.

### PF-F3 — TMDB optional artwork continues even for an already aborted request

**P2 lifecycle; high confidence.** The four-download cap prevents an unbounded upstream TMDB queue but does not stop obsolete work.

- `src/lib/providers/tmdb/artwork.server.ts:28`: takes `_request` and never reads it.
- `:62`: upstream provider init is `{}`, so neither an individual request signal nor a shared consumer signal is passed.
- `:67–75`: obsolete work continues through complete buffering, optional persistence and successful response construction.

**Reproduction:** actual module with cache misses, cache persistence succeeds, synthetic provider boundary records `init.signal`. Pass a Request whose AbortController was aborted *before invocation*. Result: **one provider call, no supplied signal, HTTP 200**. This proves avoidable work after demand has already ended, independent of browser request timing. No provider bandwidth/CPU claim is inferred from the tiny fixture.

**Smallest safe repair:** reject/return cancellation before cache/provider admission when request is already aborted. For cancellation during a shared download, preserve deduplication: track live consumers and abort the shared provider request when its last consumer leaves. Simply attaching the first request's signal can incorrectly cancel a still-interested second consumer. Reuse a shared abortable single-flight owner if one already fits; otherwise the broader in-flight cancellation part needs an explicit ownership decision, while pre-abort admission can be fixed immediately. The approved UI needs no redesign.

**Focused acceptance:** already-aborted miss performs zero provider calls; cancel the only waiter mid-download cancels upstream; cancel one of two same-key waiters preserves the other's delivery; last-consumer cancellation releases the pending slot and a later retry succeeds. Distinct-key admission remains at four and saturation still redirects to CDN. Bound provider-error and cache-write-failure lifetimes separately.

### Central database gate correction

The coordinator's serial database gate caught a meaningful implementation mistake in notification JSON binding: the first batching implementation passed `JSON.stringify(data)` into a `::jsonb` parameter. Bun SQL serializes native JSONB parameters itself, so this stored a JSON scalar string (including scalar `"null"`) and caused visibility filters and Seerr payload fields to fail. The initial synthetic fixture parsed that string and masked the driver behavior. The helper now passes the native object/null, matching the repository's documented `src/lib/server/db/jsonb.ts` contract. The synthetic fixture preserves native data and explicitly rejects pre-encoded strings; the actual DB transaction test checks null/object payload fidelity. The focused post-correction run passed **15 tests / 139 assertions / 3 files**. Coordinator reruns of affected DB suites remain the required integration evidence; earlier all-unit passes alone did not certify driver encoding.

Final small regression addition verifies the second image-cache consumer, `serverArtwork`, also returns the complete authorised WebP when `put` declines. Latest new-suite run: **9 tests passed / zero failures / 81 assertions** across notification batching (three) and artwork lifecycle (six). No real DB success is claimed here; the coordinator has started the affected disposable DB rerun after native JSON binding was corrected.
