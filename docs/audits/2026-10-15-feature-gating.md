# Feature availability and personal controls — audit and implementation plan

Reviewed 15 October 2026 at `8a350fd`, on `codex/performance-criteria`. This is an audit and proposed plan, not authorization to implement it. Only this report is added by this audit. No production code, schema, tests, dependencies, services, databases or credentials were changed. Nothing was committed, pushed, deployed or published.

Follow-up, 16 October: the context-menu implementation now provides the shared work-menu boundary and work-level personal title/artwork preferences described as proposed below. The original evidence remains a dated baseline. Feature-gating implementation is selected next, with consequential policy choices to be confirmed with the user before starting; none of the normal feature flags below is implemented by the menu work.

Coast needs a normal **Features** settings section, separate from its existing experiments, with installation availability controlled by administrators and personal opt-outs for optional behavior. The existing independent medium gates are a useful foundation. They do not yet form a complete policy for optional behavior, background work or active sessions. Adding checkboxes only to navigation would leave substantial work and access paths active.

The proposed scope is a small set of feature families with explicit consequences. Existing privacy audiences, connection sync choices, job schedules, playback limits and provider permissions remain authoritative in their own settings. A feature switch must never grant permission, erase history or silently rewrite someone’s external collection.

It was then run successfully with the existing bundled runtime at `.tools/bun-1.4.3/bun-darwin-aarch64/bun`: **4 passed, 0 failed, 81 expectations**. These pure tests cover independent existing gates, path resolution and medium/filter options. They do not exercise the proposed policy. `git diff --check` also passed. No runtime was installed and no broad suite, application, live provider or database fixture was started. Other test files were inspected as evidence of intended contracts, not reported as passing. This audit does not certify live provider cancellation, direct-media revocation, device behavior or multiple processes.

The roadmap already separates unimplemented watch-without-tracking, sub-profiles, backups/exports, connector grants, additional reading formats and guest/public party proposals from implemented features. None becomes implemented by receiving a feature name here. See [roadmap](../roadmap.md), [architecture](../architecture.md) and [performance requirements](../performance.md).

### Confirmed gaps requiring explicit treatment

These are source findings. They are not evidence of exploitation or new runtime test results.

1. **Personalisation has no real opt-out path.** Hiding its rows alone would leave `taste.refresh`, provider recommendation refreshes and personal score reads active. [Taste scheduling](../../src/lib/social/taste-cache.server.ts#L37) selects stale non-disabled users; [shared recommendation seeds](../../src/lib/recommendations/providers.server.ts#L100) use `interestWorks(null)`, whose [signals](../../src/lib/recommendations/interests.server.ts#L5) aggregate non-disabled users’ retained tracking, ratings, reactions, reading, gaming and music. A future opt-out must also exclude that user from shared seed evidence. This does not claim existing profile privacy promises an absence of derivation.
2. **Disabled media can still receive local taste-profile computation.** [Taste execution](../../src/lib/social/taste-cache.server.ts#L78) builds profiles for movie/show/game/music/book/comic from unfiltered evidence. Candidate selection applies medium gates later, but [profile persistence](../../src/lib/social/taste-cache.server.ts#L110) iterates those constructed profiles. Output hiding and candidate filtering therefore do not establish zero derivation over retained disabled-medium data. Filter admitted evidence before profile construction and recheck before publication.
3. **Existing audio sessions have different disable semantics from new sessions.** Music is checked by [playback preparation](../../src/lib/playback/service.server.ts#L164); ordinary [progress](../../src/lib/playback/service.server.ts#L444) and [stream](../../src/lib/playback/service.server.ts#L591) paths verify session/source/generation but do not recheck Music. Their generic paths are outside `experimentalPathFeature`. Disabling Music is not currently a reliable claim that an already active audio session or its personal tracking stops. By comparison, [reading ownership](../../src/lib/reading/sessions.server.ts#L76) rechecks work/category for subsequent operations, and [share assertion](../../src/lib/sharing/service.server.ts#L61) rechecks sharing/transcoding/medium policy.
4. **Save-and-reload can misrepresent an existing live-read choice.** [ConnectionCard](../../src/lib/ui/components/ConnectionCard.svelte#L99) initializes/reloads `liveRead` from `provider.connection.settings.liveRead !== false`. [listProviders](../../src/lib/providers/instances.server.ts#L205) exposes selected connection settings but omits `liveRead`. A saved false can therefore appear enabled after reload even though workers honor false. Fix that projection as part of settings consistency, without replacing the existing connection setting.
5. **Notification paths do not share one complete feature predicate.** Layout uses the older lightweight [inbox](../../src/lib/server/notifications/index.ts#L94), whereas the expanded [notification inbox](../../src/lib/server/notifications/inbox.ts#L16) also filters work categories. [SQL notice visibility](../../drizzle/0038_split_experimental_features.sql#L8) explicitly checks Parties for synced invitations, but ordinary recommendation notice eligibility is different. Count, badge, toast, inbox, linked action and creation policy must agree under the new feature policy. Do not infer that every retained notice is already uniformly hidden by all gates.
6. **Policies do not define an app-wide transition protocol.** [updateConfig](../../src/lib/application/configuration.server.ts#L7) only persists config and diagnostic audit changes. Existing handler checks can fail/no-op jobs when reached; [planning reminders](../../src/lib/experiments/planning.server.ts#L55) return while Planning is disabled. No general disable operation describes pending work, in-flight effects, active rooms, old cached personal output or reenabling. It would be misleading to label a proposed switch “stops everything immediately.”
7. **Policy checks are distributed across JavaScript, queries and SQL functions.** Besides `enabledCategories`, raw medium clauses occur in [presence](../../src/lib/social/presence.server.ts#L9), [social queries](../../src/lib/social/queries.server.ts#L10), [friend insights](../../src/lib/social/insights.server.ts#L7), [friend backgrounds](../../src/lib/social/service.server.ts#L20), notifications and shares. A client resolver alone cannot cover these paths. An inventory-driven conversion and database equivalence fixtures are required.

## Proposed control model

**Consequential assumptions for the plan:** normal feature defaults preserve implemented behavior; existing experiments retain their current values and Off defaults. A personal opt-out stops the relevant optional processing and access for that user, rather than merely hiding a tab. It preserves stored personal data and prior privacy choices. Feature disable does not delete provider credentials or undo completed remote actions. These are proposed product contracts to approve with implementation scope, not changes made here.

Use these distinct concepts in both code and wording:

| Concept | Owner and meaning | Example |
| --- | --- | --- |
| Installation availability | Administrator hard ceiling, applicable to direct requests and workers as well as UI | Requests unavailable for this installation |
| Personal feature choice | User can turn an available optional feature Off; cannot override an administrator Off | Do not use personalisation for me |
| Experiment admission | Existing administrator experiment gate; maturity/risk admission, independent of the normal choice | Music still needs its experiment admitted |
| Permission/grant | Current role, ownership, privacy, source access, token scope or explicit grant; always required | Sharing grant; friend relationship; Seerr approval permission |
| Runtime readiness | Configured provider, current account generation, compatible format/device, connected source | A game cannot become playable by switching Gaming On |
| Existing preference | Presentation or narrowly defined behavior within an available feature | Collection reasons, subtitle defaults, sync fields, presence audience |
| Schedule pause | Automatic refresh/admission paused; cached reads and explicit Run now may remain available | Paused Recommendations job |

### One source of truth, reused by action projection

Extend the existing config and user-settings owners. Add a finite, typed feature definition/decision helper with presentation metadata and a small resolved policy DTO. Do not add a rules language, remote flag service, plugin system, alternate scheduler, per-component policy store or independent menu-policy implementation.

For any operation, the decision is the intersection of:

`implemented capability ∧ installation availability ∧ experiment admission (if applicable) ∧ relevant user choice ∧ required dependencies ∧ current permission ∧ runtime readiness`.

These checks can fail independently. Expose a small reason classification such as administrator-disabled, personal-disabled, experiment-disabled, permission-denied, source-unavailable or unsupported. Do not return hidden private owner/source details. Authentication and grants are still checked in their existing authoritative boundaries. The DTO is a presentation aid, never authorization evidence accepted back from the browser.

The same policy result feeds the context-menu audit’s proposed action-capability projection, Header/navigation, medium controls, shelves, detail/hero actions and settings explanations. Menus should not invent new flag precedence. Keep unsupported actions absent, optional disabled features absent from ordinary discovery, and explain an unavailable prerequisite where an existing action or management record needs recovery. Do not use a fake successful response when an operation is disabled.

Precedence and identity rules:

1. Administrator Off wins over every user On, admin role, manually promoted job or token scope. Being an administrator does not bypass an installation feature disable. Existing administrator sharing permission bypasses only the account sharing grant, exactly as today.
2. User Off wins over admin availability On. Reenabling installation availability restores the remembered user choice; it does not overwrite an explicit personal Off or prior private audience.
3. An experiment Off still wins when a normal preference is On. No experiment is graduated merely by moving controls into Features. For experimental feature families, avoid duplicating two administrator checkboxes for the same availability: use the existing experiment admission as their current installation ceiling until a separately selected graduation.
4. Self requests use the actor/owner’s resolved choices. Cross-user reads apply installation policy, viewer interests and the owner’s relevant feature/publication choice, then section/category privacy. Turning Social Off must not erase the owner’s ability to inspect their own private history/profile; retain the existing self-read safety semantics for management and personal data.
5. Invitations, friend recommendations and other cross-user actions require both parties’ relevant participation/medium choices. No feature choice weakens friendship, ownership, source or audience requirements. Guest reads have no signed-in preference; use installation policy and owner publication/privacy. A shared link uses the creator’s current feature/grant/source policy and its own viewer capability, never arbitrary query-supplied user settings.
6. Machine tokens resolve the current token owner’s choices and scopes. Browser requests and machine requests reach the same domain checks. Replay caches must not return newly withdrawn data just because an idempotency key was once valid; check current feature/permission eligibility before serving replay output while preserving already-recorded idempotent outcomes and never reexecuting writes.
7. Schedule pause/Developer mode only affects their documented automatic-work admission. Run/Retry can override schedule pause where supported, but cannot override installation, experiment, user, generation or permission gates. Cleanup/final reports needed to release an already-authorized session remain narrowly allowed.

Query builders need the corresponding policy predicate before counts, ranking and pagination. Use the resolved booleans for actor-scoped queries and explicit owner/viewer joins for cross-user rows. SQL functions that own privacy/notice eligibility must participate in the same contract; do not put all policy into JavaScript and leave raw SQL as a second truth. Keep independent Books and Comics even when UI combines them as Reading.

Request snapshots keep their current lifetime. Workers must read fresh policy outside HTTP request context at admission, before outbound calls, at bounded chunk boundaries and before publishing personal results. Transactional rechecks use the supplied transaction. Policy changes also need a primitive feature signature in client resource scope keys and personal cache validity; equivalent session object replacement must not refetch rows. A hash of the few relevant resolved choices is preferable to a new persistent policy revision subsystem unless measured cross-process requirements show one is necessary.

## Feature inventory and proposed settings matrix

`A` = administrator availability; `U` = personal choice; `E` = retain experiment admission; `P` = keep existing preference/permission instead of another switch. Defaults describe normal availability/personal choice. An experimental family remains effectively Off until its existing E is On. The disable contracts in the next section apply wherever referenced.

This matrix deliberately does not propose one switch per route, shelf, action, queue kind or provider field. The normal Features page can group Media, Personal experiences, Playback/reading and Integrations, with links to the existing detailed settings. An administrator installation section can use a distinct route ID such as `features-policy`, alongside the personal `features` route, because the shared sections table uses unique IDs. Existing experiments can remain in their current Policies group initially, clearly labeled separately; relocating them is not required to deliver normal Features.

## Disable, preservation and reenabling contracts

The following are proposed requirements for implementation, not descriptions of current universal behavior.

| Scope | Admission, active work and output | Preserved records and reenabling |
| --- | --- | --- |
| Medium Off | Block new category operations/provider reads, filter before counts/pages/ranking, skip personal import phases, stop associated optional live/achievement/taste work. Mixed shared traversals may continue for other categories/users. Recheck at safe chunk/publication boundaries. End affected active playback/reading/party participation on the next controllable boundary, using final operational cleanup. | Keep identity, history, membership, bookmarks, source evidence and credentials. Do not publish negative availability/ownership or export removals from a skipped category. Reenable reads stored state and schedules fresh bounded work normally. It does not replay all old mutations or reminders. |
| Personalisation Off | Block personal feed/ranking/score/taste reads and computation, account recommendation fetches, seed contribution, explanation payloads and friend taste comparison participation. Ordinary Continue/Next/favourites/history and non-personal Discover stay usable. Remove personalisation-owned resources/sentinels. | Retain canonical personal evidence; dormant derived caches remain private and ineligible. Include choice in validity checks so stale workers cannot republish. An optional explicit clear-derived-data action can be designed later; Off itself is not deletion. |
| Social Off | Stop optional cross-user feed/friend enrichment/reactions/recommendations/publication, incoming participation and optional presence. Do not start friend panel/status observers or social shelf loads. End/leave party participation if its social prerequisite is withdrawn. | Preserve friends/reactions/privacy and own personal history projections. Keep management paths to remove relationships, revoke shares or review saved settings. Reenable restores remembered choices; it does not change a private audience to friends/public. |
| Playback/reader capability Off | Reject new sessions and source selection; abort client-owned preparation/rendering; close active UI and release reader workers/object URLs/media/HLS owners. Server revokes continued relay/resource admission on subsequent requests and queues required stop/cleanup. | Preserve saved progress accepted before cutoff; do not invent completion. Final operational stop must not become a new personal watch/listen. Local files and buffered/direct media bytes cannot be recalled. Direct provider URLs may outlive app policy until provider authorization ends: document/test the real bound. |
| Parties Off | Stop room creation/invites/joins/commands/new heartbeats. Personal opt-out leaves that user; a host opt-out applies the existing end/transfer rule explicitly. Installation Off ends coordination for all rooms and cancels optional invites. Personal playback need not end when only coordination is disabled. | Keep room/participant records and original personal sessions where playback remains available. Permit narrow leave/end/cleanup even after general party eligibility is withdrawn. Do not trap users behind a disabled gate that also blocks exit. |
| Planning Off | Do not admit plans/releases/reminders for the user. Existing delayed jobs must see current medium/planning/party/recipient policy, skip without delivery and finish/cancel with an intelligible reason. | Preserve plan state and original times. Missed reminders are not delivered en masse on reenable. Keep cancellation/management possible without generating fresh feature activity. |
| Requests Off | Block new remote intent and scheduled request refresh unless explicitly retained as management. Cancel unsent new-request jobs with truthful local state; a request already accepted upstream remains remote until an explicit authorized cancellation succeeds. | Keep history and pending remote identities. Owned cancellation should remain available as a cleanup action, subject to current external permissions and installation network policy; never silently override an operator’s explicit egress disable. UI must distinguish “new requests disabled” from “integration unavailable.” |
| Sharing/API/webhooks Off | Recheck before grant/token issuance, authenticated request, state/file/stream/HLS resource use, webhook creation/emission and delivery. Cancel unsent deliveries; mark active sessions for cleanup. Keep revocation and subscription/token/share inspection available. | Retain credentials, scopes, grants and history without serving content. Never turn API availability On into token creation. Reenable cannot flush disabled-period events; fresh events follow current scopes/subscriptions. |
| Schedule pause | Stop future automatic admissions; existing manual requests/retry and cached output follow documented controls. Feature-disabled reasons must be shown separately from paused/queued/rate-limited. | Keep queued intent only when its real admission policy remains valid. Reenable cadence does not bypass retries, cooldowns, generations or connection ordering. |

Implementation should not wait while holding a database transaction on provider cleanup. Commit the policy and bounded local transition first; use existing durable cleanup jobs for external release. Mark pending/failed optional jobs cancelled or otherwise terminal with a clear policy reason, rather than leaving an early disabled job blocking the connection lane indefinitely. Shared jobs with mixed recipients skip only excluded users; do not cancel another user’s work because the job’s scheduling actor opted out. Taste currently batches users under one job: evaluate each captured user again, not only the job’s `userId`.

A request already in flight may have sent an external effect before disable commits. Check fresh policy before each subsequent outbound call and before publication, preserve replay/account/lease evidence, and report the race honestly. Do not “undo” a remote effect without the existing ownership evidence. Long imports keep bounded checkpoints; skipping a phase must not create a completed authoritative census or erase prior positive data.

For pure preference changes, clear/abort withdrawn client resources immediately after save, then refresh the existing targeted route dependencies once. Other tabs learn through the current navigation/session refresh contract; server enforcement applies to their next request even before their UI refreshes. No new universal polling loop is proposed. If sub-minute cross-tab visual propagation becomes a requirement, assess a narrowly scoped browser event only after that requirement is selected.

## UI and settings consistency

Preserve the approved controls, layout, menus, dialogs, skeletons and refresh behavior. Add ordinary settings rows using the existing save/unsaved-edit pattern. Group by user outcome, name administrator limits clearly, and show the dependency reason next to an unavailable preference. Do not reset remembered personal values when an admin gate closes. Read-only descriptions of disabled stored state can remain in management screens.

Every feature family needs consistency across navigation, shortcuts, card/menu/hero actions, medium filters, direct pages, modal/deep links, notifications, source options, progress/sequence continuation, profile/share/guest reads, API scopes/endpoints and jobs. In particular:

- Do not fetch a disabled shelf or mount its lazy sentinel simply to receive an empty response. Do not load `DynamicFeed`, reader/HLS/EPUB/PDF/chart modules, friend enrichment or party/presence timers without an admitted consumer. Static imports already shared with core UI need evidence before a performance-only code split.
- Resource scope keys include primitive effective policy; `createResource.replace` cancels previous requests and clears withdrawn data. A failed/aborted old request cannot repopulate an opted-out context. A settings refresh that replaces objects but preserves feature values must not restart all shelves.
- Normalize stale URL categories/selections to a visible eligible value without silently changing the saved feature preference. If every medium is Off, keep Settings/account/recovery reachable and show a useful empty state. Do not secretly turn a medium On or impose an arbitrary “at least one” rule.
- Continue/Next/queue sequence selection cannot loop through disabled members or silently delete them. Already loaded modal/detail data must clear when access is withdrawn; navigation to the full page is only appropriate if that category/permission remains allowed.
- A current server response remains authoritative when an old tab offers an action. Handle the structured disabled reason using existing feedback, not a successful local optimistic update. Cancel optimistic work and refresh only the affected resource.
- Connection controls display saved values after reload, including `liveRead`. Management lists (tokens, shares, pending requests, conflicts) remain available for revocation/cleanup when creation is disabled. Settings reset preserves privacy and administrator grants today; explicitly decide whether personal feature choices reset, and keep privacy/egress opt-outs out of a casual appearance reset.

## Phased implementation plan

Each phase is a proposed implementation unit. No phase authorizes a commit, dependency, migration execution, release or deployment.

### Priority ledger

| Order | Proposed work | Reason and completion boundary |
| --- | --- | --- |
| FG-01 — first | Approve feature/default/lifecycle contracts and the finite shared capability model | Prevent two policies in menus and settings. Proposed defaults preserve normal behavior and retain current experiment choices; the personalisation/social participation choices above remain proposals. |
| FG-02 — first implementation | Existing settings and gate consistency: `liveRead`, disabled-medium taste evidence, active audio policy and notification predicate parity | Fix the concrete source gaps before claiming a new control works app wide. Each requires a focused regression fixture and explicit active-session behavior. |
| FG-03 — foundation | Config/user schema, current-policy resolver, query predicates and authoritative command checks | Cover browser/API/domain paths with the same precedence and preserve owner/viewer identity, privacy and data. No settings UI should promise control before this exists. |
| FG-04 — enforcement | Outbox ownership/admission/chunk/publication rules and bounded disable cleanup | Prevent hidden queued work, stale worker publication, blocked lanes and false absence/removal. Keep existing scheduler/generations. |
| FG-05 — visible delivery | Normal Features settings, projection-driven navigation/actions, resource teardown | Deliver actual user/admin control with the approved UI; consume the [context-menu plan](2026-10-15-context-menus.md) rather than introducing separate menu policy. |
| FG-06 — completion | Cross-user/guest/token/share combinations, preservation/reenable checks and documented acceptance limits | Demonstrate coherent behavior and absence of optional work; keep real provider/device acceptance separate and explicitly authorized. |

The order is intentional: settle the proposed behavior, repair known contradictions, enforce the common contract, then expose the settings. This avoids shipping a cosmetic control whose backend still runs. Individual vertical slices can complete that order without migrating every family simultaneously, provided each slice is complete across its server, worker and UI paths.

### 1. Fix the contract and audit inventory

Approve the bounded matrix, defaults and lifecycle behavior, particularly strong personal opt-out semantics, playback cutoff/cleanup, Social versus public profiles, requests cleanup and personalisation’s shared-seed participation. Record feature-to-operation-to-job ownership. Do not design a general policy engine or graduate an experiment as an incidental cleanup.

Use one finite typed feature model and capability projection shared with the menu plan. Record source ownership and supported combinations. Add only normal flags that the matrix requires; reuse `enableRequests`, `enableTrakt`, sharing grants, experiments, detailed connection choices and job schedules. Correct the existing `liveRead` read projection and resolve the demonstrated profile/notification/session consistency gaps with focused changes once implementation is selected.

### 2. Store and resolve policy without changing effective defaults

Extend `configSchema`/`defaultConfig`, `UserSettings`, the personal mutation allowlist and explicit settings section fields. Preserve server ownership of administrator grants/limits. If nested settings are used, implement deliberate validated merge semantics: the current user mutation does a shallow JSON merge, so a partial nested patch must not wipe another choice. Do not introduce multiple equivalent flat/nested flag paths.

Current private-project data needs a direct versioned migration only where stored shape/SQL functions require it; do not add legacy aliases, compatibility shims, dual-read fallbacks or a migration framework. Preserve the current stored experiment values and provider choices. Defaults can usually supply missing new personal fields without rewriting every user. Test absent fields, explicit false and reset semantics.

Compute the client DTO from current installation config plus current user choices. Query owner/viewer settings when operation scope requires them; do not reuse the actor’s session settings as another owner’s policy. Include the relevant effective feature signature in cache keys and taste validity; retain request-local config ownership and transaction reads.

### 3. Enforce backend and lifecycle boundaries first

Add required checks to owning services, not just catch-all dispatch. Cover browser and machine mutations, direct work details/history, reading file/session/close, playback start/progress/stream/HLS/error/cleanup, parties, planning, sharing, social commands, provider linking/reads and metadata/availability publication.

Update query predicates before count/page/ranking and extend SQL privacy/notification helpers where cross-user eligibility is owned there. Apply policy at enqueue, schedule/claim admission, handler entry, safe chunk boundaries and publication, using the existing queue lanes, account generations, checkpoints and lease checks. Associate each job kind with its actual work/recipient policy; shared jobs must not inherit the scheduler actor’s personal interest as installation policy.

Define the local disable transition in the existing application configuration/personal-settings workflows: persist the policy, withdraw read access, cancel unsent optional work and schedule necessary active-session cleanup. Use the existing outbox. Avoid table-wide unbounded cleanup in the HTTP save; page any large transition. Preserve data and do not trigger Collection cleanup/removals.

### 4. Add Features settings and consume one projection

Add personal Features and administrator availability controls with the existing settings patterns, clearly separate from Experiments. Show current availability, remembered choice and prerequisite; link to detailed Playback/Privacy/Connections/Jobs/API settings for existing controls. Do not expose unsupported roadmap toggles.

Apply the same capability DTO to the menu/action projection, Header, medium selectors, shelves, modal/detail, notifications, reader/player/party owners and preview fixtures. Remove disabled resource owners and prove there are no “hidden but still fetching” consumers. Keep the approved design intact.

### 5. Verify meaningful combinations, then document release behavior

Use focused pure tests for precedence and capability decisions, isolated database fixtures for enforcement/projections/jobs, and local browser fixtures for lifecycle/UI consistency. No live acceptance or rollout is implied by fixture success. After targeted checks pass, run the repository-required type/build/inventory gates and appropriate suites once, proportionate to the selected changes.

Migration/release notes should say what each Off does, how data is preserved, where existing grants/settings live, how old active sessions and pending jobs are handled, and the limit of buffered/direct media revocation. Configuration schema/SQL changes must ship in the same version as their enforcement. Review the concrete diff before deciding whether to split phases into implementation PRs. No automatic external rollout or commit is part of this plan.
