## Outcome

The strongest foundation is already present: shared work identities, concrete activity models, durable outbox delivery, provider transport controls, shared Shelf/Heading/Card composition and reusable resource/mutation helpers. Preserve these rather than introducing another scheduler, generic activity table, universal orchestrator or replacement design system.

The first repairs should be two privacy gaps and a bounded artwork cache, followed by database CI coverage. Most remaining opportunities are ownership and lifecycle consolidation. All 55 UI component files have production import references in the structural inventory; this audit did not establish an unused component safe to delete. Imports do not prove every prop, style or export is useful; compiler-aware reachability is a later pass.

[Findings register](2026-10-02-findings.json) contains 18 findings with locations, confidence, impact, action and acceptance criteria. [Coverage inventory](2026-10-02-coverage.json) records the source graph, review limits and test results. P1/P2/P3 indicate repair priority, not security severity; the three security findings are medium severity.

## Proposed ownership model

Keep the existing structure while tightening responsibilities in small passes:

| Responsibility | Owner | Must not own |
| --- | --- | --- |
| HTTP endpoints/page loaders | Validation, viewer/subject resolution, transport errors, calling a use case | Provider credential writes or duplicated domain policy |
| Application use cases | A bounded workflow spanning domains: link account, change sources, import account, reconcile delivery | Every query, global state, provider protocol parsing |
| Domain commands | Tracking, Collection, lists, profile and social invariants and transactions | HTTP status shaping or direct provider requests |
| Domain queries | Authorized read DTOs, counts/filters before pagination | Hidden writes and outbound reconciliation |
| Provider adapters | Protocol, mapping, supported capabilities and remote error translation | Coast page composition or cross-domain configuration side effects |
| Provider account/storage services | Credentials, account evidence/generation and instance identity | Deciding personal relationships from server presence |
| Existing outbox/task registration | Durable effects, deduplication, ordering, cooldown, leases and retries | A parallel scheduler |
| UI sources/resources | Loading, cancellation, paging and mutation refresh | Separate truths for relationships or progress |
| Shared renderers/elements | Approved visual composition and interaction semantics | Provider calls or fixture installation |

A thin application layer is worthwhile for multi-domain workflows and a future public API. Start with source/account changes, where the import graph already forms a cycle. Do not require every simple query to pass through a generic orchestrator. Shared work IDs and provider-scoped mappings remain distinct; music artists remain browsing/preferences entities and activity keeps its medium-specific models.

Move shared Trakt identity resolution beneath both import and projection rather than importing the importer from the exporter. Separate pure config reads from authorized config mutations to break auth/config coupling. The TMDB adapter/details edge is eager; playback/synced-client and sync-value/change edges include deferred imports and should be evaluated individually, not mechanically outlawed. Import cycles are maintenance evidence, not demonstrated runtime failures.

## Component and element consolidation

Shelf is a shared renderer today. Keep that renderer and improve its sources: common cancellable loading, explicit cursor/page/local capabilities and pure query/filter mapping. Preserve child-specific semantics such as journal grouping, explicit episode skip, music queue ordering and profile visibility. A single giant switch storing each old implementation is not consolidation; neither is creating a wrapper per variant.

The best next reusable elements/resources are:

- One mutation lifecycle with typed failure, busy state and targeted refresh; one cancellable resource lifecycle for menu/feed loading.
- Shared accepted-friends data loading for recommendation and synced-session controls, with separate actions/dialogs.
- Pure browse-filter mapping reused by URLs, API parameters and controls, preserving Collection versus accessible Library meaning.
- A small action-result/notice presentation using the existing design, only after its differing remedies are captured.

Heading, MenuAction, Button, ContextMenu, Dialog, MediaCard, Shelf and player controls remain the visual anchors. Keep the approved row headings, navigation, cards and hero. The six glass materials remain parameterizations of shared behavior. Do not add text sizes, colors or material variants merely to make a refactor easier. Semantic icon sizing is worth reviewing, but numeric sizes are not automatically wrong or removable. Preserve native dialog/menu accessibility and test actual keyboard behavior before merging focus abstractions.

## Component viewer specification

Retain the permanent admin viewer and its Typography / Colors / Materials / Elements / Components grouping. Keep the existing section headers and separators; no iframe or discretionary visual redesign.

1. Generate a composition manifest from component imports and rendered tags. Distinguish actually rendered elements from type/helper imports, deduplicate recursive references, and mark runtime/snippet composition as unresolved rather than inventing a dependency.
2. Beside each component preview, show links/chips for its used elements. Each element links back to components and actual app consumers. Keep direct composition separate from an expandable transitive tree.
3. Keep a small hand-authored recipe registry for meaningful sample states: normal, loading, empty, error, disabled and partial availability where applicable. Do not auto-render every dependency as another row or keep obsolete components only to fill the catalogue.
4. Inject fixture transport and stores into demos. No global fetch replacement or production playback singleton mutation. Preview interactions stay local, while the app's notification/playback network continues normally.
5. Import preview recipes lazily; keep a user-opened interactive preview stable while scrolling. Viewport mounting alone does not defer code when one Demo statically imports everything.
6. Add a cheap manifest/recipe consistency check. Retain manual unapproved-design labels, particularly friend avatars. Links and embedded controls need keyboard labels and reduced-motion/material fallback examples.

Acceptance: the viewer explains how real components are built, reflects current production use, preserves live browsing/playback state and cannot write synthetic fixture data to real endpoints.

## Areas for future investigations and parity

These are investigation targets, not established bugs or newly approved product features:

- **Retention and recovery:** define expiry/retention for transient rooms, invites, completed jobs, previews and diagnostics separately from durable history, projection attribution and delivery provenance. Search did not establish an app-wide retention policy. Exercise backup/restore with encryption keys and external/bundled PostgreSQL; never sweep durable sync evidence as trash.
- **Public API:** decide machine authentication/scopes, rate budgets, typed errors, pagination and idempotency around domain DTOs. Current API versioning does not by itself establish a public connector contract; docs/connectors.md remains a proposal.
- **Provider parity:** maintain a capability matrix for screen/music/games and distinguish unsupported remote state from failed sync. Games without an installation-capable source intentionally remain Unknown. Live Trakt, account switching and social privacy require real-account acceptance beyond fixtures.
- **Accessibility and responsive behavior:** keyboard/focus journeys through nested menus, dialogs, player, material sliders and lazy rows; screen-reader announcements, touch targets and contrast over varied artwork. Existing menu/native-dialog controls are evidence of implementation, not full accessibility certification.
- **Playback lifecycle:** buffered outage recovery, navigation persistence, simultaneous sessions, actual-play thresholds and experimental synced transport. Use proportionate desktop/mobile checks before claiming live playback acceptance.
- **Observability:** stable error codes and remedies across AppError/provider/action boundaries; task outcomes, freshness, account generations and actionable failures with redacted diagnostics. Avoid collapsing all metadata absence into conflicts.
- **Product QOL:** exact-next For You, empty-row/loading policy, avatar meaning approval and the existing social/onboarding/synced roadmap remain separate product passes. Browsing context versus modal media pages still needs exploration.

## Findings detail

### AUD-01 · P1 · Profile metadata exposes private favourite IDs

Details visibility returns saved profile metadata including favouriteOrder and pinnedFavourites independently of favourites visibility. Custom ordering contains the favourite UUIDs. Conditional on the viewer having details access; public-read mode can make the viewer anonymous. Security scan: csf_39f1de0b5fc509144c9fe080, medium severity.

Recommendation: Return an explicit nonowner profile DTO; omit owner-only ordering/pinning identifiers or gate them on favourites privacy.

Acceptance: Owner ordering survives; friends/public/private combinations do not reveal denied favourite IDs.

Evidence: `src/lib/server/queries/profile.ts:68`, `src/lib/core/profile/service.ts:113`, `src/routes/profile/[username]/+page.server.ts:46`. Confidence: high; classification: observed.

### AUD-02 · P1 · Paused Collection filter bypasses progress privacy

The paused predicate reads the latest raw game playthrough status. Visible collected/watchlisted games can therefore expose private paused progress through returned identities and counts. Requires experimental features and Collection access. Security scan: csf_eaa9cb6c6c44ea299fa24c20, medium severity.

Recommendation: Use a privacy-filtered paused assessment consistently in predicates, returned fields and totals.

Acceptance: A shared collected game with private progress is not discoverable with activity=paused; owner filtering remains correct.

Evidence: `src/lib/collection/query.server.ts:188`, `src/routes/api/v1/[...path]/+server.ts:199`. Confidence: high; classification: observed.

### AUD-03 · P1 · Artwork cache has no total storage budget

Valid distinct TMDB image requests create persistent files without quota, eviction or free-space guard. Each download is bounded and paths are hashed; this is aggregate disk growth, not path traversal or SSRF. Public-read plus caching exposes it anonymously; caching defaults off. Bundled PostgreSQL shares the data volume. Security scan: csf_0a3b57c6c31a0846ff35add9, medium severity.

Recommendation: Add a measured cache budget, eviction/free-space floor and bounded, deduplicated misses. Constrain public cache creation to catalogued assets or a request budget.

Acceptance: Distinct valid images and concurrent misses respect byte/file limits; cached reads and disabled-cache behavior still work.

Evidence: `src/lib/providers/tmdb/artwork.server.ts:35`, `src/lib/providers/tmdb/artwork.server.ts:49`, `src/lib/social/public.server.ts:8`. Confidence: high; classification: observed.

### AUD-04 · P1 · CI skips database behavior and a privacy fixture is stale

The normal suite passes 181 tests and skips 241 without database flags. Isolated runs of 27 database suites produce 199 passes and one reproducible failure: a fixture expects another user's favourites without establishing friendship/public privacy. CI has no PostgreSQL service or database test configuration.

Recommendation: Repair the fixture by explicitly establishing authorized sharing, and separately assert the friends-only denial. Run the supported isolated PostgreSQL suites in CI with explicit environment flags and deterministic cleanup.

Acceptance: CI exercises database suites without silent skips; both permitted profile viewing and denied default viewing pass. Never relax privacy to satisfy the fixture.

Evidence: `.github/workflows/verify-and-publish-preview.yml:21`, `tests/domain-application-db.test.ts:216`. Confidence: high; classification: observed.

### AUD-05 · P2 · API profile gate hardcodes screen for other categories

The generic cross-user API gate checks screen access before category-aware Collection reads. A user sharing game/music Collection while keeping screen private can be denied an otherwise permitted view. profileVisibility also projects section visibility using screen.

Recommendation: Resolve requested category and section once at the application boundary; use the same policy in pages, queries and APIs. Keep subject identity separate from viewer access.

Acceptance: Game-only and music-only sharing work; screen denial and owner-only game notes remain enforced.

Evidence: `src/routes/api/v1/[...path]/+server.ts:199`, `src/lib/social/privacy.server.ts:11`. Confidence: high; classification: observed.

### AUD-06 · P2 · Admin demand paginates users before removing empty demand

adminDemand selects up to 60 opted-in users, computes demand, then removes users with zero results. Its page count counts all opted-in users. This can produce empty pages before later users with demand.

Recommendation: Define pagination around users with demand, or explicitly expose user traversal semantics; prefer filtering/counting demand before page selection and batching the demand projection.

Acceptance: A population over 60 with demand only on later users produces discoverable, correctly counted results; opt-outs remain absent.

Evidence: `src/lib/collection/demand.server.ts:35`. Confidence: high; classification: observed.

### AUD-07 · P2 · Integration side effects form a broad dependency loop

The structural graph connects instance/account configuration, source changes, Collection projection, Trakt import and catalogue ingestion in one cycle. Some edges are deferred imports; this is ownership coupling, not proof of a startup failure. Additional eager cycles connect auth/config and TMDB adapter/details.

Recommendation: Place source-change workflows in focused application services above provider repositories and domain services. Move shared identity resolution below import/export; extract pure configuration reads below auth-admin commands.

Acceptance: A connection/source change invokes one application workflow; providers do not import Collection workflows; eager cycles are removed with behavior-preserving fixtures.

Evidence: `src/lib/providers/connections.server.ts:89`, `src/lib/providers/instances.server.ts:255`, `src/lib/collection/projection.server.ts:6`, `src/lib/sync/trakt-import.ts:17`. Confidence: high; classification: observed.

### AUD-08 · P2 · Catch-all API mixes transport and domain orchestration

The 606-line handler dispatches unrelated domains and combines policy, validation, direct queries and mutations. Large settings and action components similarly mix many independent responsibilities. File length alone is not a defect, but the ownership overlap makes shared public API behavior difficult to define.

Recommendation: Extract domain handlers with explicit commands/query DTOs while retaining one transport/auth/error boundary. Introduce application workflows only for multi-domain operations, not a universal orchestrator or second scheduler.

Acceptance: Existing routes and URLs remain stable; equivalent page/API calls use one policy and domain implementation; account-generation and outbox ordering guarantees stay intact.

Evidence: `src/routes/api/v1/[...path]/+server.ts:199`. Confidence: high; classification: observed.

### AUD-09 · P2 · Social feed does not use the common request lifecycle

The social source maintains its own busy/error/cursor state, drops load requests while busy and lacks cancellation or request-generation checks. Other adapters use the existing resource helper. Late results can outlive the source; whether a current page triggers a category race needs an interaction test.

Recommendation: Use the common cancellable resource lifecycle with explicit replace/append semantics and source teardown.

Acceptance: Rapid category changes and unmounts cannot publish old results; cursor append deduplicates without skipping a pending reset.

Evidence: `src/lib/ui/shelves/social.svelte.ts:6`, `src/lib/ui/resource.svelte.ts:21`. Confidence: high; classification: structural risk.

### AUD-10 · P2 · Reactions retain target state without stale-response protection

ReactionActions owns its own load/write state and has no target-generation/reset logic or abort signal. A reused instance can retain selection/counts from an earlier target or accept its late response.

Recommendation: Use createResource keyed by target kind/id and the existing mutation primitive; share accepted-friends loading between recommendation/session controls where contracts match.

Acceptance: Target changes clear old counts and ignore late results; one reaction per target and lazy action loading remain intact.

Evidence: `src/lib/ui/components/ReactionActions.svelte:7`. Confidence: high; classification: structural risk.

### AUD-11 · P2 · Preview fixtures replace global fetch and player state

The viewer replaces window.fetch for all API traffic while mounted, permits live notification reads and blocks non-GET calls. Its player preview uses the real playback singleton. This can interfere with background playback/heartbeat/notification work; the fixture isolation comment overstates isolation.

Recommendation: Inject preview-local transport, fixture stores and player state into demos. Use the same real components with isolated dependencies; no iframes.

Acceptance: Opening/closing the viewer during real playback leaves its session and network requests untouched; synthetic actions cannot write live data.

Evidence: `src/routes/ui-preview/demo/fixtures.ts:24`, `src/routes/ui-preview/Demo.svelte:96`. Confidence: high; classification: observed.

### AUD-12 · P2 · Viewer inventory and lazy loading are manually maintained

One Demo statically imports the catalogue; viewport mounting does not make those imports lazy. PreviewSlot destroys demos out of view. The inventory does not expose actual element composition or reverse usage. All 55 UI component files have production import references in the structural graph; no deletion is justified by this audit alone.

Recommendation: Generate a validated composition/used-by manifest from source imports and rendered tags; retain hand-authored preview recipes and labels. Load recipes by module and preserve user-opened preview state.

Acceptance: Each component links to used elements and application consumers; missing/stale entries fail a lightweight check; offscreen demos avoid eager code loading and unexpected state resets.

Evidence: `src/routes/ui-preview/catalog.ts:1`, `src/routes/ui-preview/Demo.svelte:10`, `src/routes/ui-preview/PreviewSlot.svelte:1`. Confidence: high; classification: observed.

### AUD-13 · P2 · Shelf adapters combine query mapping and presentation decisions

Shelf is a genuinely shared renderer, not repeated versions pasted into one file. Library source mixes Collection/Library filter mapping, routes and medium choices. The broad optional source contract allows combinations that are hard to validate.

Recommendation: Keep one Shelf renderer. Extract pure filter/query mapping and a small shared loading/pagination resource; use discriminated source capabilities for cursor/page/local modes. Extract repeated controls only when their semantics match.

Acceptance: Library, Collection, journal, episodes and feed keep their current layout, lazy behavior, filters and page controls; no repeated rendering implementations or new wrapper-per-variant components.

Evidence: `src/lib/ui/shelves/types.ts:25`, `src/lib/ui/shelves/library.svelte.ts:32`, `src/lib/ui/components/Shelf.svelte:1`. Confidence: high; classification: observed.

### AUD-14 · P2 · Global invalidation is the default after writes

change invalidates every active route load. createMutation also invalidates all and refreshes its own resource. Callers use differing write paths. This creates a potential broad reload cost; no production latency measurement was performed.

Recommendation: Standardize mutation completion and invalidate specific resource dependencies, keeping one authoritative local refresh. First measure request counts for representative writes.

Acceptance: Favourite/reaction/rating changes update affected cards and counts once without unnecessary page-wide queries; background state is not stale.

Evidence: `src/lib/ui/client.ts:39`, `src/lib/ui/mutation.svelte.ts:15`. Confidence: high; classification: structural risk.

### AUD-15 · P2 · Small returned pages still perform broad computation

Job timings enumerate connections and maintenance kinds, metadata due groups the shared TMDB pool per instance, taste reads join users and the work pool, and admin demand repeats its CTE per selected user. Bounded output does not establish bounded query work. PostgreSQL may optimize parts of these plans.

Recommendation: Capture EXPLAIN ANALYZE with production-sized disposable fixtures, then start from relationship/account-specific candidate IDs and batch relevant aggregates. Add indexes only when plans justify them.

Acceptance: Record query counts, rows scanned and timings at realistic scale; privacy predicates and counts remain correct.

Evidence: `src/lib/providers/job-timing.server.ts:17`, `src/lib/social/insights.server.ts:17`, `src/lib/collection/demand.server.ts:35`. Confidence: medium; classification: measurement required.

### AUD-16 · P3 · Server ownership and domain vocabulary vary by folder

Server-only code uses directory conventions in some areas and .server.ts in others. core, server/queries and standalone domain folders overlap. mediaId sometimes refers to a shared work UUID. Existing route/component naming is mostly consistent, and generated migration names are not actionable trash.

Recommendation: Adopt a short ownership glossary and conventions for new/touched files: domain model/presentation, server commands/queries, reactive .svelte.ts resources and PascalCase components. Rename in small domain passes with import updates, preserving UUIDs/URLs/schema.

Acceptance: New names communicate subject/work/source meaning and execution boundary; no compatibility shims, speculative folder framework or cosmetic database renames.

Evidence: `src/lib/catalogue/service.ts:1`, `src/lib/core/tracking/service.ts:1`, `src/lib/providers/connections.server.ts:1`, `src/lib/ui/shelves/types.ts:1`. Confidence: high; classification: observed.
