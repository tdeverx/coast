# Context menus: app-wide audit and implementation plan

15 October 2026 baseline. Source: `8a350fd43f16c31aaec32866ca02371297792608`, the performance-criteria branch submitted as PR #31. The original audit below documents the pre-implementation behavior and route forward. Its historical paths/counts remain as evidence; the [implementation follow-up](#implementation-follow-up--16-october-2026) records the subsequent changes. The scope includes reworking underlying feature implementations where that is necessary to make actions reusable. A cosmetic wrapper around existing divergent implementations is insufficient.

## Main finding

Coast already has one menu renderer: `Button.svelte` and `createMenuController`. The disconnect is primarily in identity, action capabilities, data loading and command ownership. Movies/shows use a large dedicated `MediaActions`; music, games and reading use `PresentationActions`, while game and reading detail pages also own separate tracking dialogs. The same item therefore offers different actions and takes different request paths depending on where it appears.

Use the approved movie/show interaction as the starting point, while repairing its own loading/lifetime problems. Keep the current material, dimensions, spacing tokens, keyboard/mobile behavior and existing domain operations. Aim for one work-menu entry point used by cards, heroes and embedded cards, with thin medium-specific capabilities and forms. Non-media menus share the same host and lifecycle rules without pretending a friend, task or filter is a catalogue work.

## Measured loading paths

The [evidence record](2026-10-15-context-menu-evidence.json) runs actual compiled component scripts with the actual shared resource/work/mutation owners. Only API/lifecycle boundaries are injected. These are operation counts and control-flow evidence, not production milliseconds, SQL plans or provider throughput.

| Synthetic card | Root open GET path | Consecutive opens without a content change |
| --- | --- | --- |
| Screen item | `media/work/actions` | 1 + 1 reads |
| Stored game | `collection/work` → `games/work` | 2 + 2 serial reads |
| Stored book/comic | `collection/work` | 1 + 1 reads |
| Provider music with known work | `collection/work` → provider music detail | 2 + 2 serial reads |
| Provider music remapped to a different canonical work | old Collection → provider detail → new Collection | 3 + 3 serial reads |
| Provider music without known work | provider detail → resolved Collection | 2 + 2 serial reads |
| Canonical music | `collection/work` | 1 + 1 reads |
| Remote comic without work identity | none | none; common work actions absent |

The primary-play probe also holds the unresolved track's Collection/menu-state request after provider identity has resolved. Playback does not start until that unrelated state completes (`PresentationActions.start` calls the entire `load`). Identity preparation for Play must not wait on saved-list/rating data.

The screen disposal probe finds no AbortSignal and permits its held response to publish into the disposed owner's data. Presentation's provider request has a signal, aborts on teardown and rejects late publication. Neither host exposes a close-driven data-owner lifecycle: closing a menu is not the same as destroying its card/component.

A separate actual `mediaActionData` probe varies child and saved-list counts together at 1/60/600. The function requests hydration for 1/60/600 child IDs and returns 1/60/600 children and lists, yielding 783/9,951/96,191 serialized synthetic bytes. Ten direct statement boundaries remain constant, but that count excludes all hydration/helper internals. The real hydration helper batches by 60; batching does not bound the aggregate root payload. **The current menu does not consume `data.children`.** These samples demonstrate avoidable work shape, not production response size or a measured query-plan bottleneck.

An additional actual `createApiClient`/`createMutation` probe returns a synthetic successful write response, then rejects route refresh. The mutation reports `false`, displays only the refresh error and produces no success notice, despite one accepted transport write. This does not prove a duplicated real history event; it proves that acknowledgement and refresh outcomes are conflated. The shared operation contract must preserve the acknowledged result and expose refresh recovery separately rather than encourage resubmitting a successful command.

## Target structure

Keep `Button.svelte`, `controls/menu.svelte.ts`, `context-gesture.ts`, current tokens, `Rating`, `ReactionActions` and existing dialogs as the common rendering/interaction base. Do not add a second popover implementation or a plugin/command registry framework.

Introduce one **work-menu facade** for catalogue items (working name `WorkMenu.svelte`) and evolve `controls/work.svelte.ts` into its shared data/operation owner. `WorkActions.svelte` can remain its reusable section fragments. Extract medium-specific command state/forms from the large screen component and inline game/reading pages into thin domain owners only where reuse requires it. Retire the duplicated presentation-menu orchestration after consumers migrate; no compatibility wrapper is needed for this private project.

Suggested responsibilities:

| Owner | Responsibility |
| --- | --- |
| Shared Button/menu controller | Opening, closing, geometry, nested desktop/mobile navigation, focus, selection roles and stable visual treatment. Add an explicit close signal/callback; preserve existing events. |
| Work-menu facade | Render shared sections and optional medium extensions; own dialogs outside transient submenu content. Cards/heroes/embedded cards call this same facade. |
| Shared work action controller/read model | Canonical target/context key, effective capabilities, local personal state, per-region loading/errors, revisions, single-flight reads and mutation reconciliation. Reuse `workActionData`/existing queries and core services; do not wrap a full detail-page loader. |
| Screen/game/music/reading adapters | Existing domain behavior and target resolution: episodes/versions/requests; selected playthrough; album/track/artist distinctions; reading edition/state/session. No private queue or duplicate relationship implementation. |
| Pure action helpers | Common labels/icons/group ordering/checked/disabled reasons; explicit data and callbacks, not server-supplied arbitrary commands. |
| Non-media owners | Friend/task/profile/filter/player actions use the same Button host, lifecycle and operation patterns, but keep their own domain IDs, permissions and live state. |

A canonical work target must distinguish work ID from provider external ID, edition/source connection and display ID. Occurrence context includes list ID/entry ID and sequence cursor. A provider-only result has an explicit resolve/import action, never fabricated capabilities. A person/artist may have actions without a work UUID. Never infer that a known local ID alone means the user can read/play/share it. Keep acting viewer separate from displayed profile owner; current read-only contexts suppress all card actions. Whether signed-in viewers should get their own save/recommend actions on another profile is a product decision to resolve explicitly, without granting edits to that profile.

Common semantics are play/read/open when applicable; track/log/history; save/favourite/rating; lists/queue where supported; recommend/react; share/plan where enabled and supported; contextual occurrence actions; personal/admin maintenance when authorized. These are semantic slots, not a requirement to show irrelevant or currently unsupported actions. Seerr remains screen-specific; a file reader is not a stream-sharing implementation; game playthrough progress is not watched state.

## Performance and state contracts

- Root opens the existing menu immediately. Navigation and safely known capability entries need no provider round trip. Canonical common root data has at most one local snapshot request; zero repeat reads while the same scoped snapshot remains current. This is a structural target to measure, not a universal millisecond promise.
- Keep provider detail resolution, request destinations, reading files/editions, long lists, queue contents and history demand-loaded. Independent regions may load through existing resources; do not raise provider or SQL concurrency. User mutations retain the existing priority/rate-limit path.
- A snapshot key includes viewer, explicit target/kind, source account/generation when applicable and list/sequence occurrence. Track relevant tracking/social/planning/settings/permissions revisions. A content refresh must not change selected occurrence or close a shallow panel. Closed menus do not refetch on every heartbeat.
- Keep initial reuse component/page-scoped with finite ownership, releasing state on teardown; do not introduce an unbounded app-wide menu cache or cross-request authorization cache. Any later shared cache needs a measured need, finite budget and invalidation rules.
- Generation fences supplement actual AbortSignals. Close cancels owned optional reads; dispose is terminal. Same-key reopen and obsolete post-mutation refresh cannot publish stale data. Commands capture the target and retain final required accounting/cleanup even if the menu closes.
- Distinguish never loaded, loading, empty, unsupported, temporarily unavailable, policy-disabled, denied and failed. Local saves do not disappear because optional provider data failed. Permission-withdrawn data clears immediately; user-facing reasons must be safe and precise.
- Preserve exact list counts and occurrence IDs with bounded paging. A 60-ID hydration batch is not permission to fetch every child or list on each root open. Remove unused data before inventing indexes; measure plans before adding indexes.
- Mutations reuse existing core services, content revisions, durable exports/idempotency, privacy, history and server revalidation. Avoid broad route refresh plus eager reloading of every menu section when a narrower existing method suffices.
- Do not add hover provider prefetch, background polling, a second scheduler, broad material changes, a new rendering dependency, or a large universal action object holding all medium details.

## Implementation sequence and completion gates

1. **Capture the parity contract.** Record each medium/entity, stored/provider state and context (card/hero/row/grid/list/activity/notification/read-only). Freeze current screen commands and intentional differences. Add actual rendered/core fixtures for occurrence IDs, selected playthrough, reading edition and provider-free local actions.
2. **Establish shared ownership first.** Add menu close ownership to the existing host; use `createResource` for screen/presentation reads, cancellation, scope/revision and same-owner reuse. Keep dialog ownership stable and capture mutation targets. Prove late success/error/refresh cannot alter a replacement. No new UI design.
3. **Make root projections small and local.** Remove unconsumed children, split/paginate long list/target state and add narrow game/reading/music capability state via the common facade/read model. Canonical root actions must work when a provider is offline. Verify plans/cost at growing child/list counts before selecting further SQL changes.
4. **Migrate complete vertical slices.** First retain movies/shows/episodes/collections behavior in the facade. Then music/artist, games, books/comics—including extracting and reusing their page commands/forms. Migrate card and detail/hero together for each slice; do not leave the page on a separate feature implementation. Provider-only identities use explicit resolution/import. Carry list/sequence context throughout, and keep existing action deep links opening the same shared commands/dialogs.
5. **Apply the shared contract app wide.** Work cards embedded in Activity/notifications and mixed Library/Search/Discover automatically use the facade. Bring friend/party/task/account/filter/player menus onto common lifecycle, feedback and accessibility rules while preserving their existing local/live data. Coordinate effective feature capabilities with the gating audit.
6. **Complete metadata/presentation parity deliberately.** If the shared Personalise/Admin controls are to apply beyond screen media, refactor the screen-only persistence/read-model boundary first. Reuse work identity for common personal title/artwork preferences and add medium-specific adapters/validation for genuine metadata differences; preserve effective search/artwork, source attribution, locks and revisions. Do not broaden screen snapshots blindly or display controls that cannot save. Schema work belongs to this feature slice and needs its own migration/correctness plan.
7. **Remove superseded paths and validate.** Delete unused presentation orchestration and duplicated page command/form state once consumers migrate; run inventories. Complete scoped tests, serial disposable DB integration, type/build checks and representative browser acceptance before any push request. No production dependency is presently justified. Full metadata/presentation parity can require schema changes; settle that slice's validated fields and migration plan before editing persistence.

### Final audit fixes
