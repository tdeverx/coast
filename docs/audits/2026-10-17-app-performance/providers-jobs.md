## Findings and options

### PJ-01 — P2, behavior reproduced: private artwork cancellation is owned by the first caller

Owner: `src/lib/providers/server-artwork.server.ts:18-30`; relay: `src/lib/providers/artwork.server.ts:61-69`. The same private image key shares one promise, whose download callback captures the first HTTP request's signal. A second still-interested caller joins that promise. If the first caller navigates away, both calls fail; the second caller's own request never aborted. Relay failure can then enter TMDB fallback and create additional lookup/download work. Conversely a joining caller cannot independently stop waiting because `serverArtwork` accepts no caller signal. TMDB's corresponding owner already implements per-waiter cancellation and only aborts the upstream after the last consumer leaves (`tmdb/artwork.server.ts:12-29`).

Reproduction: actual `serverArtwork`, with inert cache/config and an abort-aware download. One download, two same-key callers; abort first signal; **both reject while the second is still interested**. This is a lifecycle defect, not an inferred memory leak. The key already includes connection/account generation and authorization occurs before joining, which must remain.

Recommended shared option: extract the existing TMDB waiter/last-consumer ownership into one small artwork-flight owner used by both public TMDB and private server artwork, with independently owned AbortController and per-caller signal. Keep the authorization, path, byte limit and delivery adapter-specific. Validate both consumers against the same cancellation/failure matrix; a server-only copy of the algorithm would permit drift. Keep bounded transport, per-caller authorization and optional cache admission. Keep private destinations private. Keep the common primitive narrow: ownership/admission/result sharing only, with existing cache and transport owners unchanged.

Acceptance: first caller leaves while second succeeds; joining caller aborts independently; all consumers leave before queue admission and during body consumption; old completion cannot delete a replacement; no persistence after final cancellation; optional disk-write decline still delivers the image. Reproduce using the actual user's repeated same-image tab/panel navigation with cache disabled/enabled after the unit fix. Expected benefit: fewer broken image loads/fallback requests, bounded to concurrent callers of the same private image; measured production frequency is pending.

### PJ-02 — P2, actual controller reproduction: crop cache does not provide true single-flight

Owner: companion `Coast/Api/TrailerCropController.cs:19,49-50,63-106`. `ConcurrentDictionary.GetOrAdd` can execute its value factory concurrently. Here the factory calls `AnalyzeAsync`, which starts a process before its first suspension. Losing factories still run their subprocess. Dictionary thread safety does not deduplicate this side effect.

Reproduction: linked actual controller, eight simultaneous requests for one exact item, a barrier in the inert encoder-path getter to make factory overlap deterministic: **eight calls started eight processes**, all requests returned successfully. This verifies a race mechanism; it does not mean ordinary single-tab use always duplicates work.

Smallest option: store a `Lazy<Task<CropResult?>>` with execution-and-publication behavior or an equivalent explicit shared work owner so process creation occurs only after the winning owner is selected. Remove a failed entry by exact owner identity, not merely key, to prevent one old failing waiter deleting a replacement. Test actual start count, not only equal response values.

Acceptance: 2/8/32 same-key contenders start exactly one subprocess; all receive the same crop; faulted work is retryable and old failures cannot evict current work; cancellation integrates with PJ-03. No production dependency is necessary.

### PJ-03 — P2, reproduced lifecycle; present load unmeasured: crop processes and retained results lack aggregate bounds

Owner: companion `TrailerCropController.cs:19,50-57,72-114`. The static task dictionary has no capacity, byte budget, TTL, content revision or shutdown cleanup. Successful `null` results are retained too. Every distinct item starts its own process without aggregate admission. The process has a useful 20-second timeout and `-threads 1`, but those bound one process, not simultaneous processes. `RequestAborted` is never observed. Standard error is read completely into one string; the eight-second media sample is not a strict stderr byte bound. Standard output is redirected but not drained (the intended FFmpeg `null` output usually emits nothing).

Reproduction: actual linked controller starts **12 different-item processes within 70 ms**, plus a request with `RequestAborted` already cancelled still starts a process and completes. After all work, **14 distinct completed entries remain** and remain after another 300 ms. No production OOM claim: completed results are small, and a short idle check merely agrees with the source's absence of eviction. High CPU pressure is a conditional workload risk.

Smallest option: one plugin-owned bounded crop worker/admission owner, true single-flight from PJ-02, explicit result TTL/capacity, key including stable content/version scope, independent waiter cancellation and all-waiters cancellation, and process-tree termination/drain on timeout or plugin shutdown. Stream stderr through a capped parser retaining the last valid rectangle rather than all diagnostic text. Decide whether crop analysis is worth a background subprocess at all: native trailer dimensions/manual opt-out could be a simpler product choice, but changes in crop behavior need approval.

Tradeoff: an aggressive one-process cap makes queued crop responses slower; overload should give a retryable/fallback result rather than silently remove trailers or bypass admission. Successful memoized crops avoid future decoding; a cap that is too small creates repeat analysis. Authorization must remain checked independently of result reuse. Tests should count aggregate active processes, exact process starts, queue size, released credits, retained keys after many distinct inputs, content replacement, failed/null results, request withdrawal and shutdown. A sustained actual trailer session and real FFmpeg RSS/CPU are still required before choosing final numerical caps.

### PJ-04 — P2 user-visible latency, call counts verified: Comic Vine search waits on optional enrichment

Owners: `src/lib/providers/comic-vine/adapter.server.ts:105-143`, `server/security/provider-fetch.ts:335-336`, `providers/reading.server.ts:63-69`. A successful ordinary issue search always then performs a volume search; matching volumes add a third request for series issues. An empty first page can add a fallback volume search, for up to four serial calls. All use the same 18,100-ms paced origin lane. The successful first issue page is not returned until optional enrichment finishes.

Actual adapter probes: ordinary populated issue page with no matching volumes = **two requests**; matching series = **three requests**. With an initially empty lane and no other traffic, the configured lane imposes at least **18.1 or 36.2 seconds** of inter-request spacing across those two/three-call chains. Total elapsed time also depends on provider response times, competing requests and cooldowns. This is arithmetic from the verified request count and production lane spacing, not a timed live API measurement. A four-request chain has at least54.3seconds of configured inter-request spacing. Search caching (100 entries / 15 minutes) and exact-key flight reduce repeats, but cold/new query pages still incur the dependency chain. `verify()` calls search and inherits its optional work.

Options: (A) return ordinary issue results when available and offer/load series enrichment separately under the existing UI contract; (B) reuse a bounded query-to-volume resolution across page changes and only request series data when needed; (C) retain current search semantics and visibly communicate long-running work. Option A can alter search result completeness/order, so product acceptance matters. Do not loosen pacing, bypass `Retry-After` or add adapter-specific hidden queues to make a benchmark pass. A dedicated minimal verification operation may avoid broad search enrichment if the API supports it; verify against official provider behavior before implementation.

Acceptance: exact item identity/order/total rules, empty-search fallback, issue-number/fraction labels, volume false matches, errors in optional enrichment, new query cancelling older demand and quotas across concurrent users. Measure actual cold/warm search and page navigation using an authorized provider account; this pass made no such requests.

### PJ-05 — P2 at long personal histories, actual loop counts verified: one Trakt value can require a full account walk

Owners: `src/lib/sync/trakt-export.server.ts:29-88,109,316`; `providers/trakt/adapter.server.ts:80-89,159-160,347-385`. Before overwriting a personal value, `readTraktValue` walks 100-record category pages until a match or a short terminal page, with a 10,000-page ceiling. An absent value in 10,000 records takes 101 API calls; an episode collection read aggregates all show collections. `clearProgress` and `recentHistory` also use full aggregating readers. These are distinct from the healthy staged import path and have no durable cursor or `jobCheckpoint`. A healthy heartbeat allows the account lane/worker to stay occupied throughout the walk.

Actual extracted production function with inert local identity/provider boundaries: 100 / 1,000 / 10,000 absent-target records required **2 / 11 / 101 calls**. For the last case, 250-ms configured pacing alone adds at least **25 seconds**; live latency is unmeasured. At the hard cap, pacing would add roughly 42 minutes before network time. This is a supported upper-bound path, not an observed real-account duration. Multiple per-item exports can repeat the same scan; queue compaction reduces superseded edits but does not turn different-title exports into one census.

Options: use exact provider identity lookups where an officially supported endpoint exists; otherwise extend the existing durable staged/census owner to answer multiple required values from one complete, activity-fenced read, or make the required full walk resumable while retaining an exact no-match conclusion. Preserve conflict detection, remote changes, history event identity and the fact that a partial list cannot prove absence. Avoid caching personal state across account generations or using a stale import snapshot as authoritative current conflict evidence. A single-flight *complete read* scoped to account/generation/category/activity can reduce concurrent duplication, but stale publication and write ordering must be specified first.

Acceptance: target first/middle/last/absent, exact-multiple terminal page, mutable account activity, failure midway, cancelled/reconnected account, provider permission errors, lease loss and another account progressing after safe checkpoints. Baseline actual retained histories and provider diagnostic call counts are needed to rank frequency against PJ-04/PJ-07.

### PJ-06 — P2 linear round trips / redundant writes: Trakt list delivery still rebuilds full identities and rewrites converged lists

Acceptance: unchanged/rename/add/remove/reorder, ambiguous provider aliases, duplicate aliases, mixed supported/unsupported media, deleted lists, concurrent local edit after snapshot, partial upstream failure, lost create reply, very large payload and retries. Count DB statements/provider calls and compare complete remote results; millisecond-only assertions would miss the benefit.

### PJ-07 — P2 opt-in backfill: Jellyfin final reconciliation escapes page/transaction budgets

Owner: `src/lib/sync/jellyfin.server.ts:841-857`; enqueue owner `src/lib/sync/changes.server.ts:72-116`. Under `reconcileTracking === true`, after bounded import pages the finalization transaction locks the current account, reads **all** non-empty screen tracking rows, reads **all** music progress, upserts reconciliation intents one at a time, reads every eligible intent and enqueues each one individually. No keyset page or checkpoint splits this final stage. A large user's imported library can therefore finish its paged traversal and then appear stuck in finalization while holding account locks and a DB transaction. This is conditional on an explicit account option; the coordinator should report whether any actual account enables it.

Smallest option: introduce bounded, replay-safe finalization phases in the *existing* scan progress/checkpoint owner. Seed intents in set-based batches and keyset-page enqueueing under account-generation/reset/attempt fences. Advance phase/cursor only in the commit with effects; completion/negative availability remains after required reconciliation setup. Avoid putting all intended work IDs into one ever-growing JSON payload. Reconciliation jobs can remain individually durable and compactable.

Acceptance: preexisting imported tracking without mappings, music+screen mix, edits concurrent with seeding, interrupted/resumed finalization, reset/account/feature changes, more than five committed pages, and exactly one effective current-version delivery per intent. Operation-count budget should be based on page size, not entire user history. Actual-data cardinalities and lock/transaction spans are still required to quantify current impact.

### PJ-08 — P2 conditional high-count spike: a single music track can materialize 10,000 listens in one transaction

### PJ-09 — P2 scale candidate: final shared-library membership update rewrites matching parents and correlates child counts

Owner: `src/lib/sync/jellyfin.server.ts:830-840`. ### PJ-11 — P2 large ownership snapshot candidate: Steam rewrites growing immutable snapshot content when only its cursor changes

Owner: `src/lib/providers/steam/sync.server.ts:47-78`. A complete owned-game response is correctly staged once in `provider_job_snapshots` and processed in transactions of 100 titles. Read both with action/generation/attempt checks; snapshot cleanup remains owned by existing triggers. This needs no new table or cache. Avoid replacing a constant-size cursor with a copied partial snapshot each yield.

Acceptance: full complete library state including negative ownership, crash at each snapshot/cursor commit boundary, exact initial/resume counts, reconnect/reset, optional IGDB scheduling, empty/private/incomplete snapshots and terminal cleanup. On an actual-data clone, measure snapshot bytes, TOAST/WAL and unchanged-import statement counts before prioritizing over current bottlenecks.

### PJ-14 — explicit policy choice, not a newly unbounded queue: queued provider time has no caller deadline

Multi-caller flights need per-waiter ownership like PJ-01; aborting one viewer must not abort a needed shared job. Tests: waits beyond caller budget execute zero upstream calls, job waits survive/recover appropriately, promotions/fairness/reservations and Retry-After stay correct, no retry-budget consumption for requests never sent.

### PJ-15 — P2 source-scale candidate: bulk task controls load every matching job and run serial transactions

Owners: `src/lib/server/queue/index.ts:602-620` (`updateTaskActions`), per-job commands at `623-661`, and `src/lib/ui/components/JobSchedule.svelte:57-63,148-154`. Retry, cancel and promote first select the complete matching current-generation ID set, then await a separate command/transaction for every ID. The ID array, SQL round trips and total HTTP command span therefore grow with matching jobs even though the task card displays only representative rows. Retry also reacquires the shared provider-maintenance advisory lock per job and performs the current retry/active-work checks; cancel resolves per-job notifications; promote updates in-memory request priority after its guarded write. Those semantics are required, not incidental work to delete.

Actual-data context: the deployed read-only snapshot contains **8,919 pending `jellyfin.reconcile` jobs** and **2,867 pending `jellyfin.delta` jobs** ([actual SQL](evidence/deployed-real-sql.json)). Those installation totals are not a count of jobs eligible for one particular task control: instance scope, connection/generation and current state can reduce that set. No task-control mutation was performed and no control latency, lock wait, WAL volume or production failure was measured. The confirmed finding is unbounded per-command selection plus serial transaction work at an installation with a substantial actual backlog. `JobSchedule` keeps `busy` until the whole response settles, and its navigation guard cancels navigation to a different path while busy. A long or unresolved command therefore also retains that task interaction/navigation state; this is a source consequence, not a reproduced browser hang.

**Canonical shared owner and all consumers:** task-control admission, selection and progress belong in the existing queue command owner, reusing the canonical cancel/retry/promote policies. Apply one contract to every provider task, all media/experiments, local/event-driven tasks with dynamic/null scopes, Jobs and integration task cards using `JobSchedule`, and any API/client invoking those commands. Keep the individual-job command paths semantically aligned. Do not create task-specific queues or independent per-card batch loops.

**Smallest option:** bounded keyset-selected chunks with a finite command work/time budget, explicit continuation/progress and exact updated/skipped/failed accounting. Define the initial target boundary, scope and account-generation fence so resumption does not silently capture newly created/reconnected work. Persist or otherwise validate the continuation under the same authoritative command owner; recheck authorization and per-job policy at each chunk, and specify recovery after a committed chunk whose HTTP acknowledgement was lost. Keep per-job notification resolution, retry-credit and service gates, duplicate-active/conflict skips, manual purpose/priority promotion and current-generation selection. Cancel-waiting must continue to leave running jobs untouched. Do not replace all controls with one broad SQL UPDATE that bypasses those effects.

**Alternatives/tradeoffs:** a bounded request/continuation path is simpler but needs an explicit partial-completion result if the viewer leaves; the UI should release its local busy/navigation ownership after acknowledgement while preserving actionable progress and honest partial outcomes. If commands must finish after navigation or restart, use the existing durable job/checkpoint infrastructure with a fenced command identity and status, rather than a second scheduler; that adds cancellation/recovery/retention work and needs an explicit decision. Set-based work is appropriate only where the shared writer preserves every policy and side effect. Increased connection concurrency does not remove the total work and can amplify lock contention.

**Acceptance:** first measure the actual eligible counts with a read-only selection; perform mutation verification only in an isolated clone of actual data. Cover each action and both provider/local/null scopes, one and many eligible jobs, concurrent state changes, account replacement, authorization withdrawal, retry conflicts/gates, notification outcomes and active-request priority. Verify bounded IDs retained/rows processed per chunk, SQL/lock spans, exact total outcomes, safe continuation after response loss/restart, no newly created work swept in, and navigation/close during slow or failed delivery without declaring unfinished work complete. Record actual clone latency and WAL before claiming a speedup. No new synthetic workload or live mutation was run for this finding.

## Actual queue backlog: diagnostic lead, not an invented throughput result

The exact deployed snapshot contains **8,919 pending `jellyfin.reconcile` and2,867 pending `jellyfin.delta` jobs**; the development snapshot had no pending queue rows in its captured state. It bounds each payload to200 IDs and durably acknowledges every page, but does not merge repeated item IDs across pending page/tick jobs. The generic option is a bounded durable delta-work-set/coalescing operation under the existing queue/account/instance owner, used by every screen/music/reading delta producer, preserving removal/permission ordering and authoritative access checks. Do not introduce a companion-private in-memory queue. First inspect actual pending-payload ID overlap, age and gating; if overlap is negligible, coalescing may add complexity without meaningful benefit. Such payload inspection must remain aggregate and not publish private item IDs. Any new durable representation is an implementation option requiring review, not an audit edit.

## Important defenses rechecked and retained

- **Transport:** approved final origins, DNS address validation/pinning, private-network opt-in, redirected-response rejection, stripped cookie/proxy headers, explicit port policy, per-body bounds and timeouts. JSON bodies are fully buffered before releasing a nonstream lane. Streams bypass short-lived API admission intentionally and use separate large-byte/read-idle limits; playback owner review must cover viewer/session concurrency rather than inserting media into the paced JSON lane. No provider or public credential was read or emitted by the audit.
- **Request lanes:** common priority owner, same-origin serialization, queued cancellation, urgent reservations, cooldown and one owned idle-cleanup timer are present. Earlier idle-origin retention / unbounded-admission findings are fixed. Per-admission scanning of all origin metrics and per-selection scanning of up to128 entries are small bounded CPU costs; optimize only if actual origin counts justify counters/heaps. Another scheduler is unnecessary.
- **Durable queue:** three workers, one urgent-only, no poll overlap per worker; reserved advisory locks serialize service traversals/account lanes and release in `finally`; 20-second heartbeats, five-minute recovery lease, monotonic attempts and publication predicates; yield after five committed checkpoints or ten seconds at a safe boundary. These are useful budgets, but the unsplit units in PJ-05/PJ-07/PJ-08 remain exceptions. Stop prevents new ticks; active handlers are not automatically cancelled by clearing timers, so shutdown/cancellation behavior remains in the coordinator's platform audit.
- **Scheduler:** current recurring maintenance uses EXISTS and bounded latest-success probes with Maps, including current/null-generation behavior. Old retained-history aggregate finding is fixed. Minute scheduling and explicit due rotation coexist with provider pacing; do not combine them into competing queues. `eligible.filter` per instance and `jobs.filter` with account matching add account/task-scale CPU work, but no measured current bottleneck warrants a new read model on that basis alone.
- **Seerr:** checkpoint has constant size, one bounded100-item page snapshot supports partial slow metadata work, local identities resolve in batches, scan-marker writes do not change visible request timestamps, missing/conflict phases keyset-page at100, and only individual authoritative404 permits cancellation. Provider I/O stays outside guarded writes. Account, linked Jellyfin generation, instance, user and lease checks intentionally incur reads/locks; removing them is not a valid performance fix.
- **Trakt imports:** durable staging fetches complete evidence and applies oldest-first20-record batches with activity/account/lease fences and bounded cleanup. Direct nonjob import's aggregation is a separate call contract; do not label the queued importer unbounded by reading only that branch. Linear alias matching fixes remain. Rotating token refresh intentionally holds an advisory transaction lock during a provider refresh (`connection.server.ts:184-225`); it prevents two consumers using the same rotating token. Valid-token fast path avoids the transaction. Changing refresh ownership requires a careful refresh-lease design, not merely moving HTTP outside the lock.
- **Steam achievements:**20-title bounded pass freezes exact owned AppIDs across resume, Map matching,100-row schema/progress batches, value-difference progress guards and deliberate schema freshness are present. Avoid reflagging the removed quadratic `.find` or per-achievement writes. Ownership scans still use per-title identity/state/mapping/access operations and necessary lastSeen/verifiedAt writes; a future batched import read model may reduce round trips but must preserve complete-snapshot negative evidence and canonical locking.
- **Jellyfin:**100-record screen/music pages and60-record reading pages validate IDs, totals and forward progress; page maps clear after commit; known mappings avoid canonical metadata refetch during personal scans. Screen access reuse is scoped to validated current server, source account, visible libraries, generation and census age; it does not waive per-user permission evidence. Reading metadata resolves known work/edition IDs before remote lookup and checkpoints skipped items. Companion ack and durable reconciliation jobs commit together; reset/overflow requests complete recovery and native polling stays until healthy. No speculative replacement queue/cache is proposed.
- **Memory/disk caches:** public metadata caches have finite entry count/TTL, failed promises clear, expired values sweep on lookup, shared resource priorities promote joined work, and IGDB adapter/token ownership is bounded32 instances. Entry count does not impose a bytes budget (notably people filmographies); actual payload distribution is required before adding a bytes cache. Artwork cache has1GiB/10,000-file/128MiB-free-space limits,16 pending writes/64MiB pending bodies and safe temp-file cleanup. TMDB has four active downloads and CDN fallback. Disk reads/writes serialize; cold initialization stats files one at a time, and eviction sorts the retained entries. These can cause cache head-of-line latency, but no actual slow-disk evidence was captured, so they remain measurement opportunities.

Outbox/history/server-stream evidence is intentionally permanent. Reading cleanup preserves the newest edition bookmark. Do not delete durable history to solve query/display growth. Retention catch-up cadence is one minute while batches remain, otherwise hourly; developer mode pauses recurring maintenance, so absent cleanup under that mode is a known policy tradeoff.

Read currently traverses the bounded SortedDictionary prefix to filter newer sequences; optimizing seek is a small optional gain at most4096 entries. Controller includes the current active-session snapshot on every hint page and Coast does per-account policy/state work; session repeats and account×session `.find` at `updates.server.ts:108-117` are bounded by real users/sessions, not a proven leak. Use an indexed user-session map/batched presence policy only if actual account/session counts make the cost material. Exact change loss/reset behavior must stay.
