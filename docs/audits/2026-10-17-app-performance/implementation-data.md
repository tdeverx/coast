# Shared data-owner implementation and verification

17 October 2026. Baseline: `eb0673873462b71118d1c11678d128958a05ff07`. This supplement records implemented changes for DATA-01, DATA-02, DATA-10 and DATA-11. The original audit remains the before-change record. No dependency, schema, license, UI, commit or deployment change is included.

## DATA-01 — ordered policy admission and token-only locking

`src/lib/server/public-api/mutations.server.ts` now takes the existing shared configuration/user-policy admission before the account advisory lock. The joined credential check locks only `api_tokens` with `FOR UPDATE OF api_tokens`, keeping the admitted user row shared. It freshly checks token revocation/expiry and disabled state, then rechecks the API feature under that admission before either idempotency replay or a new write.

This order avoids two related cycles: account advisory → exclusive user row versus ordinary user-share → account advisory; and upgrading an admitted user-share lock while a second shared policy holder waits for the account lock. Password/disable operations retain their exclusive user lock; token revocation retains its credential lock. The mutation waits or rejects at the existing authoritative boundary instead of bypassing either fence. Retries were not added.

**Actual verification:** the existing owner and an existing movie relationship were used in the private actual-data clone. An ordinary temporary scoped API credential was created and authenticated; its value remained in memory. Both sides invoked real functions: `publicMutation` and `trackInTransaction`, using the actual relationship's unchanged value to avoid activity/export changes. The audited public mutation reproduced SQLSTATE **40P01**. With the implementation, both calls completed. Replay returned the prior result; revoked token, disabled account and withdrawn API feature were rejected. This is full-function/domain race evidence, not a full network/HTTP-handler race or every possible write schedule. See [public race evidence](evidence/implementation-data-public-race.json).

The API transaction owner serves tracking/bulk tracking, relationships, ratings, music listens, game progress, reading progress and webhook mutations. The lock repair therefore applies to every public mutation route. Only the actual existing relationship route was exercised in this controlled race; existing route-specific regression coverage and the coordinator's broader gates remain relevant.

## DATA-02 — bounded sequence planning with live occurrence validation

The final implementation retains one complete sequence census to plan each scoped or implicit collection bulk command. It avoids an unused second collection census for an explicit source and uses a linear first-unwatched map. The census does not grant mutation authority: every Coast-source sequence-bearing normal or bulk tracking change calls the same `sequenceEntry` reader before its watch decision (`service.server.ts:178`).

`sequenceEntry` shares the canonical recursive SQL in `src/lib/core/lists/sequence.server.ts:50` with full sequence enumeration. Its optional occurrence path constrains the initial collection/list-item root and each recursive collection/show/season child before unrelated branches expand. One current matching entry is returned with the current source boundary and the same completion/progress/drop rules (`sequence.server.ts:131`). Every path segment is validated as a UUID without throwing for malformed cursors; validated UUID-array parameters drive direct indexed source/list/child equality, and malformed paths yield no matching occurrence. The final entry ID text comparison preserves exact occurrence identity. Request input cannot supply a trusted entry or skip live membership validation. This preserves a fresh statement-level observation comparable to the former full per-leaf read; it does not promise a transaction-wide immutable catalogue snapshot.

Boundary writers now share the existing policy → account order. Clearing a rewatch enters a transaction, takes `coast_lock_feature_policy` and the account advisory lock before deleting (`rewatch.server.ts:47`). Clearing remains available after the medium is disabled. Setting a boundary retains its existing work-feature check before that lock. Playlist restart retains its playback-feature check and now takes the account lock before updating its boundary (`sequence.server.ts:183`). This ordering covers normal and public bulk consumers without adding caches, schedulers or client flags.

**Final actual-data verification:** three existing collections with 2, 8 and 23 leaves were compared against audited tracking source, both with implicit collection context and an explicit source. All twelve mutations rolled back. Private comparison rows were discarded in memory; evidence contains aggregate booleans/counts only. ## DATA-10 — fresh auth reads without an ordinary session mutex

`src/lib/server/auth/index.ts` now authenticates an ordinary current/grace token through one fresh joined session/user statement. It checks session expiry and disabled state in that snapshot and returns the same public user projection. This introduces no authorization cache. A committed logout/disable before the statement is rejected; a successful read is admitted at its fresh statement snapshot, as with other request authentication decisions.

Only a due current-token rotation enters the existing transaction. It rereads the session with `FOR UPDATE`, rereads the enabled user and rechecks rotation eligibility after waiting. A competing winner therefore supplies the 30-second grace path without issuing a second replacement token. Token hashing occurs before taking the session row lock. Rotation lifetime, old-token expiry, logout, password/disable revocation and cookie publication retain their existing owner contracts.

**Actual verification:** normal temporary sessions were created for the existing real clone owner. With a deliberately held session row, audited authentication remained blocked and the new ordinary read completed while that lock was still held. This is a controlled contention proof, not a normal latency benchmark. Eight concurrent due-rotation calls authenticated with exactly one replacement token; old-token grace was accepted, expired grace and logout were rejected. A rotation waiting behind deletion returned no session, and a disabled account was rejected. See [combined auth evidence](evidence/implementation-data-actual.json).

Every browser-cookie request using `authenticateSession`, including routes, browser API and artwork requests, receives this common behavior. Bearer-token quotas remain separate. Normal signed-in browser acceptance and broader account-management regression execution are coordinator-owned.

## DATA-11 — admit only relevant medium projections for a shared card page

The existing card helper now resolves bounded canonical identity/category pairs and starts only relevant medium projections, retaining each owner's policies and the outer duplicate/order contract. All 180 actual complete-output comparisons and three validation controls matched. Single-medium pages save two ORM statements; mixed pages pay one additional identity query. Small local timing samples do not establish a general latency improvement. See [card admission implementation and tradeoffs](implementation-card-categories.md) and [actual evidence](evidence/implementation-card-categories-actual.json). This change touched only the schema import and card helper in the coordinator-owned Collection module; assessment SQL remained intact.
