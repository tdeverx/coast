# Adopted bounded repair for the installed SvelteKit navigation owner

Status: adopted after the user explicitly approved the reviewed dependency patch and maintenance obligation. The installed Kit client now matches the exact reviewed candidate. All 21 installed-owner schedules, drift checks and clean offline frozen full/production installs passed. Normal signed-in browser acceptance remains pending with root. The app’s routing UI and approved animation were preserved; no normal database or toast file was changed by this work.

The [adoption receipt](evidence/navigation-adoption.json) pins every adopted file and retains packaging/test failures with their exact boundaries. The [original proposal](evidence/navigation-adoption-proposal-md.txt) and [original record](evidence/navigation-adoption-proposal-json.txt) remain immutable historical artifacts.

The observed Discover exception is real: its outgoing derived expression reads `data.trending.length`, but the value was absent. Its own server load always returns `trending`. The exact transport/commit trace for that occurrence was not captured, so the source race below is a confirmed separate structural defect and a strong cause candidate; it is not a proven reconstruction of that particular click sequence. The earlier Settings `subtitleLanguages.join` exception remains associated only by hypothesis.

The root layout retains its approved 120 ms fade before the framework commit and 180 ms fade-in callback. Before this patch, installed Kit checked navigation ownership before that wait and again only after rendering. A newer navigation or invalidation could take ownership during the wait, yet the obsolete navigation still changed `current`, installed its render result, and registered its post-navigation callback. Version 2 sends only changed `data_N` props, so an intermediate obsolete commit could invalidate a newer result's assumptions about which page data was already installed.

Official upstream PR [17302](https://github.com/sveltejs/kit/pull/17302) describes the same defect and proposes a fix. On 18 October 2026 its API status was open and unmerged. At that pre-adoption check, official `version-2` and the `2.70.3` release tag were byte-identical to the unpatched installed client; the then-checked latest stable [3.1.0](https://github.com/sveltejs/kit/releases/tag/%40sveltejs/kit%403.1.0) and main also lacked the ownership check after `onNavigate`. A dependency upgrade is therefore not a verified cure. The older matching PR 17200 also reports open/unmerged through the API, despite the newer PR's prose calling it replaced. We did not install either PR build.

## Adopted exact change

Only `@sveltejs/kit@2.70.3/src/runtime/client/client.js` is patched. Source before: `a2e26ea4f6b2668c396af9b44bbda2047640c2c9cbb81d3660ec4b1e3310a2c3`. Candidate: `8cfd583bd4d9c9aff69d74a8f3440f7b744d731baaeb5133c8e4605a93663141`. Patch: `94c566a791131b766fe29e8e53ef9107f0ac49de92f9ab7441c629b1077bb78f`.

1. After the `onNavigate` promises settle, reject a superseded navigation before changing current state or registering its returned callbacks. Discard a preload fork already removed from the shared preload slot.
2. Give each navigation its own wrapper registrations for returned callbacks. Cleanup from an obsolete navigation cannot remove a newer registration of the same function object.
3. Remove those registrations if rendering later settles after supersession. Before a successful newer navigation dispatches callbacks, remove any older registration whose rendering has not settled yet.
4. Explicit additional fence beyond the upstream proposal: resolve a taken preload fork before mutating `current`, then check ownership again. Discard the fork and unregister the obsolete callbacks on that exit. The upstream-equivalent backport failed a controlled pending-fork schedule without this additional fence. Fork preloading is disabled in the present app; this control protects the optional installed-owner path rather than claiming an actual observed fork failure.

5. Additional owner repair: when `_invalidate` takes its new token, synchronously unregister every older returned-callback registration before any await or subscriber notification. Every registration belongs to an obsolete navigation token, even if its active indicator was already cleared. A non-null current in-app navigation is also obsolete. Clear `is_navigating` and `updating` synchronously before notifying the real writable store that `navigating.current` is null. No delayed cleanup can clear a newer subscriber-started navigation. A full-page leave with no internal current navigation retains its suppression flag. Old `navigation.complete` still rejects through the existing ownership path. There is no change to history, scroll, autoscroll or ordinary idle invalidation.

Version 2 has no version-3 shallow-goto callback path, so that upstream hunk is inapplicable. Regular shallow `pushState`/`replaceState` behavior is unchanged. This repair does not redesign or remove the app's fade, serialize user input, add a router facade, add a scheduler/cache, suppress the wrong-shape error with defaults, or change route components.

## Tradeoffs and alternatives

The user approved the bounded dependency repair above because it preserves the approved animation and repairs the common commit owner. It now carries the accepted local maintenance/drift obligation; the optional fork fence is a disclosed divergence. Installed-runtime schedules and install repeatability passed; actual browser acceptance is still required. The invalidation owner extension is an explicit additional divergence from the open upstream proposal and passed independent source review; actual browser acceptance remains pending.

Waiting for a maintained upstream release avoids the local patch obligation but leaves the defect unresolved; that is not completion. Removing the awaited fade may reduce the common user-event window but changes fast-navigation timing and does not eliminate the installed Promise.all ownership gap. A major dependency upgrade is broad work and the latest source still has the gap. Route keys, per-page fallback arrays and per-feature shims would obscure the shared authority defect and are not proposed.

Existing browser history entries pushed before the hook wait remain subject to Kit's current behavior when a navigation aborts; this candidate prevents its later state/render commit but does not retract an already-pushed history entry. Back/forward acceptance is therefore material.
