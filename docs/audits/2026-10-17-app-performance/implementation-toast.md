## Shared ownership and behavior

One nullable `notifications.toast_hidden_at` timestamp belongs to the existing notification row. Acknowledged normal toast hiding survives canonical future DTO reads without marking the inbox read, dismissing its card, changing creation time or reducing the unread count. The root feed keeps its existing filters, ordering and default of 50 / maximum of 200 window; hidden rows are not removed from that window. Source-key updates retain suppression. Existing source resolution, deletion and user cascade remove it with the notification. An intentional delete/re-create is a new notice. There is no TTL, separate suppression table or new general inbox age purge.

The canonical client owner serves the application host and UI previews. The application keys its host by viewer. It preserves three visible notices, the initial-only 30-second normal-notice age rule and seven-second auto-expiry. Initial read or already-hidden notices create no persistence/timer work. Newly arriving old notices retain the existing behavior. Previews write nothing. Local sets and timers are pruned to the current DTO; queued plus in-flight IDs are capped together at 200, with one 15-second abortable write flight. Capacity exhaustion leaves additional notices visible and exposes Retry rather than discarding an admitted intent. A separate lane owns at most one optional refresh and one coalesced follow-up flag; a held refresh cannot block subsequent writes or retry. Disposal clears timers, aborts the write and fences late feedback/follow-up.

`POST notifications/toast-hidden` accepts a strict 1–200 UUID list, deduplicates it and only updates owned rows with null timestamps. One bounded SQL statement acknowledges requested existing owned IDs, including already-hidden retries, without rewriting those rows; foreign/missing IDs are not acknowledged as owned.

Persistent dismissal keeps the existing read+dismiss endpoint. A **genuine `ApiError` with status 404** is terminal “no longer available” reconciliation: a prior lost acknowledgement, deletion or privacy withdrawal can remove the notice from that endpoint's visible set. The host releases that pending intent and refreshes without claiming a new successful write. 401/403/5xx, network errors and plain status-shaped objects retain rollback/retry. Refresh failure gives a refresh-only hint; it cannot turn an acknowledged write into a retry or imply a new write for an unavailable notice. Unsent/failed intents are not promised durable across a hard reload; durable state begins with server acknowledgement.
