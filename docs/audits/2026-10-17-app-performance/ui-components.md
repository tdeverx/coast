## New findings

### UIC-01 — P3: menu identity repeatedly serializes unrelated complete user settings

**Owner:** `src/lib/ui/controls/work.svelte.ts:10–14`; consumers: `ScreenActions.svelte:78,94`, `CatalogueActions.svelte:45,62`, `WorkListActions.svelte:17–19`, `PartyMenu.svelte:48–49`, and `createWorkActions` itself.

`workMenuScope` JSON-stringifies target/revision/policy **and the complete `page.data.user.settings` object**. That includes profile/bio/avatar bytes that do not determine most action snapshots. Scope is recomputed in reactive effects and again by resource synchronization/load/current-key checks, so it is not one serialization per page. Closed mounted menu owners also compute their scopes to remain invalidatable. This compounds the retained-card ownership in UIS-03/04; it does not mean every closed menu performs HTTP reads.

Actual root aggregate evidence shows development settings max16,276 stored bytes with an inline avatar max15,243 bytes; deployed max15,235/settings and14,947/avatar. These are PostgreSQL stored sizes, not exact JSON string lengths or measured browser allocation. The allowed220,000-character avatar cap from DATA-09 is a capacity boundary, not the actual present avatar size. No CPU/heap benchmark was run for these keys. Equivalent settings values yield the same final string, which correctly avoids a refetch on equivalent heartbeat replacement; the serialization work still occurs whenever the scope is evaluated.

**Smallest shared option:** define a primitive effective-policy/settings signature in this existing menu-scope owner, using the actual relevant fields and revisions. Separate stable viewer/policy identity from target identity so large profile payloads are not repeatedly copied. This browser signature is only invalidation identity; it must never cache or replace server authorization. Do not implement a private key in each medium or add a process-wide user/settings cache.

**All-consumer acceptance:** actual long browse with screen/music/game/book/comic menus, list membership, party queue, closed/open/context-replaced menus; record key evaluations/serialized bytes and unnecessary menu refetches. Profile avatar/bio-only updates must not refetch unrelated action snapshots; relevant role/capability/settings/identity/tracking changes must invalidate every applicable consumer. Preserve page heartbeat equivalence, privacy withdrawal and exact list occurrence/selected playthrough identity. Related: DATA-09 and UIS-03/04.

### UIC-02 — P2: the request dialog ignores cancellation of its own option read

**Owner:** `src/lib/ui/components/RequestDialog.svelte:58–95`; existing good sibling: `src/lib/ui/controls/requests.svelte.ts:15–22,57–78`; transport: `src/lib/ui/client.ts:44–64`.

The direct request dialog loads `requests/options?mediaId=…` without an AbortSignal. Its effect teardown merely increments `generation`. Closing, changing target or replacing the dialog correctly prevents stale publication, but leaves the browser/backend request running. A retry starts another read without aborting the old one. The same option endpoint in `createRequestControls` already has a controller, cancellation and generation ownership, so menu and direct-dialog behavior drift.

**Smallest shared option:** have both callers use the existing abortable resource/request-option owner, retaining the dialog's option-selection behavior and the menu's independent lifetime. Extend that common owner if needed; do not add another private cancellation algorithm. Propagate the signal through the common route/service/provider seams too, as required by PR-04/PJ-14. Explicit submitted request writes keep their acknowledgement/recovery semantics and must not be treated like disposable reads.

**All-consumer acceptance:** actual direct Request button, menu request choices, show-season/episode targeting, supplied preloaded options and missing options; close, retry, context replace and feature withdrawal while slow. At most one needed option read per owner, cancelled queued work starts no provider call, late old errors cannot affect the new dialog, and a remaining independent consumer still succeeds. Existing generation guards remain useful but are not a substitute for abort. Related: PR-04 concrete cancellation omissions; PJ-14 overall wait/deadline policy.

### UIC-03 — P2 at multi-sender cardinality: one recommendation response refreshes the page once per recommendation ID

**Owner:** `src/lib/ui/components/WorkActions.svelte:17–20`; common mutation/refresh boundary: `src/lib/ui/client.ts:75–94,101–105`, `mutation.svelte.ts:4–17`; domain: `src/lib/social/service.server.ts:114–136`.

A grouped work card may contain several sender recommendation IDs. Save/Dismiss loops through every ID and awaits `change` for each. Each successful `change` awaits tracking/social invalidation; while a shallow panel is open it awaits the common state-preserving `refreshAll`. Thus N necessary per-recommendation responses trigger N sequential refresh cycles before the next response, even though the logical user action is one grouped response. The mutation wrapper itself has a no-op refresh here; this amplification comes from using the refreshing transport inside the loop. DATA-06 covers the server-side received-recommendation projection; this is a different completion/refresh consumer.

This pass did not observe an actual multi-sender operation or measure its latency. N=1 has no extra cycle. A partial failure can leave earlier IDs acknowledged and later IDs pending; a generic retry must not misreport earlier writes as failed.

**Smallest shared option:** use the common API mutation boundary to acknowledge the per-ID writes and perform one coalesced refresh after the logical operation, including meaningful partial-success recovery. Introduce a narrow batched-mutation/refresh capability in the existing client/mutation owner if multiple consumers need it; keep domain operations in their existing server services. **Alternative:** a bounded batch response endpoint using the same recommendation domain writer, with exact per-ID outcomes. This can reduce HTTP requests too but needs explicit atomic/partial-result semantics. Do not simply parallelize unrestricted writes or drop sender identities.

**All-consumer acceptance:** actual grouped recommendation cards from screen/music/game/reading where data exists; save/dismiss with1/multiple IDs, partial failure, route/menu refresh failure and target replacement. Exact IDs and final states must match, each acknowledged mutation is preserved, and refresh count is one per logical completion/recovery, not N. Check other multi-target client loops and sequence-start refreshes through the same shared completion contract before declaring the generic fix complete. Related: DATA-06, shared acknowledgement rules in PR-02.

### UIC-04 — P2 at large previews: Collection export review transfers full entries and mounts all review panels

**Owners:** shared durable projection preview/read model `src/lib/collection/projection.server.ts:17–18,78–92`; UI `src/lib/ui/components/CollectionProjectionSettings.svelte:14–17,35–40`.

The server returns complete `Entry` objects in additions/removals/uncertain/conflicts, including delivery `payload` and remote `snapshot`. This component displays work IDs/titles/counts and submits the durable preview ID; approval re-reads the server-stored preview. The browser does not use those delivery payloads/snapshots. Summary lists slice to60, but the full arrays still arrive and remain in reactive preview state. The actual review panel loop has no page bound, rendering all conflicts plus uncertain entries. Its deduplication runs `.some` over conflicts for every uncertain entry, giving C×U comparison work. Closing the dialog retains the full preview in that component until replacement/unmount; this is one retained preview, not a growing-per-close leak.

No large actual preview was generated, and no actual transfer/DOM/memory cost is claimed. Complete server-side remote/desired evidence is necessary for safe destructive Collection decisions; reducing that durable evidence would be an invalid optimization.

**Smallest shared option:** return a narrow browser preview DTO while keeping complete evidence in the existing durable preview row; derive review IDs with a Set/Map once. **Next option:** page the review list from that same preview owner with exact totals and stable IDs, using the existing bounded resource/pagination composition. Keep every review accessible and approval/version/account fences authoritative. Reuse this generic bounded-review policy for conflict review consumers identified in PJ-12; do not create a second preview store or scheduler, or silently hide entries after60.

**All-consumer acceptance:** actual projection preview on a disposable real-data clone, including additions/removals/conflicts/uncertain overlap; compare full IDs/counts/choices and unchanged approval guards. Measure transferred bytes, mounted panels and retained state on open/close/reopen; narrow DTO must contain no unused delivery payload/snapshot. Pagination must preserve complete review access, exact chosen decisions and remote/version-change rejection. Related: PJ-12 review cardinality, UIS-03 retained-list/window policy.
