## FRT-01 — P2: a selected search medium still starts other enabled searches

`src/routes/search/+page.server.ts:24,65-120` computes and validates `selectedView`, but the returned work independently starts screen `searchMedia`, music and game `searchPresentations`, and `readingSearch` whenever their features are enabled. Initial `mediaViews` and reading-local search also run independently of the selected medium. The client combines results and its `busy` state waits for all four returned promises (`+page.svelte:23-26,40-67`). Server work therefore remains broader than a book-only, game-only or movie-only request. Quick successive debounced searches abandon publication of older results but do not pass `event.request.signal` into those provider owners.

This is source-confirmed excess demand, not a measured live-provider latency saving. An all-media search legitimately needs all enabled media; its required breadth must remain. Reading filter derivation also uses the original `view` rather than the normalized selected view, so acceptance must include `type=book` with the default view, not just `view=read`.

**Smallest option:** derive one normalized search plan from validated medium/type/features and use it for initial local reads, provider searches, response promises and client busy/error state. Thread cancellation through existing provider operations. **Larger option:** demand-load each result group through the existing Shelf/resource contract; justify this only if real all-media searches show sufficient benefit to offset the orchestration change. Do not build separate per-medium schedulers.

**All consumers:** unified Search, medium/type links, reading pagination, empty query, public screen search and every enabled movie/show/music/game/book/comic search provider. **Acceptance:** use real imported titles and real permitted providers, count requested provider families for each selection, rapidly replace a query, hide/leave/reopen, verify exact result identities/order and correct busy/error state. Disabled/irrelevant providers must receive zero calls. No actual external provider search replay was performed by the audit, so the expected reduction in work is not a before/after measurement.

## FRT-02 — P2: public details activate a signed-in-only enrichment endpoint

Actual deployed public browsing succeeded through Discover → the featured title, but generated two `401` responses from `/api/v1/media/<id>/insights`. See [browser evidence](evidence/deployed-real-browser.json). The current source has the same contract mismatch: `src/routes/media/[id]/+page.server.ts:20-21` explicitly provides a public details model; `src/lib/media/DetailRows.svelte:84-109` activates source insights without checking signed-in enrichment permission; `src/routes/api/v1/media/[id]/insights/+server.ts:5` requires a user. The shared API client also dispatches `coast:auth-expired` on any such non-share `401` (`src/lib/ui/client.ts:70-71`), including an anonymous consumer.

**Smallest option:** carry explicit enrichment capabilities in the canonical detail view model, gate optional loads at their shared owner, and distinguish an expired authenticated session from an anonymous request in the shared transport. Keep the endpoint's existing authorization. **Alternative:** introduce a deliberately bounded public read model only if public provider enrichment is a product requirement; that needs a separate privacy/provider review and is unnecessary merely to stop failed calls.

**All consumers:** direct public details, signed-in full pages, shallow detail panels, community/review/crew sections, public profiles that link to details, and shared API error delivery. **Acceptance:** on actual public catalogue data, Discover → title → insights/credits/reviews emits no private requests or false expiry notice; authenticated requests still work and genuine session expiry still prompts sign-in. Deployed build is `de2ed4b…`, while the audited build is `eb06738…`; the runtime observation and matching current source are separate evidence, not proof the two builds are identical.

## FRT-03 — P2: profile reads and onboarding polling bypass shared cancellation ownership

`src/routes/profile/[username]/+page.svelte:102-153` uses integer request guards for favourites/insights, which protect publication, but its API reads have no AbortSignal or component-disposal cancellation. Every owner selection also queues `savePreference` in a promise chain (`:77-83`) and a successful write refreshes route dependencies. Superseded reads still consume backend work. This is a consumer of the common request-lifetime problem described by PR-02/PR-03 and UIS-02, not a reason to add another loader implementation.

`src/routes/onboarding/+page.svelte:12-19` correctly prevents overlapping ticks and respects the provider device-code interval. Its two-second import refresh continues when hidden and only clears the future interval on unmount; the pending fetch/invalidation remains owned by an absent page. Registration/device-flow counterparts and shell presence belong in the same audit matrix, with their distinct required cadences preserved.

**Smallest option:** migrate these reads to the established abortable resource owner; use one in-flight poll with explicit teardown and visibility policy. Coalesce pending equivalent profile preferences while retaining acknowledged writes and final user choice. A hidden import-status view can resume immediately when visible; do not pause the durable import itself or active playback/party control. **Acceptance:** actual profile filters and actual onboarding jobs, slow/cancelled/superseded responses, navigation during a request, hidden/resume and failed preference writes. Count request starts, aborts, committed preferences and retained callbacks. Current source proves the missing cancellation seam; present latency impact is not measured.

## FRT-04 — P2 under chunk failure: shared lazy component imports lack a recovery state

The root layout loads Reader, MediaDetailPanel, FriendsPanel, NotificationInbox and StreamsPanel with `void import(...).then(...).finally(...)` and no rejection handler (`src/routes/+layout.svelte:7-8,34-45`). For You uses the same pattern for DynamicFeed (`src/routes/for-you/+page.svelte:2-4`). If the real chunk cannot load after a deployment, connection interruption or cache failure, the promise becomes unhandled; the requested panel/component is absent and the consumer has no scoped retry state. Diagnostics recording an unhandled rejection does not make the requested UI recoverable. Import caching after a successful load is healthy and should remain.

**Smallest option:** one canonical lazy-component state/error/retry owner compatible with the existing resource and toast/error system. Consumers declare demand and retry; stale completions must not publish into a disposed scope. An ES module import cannot be physically cancelled like fetch, so distinguish stopping publication from stopping network work. **Alternative:** static import selected tiny components when actual entry-cost evidence favors it, while keeping heavy readers/format engines demand-only. Do not eagerly bundle all experiments to mask load failures.

**All consumers:** all root panels, reading activation, shared details, dynamic feed, UI-reference editors and chart imports. **Acceptance:** intercept failure of an actual built chunk during a real-data flow, verify a visible actionable failure, restore the request and retry, close before resolution, reopen and change account. No chunk-failure injection was performed on the live deployment; this remains a source-confirmed recovery defect requiring that acceptance test.

## Large-detail rendering is the frontend consequence of DATA-04

Do not count this twice. The actual largest saved season has 829 episodes. Current-source `detailsData` returns every episode before the lazy detail Shelf can help. The signed-in rendered page mounted all 829 cards and about 29,000 DOM nodes; the first browser observation transferred about 6.93 MB of uncompressed HTML. The domain JSON alone was 1,490,119 bytes and used 264 ORM statements. The enhancement path can rerun the rich detail loader and serialize another rich model (`src/lib/application/media-details.server.ts:10-26`); it should enrich a narrow header/section contract instead.

The shared repair must start with bounded detail read contracts and use the existing Shelf adapters for child pages, collection members, credits and history. UI-only hiding, `content-visibility`, or virtualizing after eagerly transferring all data cannot remove the initial SQL/serialization cost. Conversely, server pagination alone does not bound a client that appends every page forever (UIS-03). Treat both boundaries explicitly. Keep exact season order, episode anchors, special filters, edition choice, occurrence identity, back navigation, focus and party/playback state.

## Healthy patterns and limits

- Most medium routes are thin wrappers around canonical detail loaders/components. Full pages and shallow panels share medium dispatch rather than maintaining separate tracking implementations.
- Library validates filters and reads only the selected grid surface; its overview delegates initial demand to Shelf. Planning and Requests use bounded server results and shared cards. Requests builds one lookup Map for card details.
- Search input debounce has component teardown; the issue is cancellation of the already-started server/provider work. Profile request counters prevent stale publication; they do not stop the old operation.
- Root session polling and normal StreamsPanel polling prevent overlap and check document visibility. Presence, active audio and party heartbeats need separate essential-work rules.
- Heavy reader/format engines and selected chart engines are dynamically imported. A total build-size sum is not an initial-download measurement.
- Preview/gallery data are fictional by design. Their source can be audited for ownership and complexity, but successful preview fixtures are not real-account or actual-file performance verification.

The main report records real browser evidence, expected clone-only artwork/credential failures, exact build identities and the open device/media acceptance matrix. Those limitations apply to every recommendation here.


## FRT-05 — public ancestry includes recommendation edges

Discovered during post-audit anonymous normal-dev acceptance. The real public hero used an unrelated show title because publicDetails selected every incoming media_relationships edge as a parent. Baseline actual-data verification reproduced related parents in movie/show cohorts. Restricting that shared parent query to structural edge kinds removes unrelated hydration and fixes the title without changing the recommendation graph or hero UI. Eight actual-data full-response comparisons preserve every field outside corrected parents; the original live page also passed after reload. For the six bare component loaders, the smallest coherent implementation needs no new request framework: one existing resource per independent import, a demand-only effect that calls `load` without tracking its own busy/error transitions, cleanup that cancels delivery, and `reportFailure` with an explicit retry callback while the same demand/viewer is active. An effect that repeatedly tests `!data && !busy` can immediately retry after rejection; avoid a reactive failure loop. Scope errors and retries to active demand, keep resolved immutable components reusable, and fence late errors after close/logout/feature withdrawal. ES module fetching itself is not physically abortable through this resource signal.

A larger reusable import adapter could centralize successful/rejected Promise retention for chart, reference and component consumers, but it must preserve their different SSR and domain lifecycle contracts. It is optional complexity, not a requirement to replace healthy caught reader/detail paths. Selected static imports remain an alternative only with measured entry-cost evidence; heavy reader/format engines should remain demand-loaded.

The next deliberate batch must exercise an actual built chunk in a real-data flow: cause a controlled chunk-load failure, confirm scoped actionable feedback without an unhandled rejection, restore the chunk and invoke retry, then verify the intended component and data appear. Also close or change account before completion; toggle capability; repeat retry while pending; check successful cache reuse and compact-empty/SSR demand. For HLS, preserve the exact session/source/party ownership and verify no extra decoder or duplicate network attachment after retry. Browser module caching and deployment asset availability can affect whether another `import()` actually recovers; no universal recovery claim follows from a unit loader stub. No automatic page reload is proposed, and this report does not treat any controlled future chunk failure as a naturally occurring incident.
