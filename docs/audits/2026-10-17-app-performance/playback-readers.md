# Playback, music, parties, sharing and readers — performance audit

Date: 17 October 2026. Audited checkout: `eb0673873462b71118d1c11678d128958a05ff07`. The dispatch named `33a9d2f5`; the working checkout had already advanced before this pass. `playback-readers-coverage.json` records hashes of the current files. This is a fresh source audit, informed by `docs/performance.md`; older reports are not evidence that a current problem persists.

This report makes no implementation changes. It distinguishes a demonstrated resource defect, deterministic failure/complexity proofs, source-confirmed work, and measurement-gated opportunities. It does **not** certify real playback latency, codec reliability or a leak-free browser. The top-level report owns actual application/database observations and the full regression results. Supplementary authored failure probes in this report establish mechanisms; they are not replacements for the user's actual-data acceptance requirement.

## Principal result

The most concrete new issue is in the installed EPUB engine: Coast calls its destroy methods, but EPUB.js 0.3.93 revokes archive **paths**, rather than the Blob URLs stored at those paths. Rewritten CSS URLs have no revocation owner either. Repeated reader open/close or minimize/reopen cycles can therefore retain assets even though the visible chapter is removed. A probe of the real installed library and real Blob URL store left 3, 6, 9, 12 and 15 URLs fetchable after five destroy cycles. This is a demonstrated ownership defect, not a production-memory estimate.

Other substantial concerns are incomplete cancellation in music/trailer entry points, control/report operations that can wait indefinitely on a hung browser request, repeated music persistence transactions during browsing, eager EPUB processing, and party/read-file work repeated at transport cadence. Several large improvements made previously are present: lazy format imports, one rendered comic/PDF page, worker termination on archive cancellation, range-backed CBZ reads, explicit session/account fences, coalesced bookmark and progress writers, bounded music child pages, and provider I/O outside the principal playback/session transactions.

## Findings and options

### PR-01 — EPUB destruction fails to revoke owned assets

**Priority P1; demonstrated dependency lifecycle defect; high confidence.** Coast owner: `src/lib/reading/reader/epub.ts:33–43,56–57`; dependency: `node_modules/epubjs/src/archive.js:183–218,245–252`, `resources.js:137–180,195–239,306–318`, `book.js:479–505,729–746`. Installed package version is 0.3.93; the same defect is in its CommonJS and distributed builds.

`ePub()` opens a binary archive using default Blob URL replacement. Archive cache maps `/OPS/image.svg` to `blob:…`. `Archive.destroy()` loops over object keys and passes each key to `revokeObjectURL`; it then discards the cache. It never revokes the values. Resource replacement generates an additional Blob URL for rewritten CSS, and `Resources.destroy()` only clears references. Calling `rendition.destroy()` and `book.destroy()` does not correct either ownership gap.

The real-library probe builds an authored archive containing one image and one stylesheet, runs the actual Archive and Resources implementations, and verifies URL reachability after destruction. After cycles 1–5, allocations and fetchable URLs grow 3→6→9→12→15. There are ten attempted revocations and zero matching any allocated URL. Actual private file asset bytes and browser heap were not measured. This can occur on minimize/reopen too: `Reader.svelte:28,59` destroys the engine when hidden and creates it again when shown.

**Smallest option:** make the feature adapter own its per-book resource URL set, including rewritten CSS, and revoke those exact values on success/failure/cancellation. Use the existing library's resource creation boundaries or a narrowly maintained dependency patch with a regression; avoid changing the global URL implementation in application runtime. Handle late resource-creation promises after destruction, so a simple snapshot of current URLs does not leak assets allocated later. **Alternative:** use a corrected upstream release after verifying this behavior and archive hardening. **Larger option:** replace the rendition engine only if actual-file results justify the maintenance cost. No replacement dependency is approved by this report.

**Acceptance:** actual-file EPUB with image/font/CSS resources; open → chapter turns → minimize → reopen → close repeated 20 times; close while resources are still resolving; malformed chapter failure; count allocated minus revoked URLs and browser workers/frames. Retained per-book assets must return to zero after each disposed owner. Retained heap/RSS must reach a plateau. Preserve CFI resume, internal navigation, script/external-resource protections and party location behavior. Existing archive bounds must continue passing.

### PR-02 — A hung report can block Stop and accumulate lifecycle events

**Priority P2; deterministic failure-path proof; high mechanism confidence, incidence unmeasured.** `src/lib/playback/reports.ts:4–25`, `src/lib/ui/components/PersistentPlayer.svelte:140–176,202–219`, `src/lib/ui/client.ts:44–64`.

There is one in-flight writer, and consecutive queued progress is correctly coalesced. Lifecycle events intentionally remain ordered. Browser JSON requests have no deadline unless a caller provides cancellation; report sends provide neither. A send that never settles therefore holds every later lifecycle event. `close()` pauses immediately but waits for `report('stop')` before clearing the session; the media source/HLS owner is released only when that session/source changes. Playback replacement also waits for the old controller's stop.

The production queue probe holds the first send, enqueues 1,000 alternating pause/start lifecycle events and a final stop, and observes one send and an unsettled stop. On release it drains all 1,002 sends. This is not a realistic claim of 1,000 normal user clicks; it proves the queue has no failure bound. A slow request delays the final drain even for an ordinary few events.

**Smallest option:** add an explicitly owned deadline/recovery state to report delivery, and release local media on Stop independently of the bounded persistence attempt. Preserve start acknowledgement retry, ordering and final played-time accounting. An ambiguous timeout must not blindly replay a non-idempotent event. The server's current session/event idempotency must be verified before retrying. **Alternative:** durable client outbox for lifecycle transitions; more complexity, justified only by an offline persistence requirement. Do not coalesce across pause/start/stop just to force a small queue.

**Acceptance:** actual playback with transport delayed/disconnected at start, pause, seek, ended and stop; Stop releases decoder/HLS/network ownership within a named deadline, retains a clear unsaved/retry notice, and cannot overwrite the replacement session. Final drain settles or reports failure; no infinite promise chain or growing queue after repeated failure cycles. Existing `playback-reports.test.ts` order/acknowledgement assertions remain unchanged.

### PR-03 — Visible-reader heartbeats overlap and outlive the renderer

**Priority P2; deterministic failure-path proof; high confidence.** `src/lib/reading/Reader.svelte:28–30,59`; `src/lib/reading/sessions.server.ts:145`; `src/lib/ui/client.ts:44–64`.

The visible reader sends a heartbeat every 60 seconds. Unlike party/share/streams polling, it has no in-flight guard. It also omits the effect's AbortSignal; teardown clears the interval but leaves requests in flight. The exact callback, driven through 20 controlled ticks with a held transport, starts 20 unsettled requests and supplies zero signals. This proves overlap under slow/unsettled responses, not that normal heartbeats currently take a minute.

**Smallest option:** one pending heartbeat per renderer owner; pass the existing controller's signal and clear its pending flag in `finally`. Keep the deliberate 60-second visible heartbeat even for an unchanged page: session presence/resume ordering is required. **Alternative:** one session heartbeat owner outside the renderer if minimized readers must remain live; that is a product lifetime decision, not an excuse to keep all renderers alive.

**Acceptance:** actual-file reader under delayed heartbeat, then minimize, replace and close; maximum one request per owner, teardown aborts it, no stale error or close affects the replacement session. No heartbeats while never opened/hidden; reopening resumes required presence without replaying abandoned requests.

### PR-04 — Cancellation stops at music/trailer route boundaries

**Priority P2; source-confirmed defect; high confidence.** `src/lib/server/api/providers.server.ts:50–60`; `src/lib/music/artwork.server.ts:19–21`; `src/lib/server/queries/music.ts:12,35–41`; `src/routes/music/[connection]/[id]/+page.server.ts:8–25`; `src/lib/playback/service.server.ts:727–759`; `src/lib/server/api/media.server.ts:57`.

`musicLibrary`, `musicDetails`, `musicSourceDetailData` and Jellyfin adapters accept AbortSignal, but several public callers omit it. The lazy `music/source/children` path passes it correctly; the provider API, complete source page, ordinary `/music` source browsing, and music artwork permission lookup do not. A card/menu/route that is cancelled can leave provider work admitted or running and may continue shared metadata persistence. Its browser response being ignored is not cancellation. Music artwork's image byte fetch has a signal, but the preceding authenticated metadata read does not. Local-trailer discovery similarly omits cancellation despite the hero caller owning an AbortController.

**Smallest option:** thread the original request signal through existing route/query/service/adapter seams and recheck before expensive observations/publication. Preserve writes that have already committed and explicit operational cleanup; do not throw away an acknowledged command. Trailer discovery should deduplicate repeated availability entries referring to one connection/item rather than call the same provider per media source. **Shared metadata alternative:** reference-counted single-flight with cancellation when its last consumer leaves; measure first, and keep authorization/account checks authoritative. Public Open Library/Comic Vine metadata flights have their own bounded provider lifetime but do not expose per-consumer cancellation; assess those together with the common provider-flight owner.

**Acceptance:** start actual source read, cancel before provider admission and while active; assert no transport starts after queued cancellation, active fetch receives abort, cancelled observation cannot grant account access, and a remaining shared consumer still succeeds. Compare full route, overlay, child shelf, menu and artwork paths. Existing adapter cancellation tests cover a good seam; add regressions at the currently missing callers.

### PR-05 — Music browsing performs serial per-item persistence before returning a page

**Priority P2; source-confirmed work amplification; real-data cost measurement required.** `src/lib/music/service.server.ts:14–20`; `persistence.server.ts:25–83,103–116`; `src/lib/server/queries/music.ts:34–65`.

Rich provider browsing observes every item through `persistMusic` sequentially, each in its own transaction, followed by a separate transaction granting page access. An ordinary source page contains up to 50 items; the generic provider endpoint permits 100. All-source browse runs at most four source operations concurrently but returns 50 cards **per selected source**, with no page-wide 60-card cap. Therefore server hydration, transactions and rendered cards grow with connected sources. Canonical metadata/edition/relationship changes are sensibly compared, but provider-item snapshot and last-seen upserts still occur on unchanged reads; artist credit lookups/inserts and album membership comparisons also remain.

This is not a recommendation to remove freshness or access evidence. The cold-path work is intentional; the question is how much unchanged warm browsing needs. The current user-sync path already distinguishes known shared metadata from missing details (`observeMusicPageAccess`); interactive rich browsing does not reuse that fast path because it must refresh changed artwork/metadata.

**Smallest option:** compare meaningful provider metadata once and skip unchanged structural work while updating access observation in a bounded batch under the current account fence. Preserve exact release occurrences and changed artist/artwork/membership data. **Next option:** one bounded page persistence operation with deterministic lock order and per-item error handling; fewer round trips, but more contention/rollback scope. **Product option:** one explicitly selected source by default or bounded merged source pagination; do not silently drop authorized cards. Requires UI/product agreement because source ordering/paging changes.

**Acceptance:** actual-data clone, replay a representative 50/60-item provider snapshot page twice; measure query count, rows updated, relation churn, revisions and WAL on the unchanged pass. Then change one track's title/artwork, album membership and artist credit; only required canonical work changes, while access freshness remains correct. Cancel at each committed boundary and reconnect mid-page. Report actual response bytes/card count for one versus all configured sources.

### PR-06 — EPUB first-page work scales with the entire expanded archive

**Priority P2; confirmed work shape; actual-file impact unmeasured.** `src/lib/reading/reader/epub.ts:9–28,33–40`; `epub-archive.ts:7–16,20–52`; installed EPUB.js `book.js:479–505`, `resources.js:137–180`.

Remote EPUBs are fully downloaded before opening. The safety preflight enumerates and extracts **every** entry, verifies actual output, then rewrites the complete archive uncompressed and converts it to ArrayBuffer. Zip extraction and writing explicitly set `useWebWorkers:false` in this browser module. EPUB.js opens that stored copy, then eagerly creates replacements for all manifest assets with `Promise.all`, before `book.open()` settles. A single chapter on screen therefore does not imply one chapter's assets in memory. At most 128 MiB input, 256 MiB total expanded output, 32 MiB entry and 10,000 entries are accepted; those are format limits, not peak process-memory budgets.

Supplementary operation counts: an archive with 24 MiB of unused assets is only 28,777 compressed bytes in the authored probe, yet preflight extracts 25,165,886 bytes across all 27 entries and returns a 25,169,782-byte stored archive before the engine can open it. The 1/8/24 MiB cases perform 4/11/27 extractions. These prove total-work scaling and expansion, not real-file compression ratios or browser jank.

**Smallest option:** move verified preflight into a cancellable worker using the existing worker ownership pattern; transfer the verified result. This improves main-thread responsiveness but does not eliminate total CPU or memory copies. **Next option:** a verified on-demand resource adapter with actual-output/aggregate budgets, replacing whole-archive rewrite and eager asset substitution; larger work with chapter/CSS/font correctness risks. **Alternative:** a finite per-session verified-byte cache across minimize/reopen; saves reprocessing but retains substantial memory, so introduce only with a measured byte/lifetime bound. Do not remove preflight protection to make startup fast.

**Acceptance:** actual small/typical/large private EPUBs; first-page, next chapter, minimize/reopen and abort; browser long tasks, elapsed startup, bytes expanded/downloaded, Blob/ArrayBuffer/external memory and URL count. Keep fonts/CSS/images/internal links and CFI resume equivalent. A worker cancellation must terminate decoding, not only abandon its promise. Confirm no unbounded Promise fan-out or retained asset set.

### PR-07 — Native comic storage order can turn forward reading into quadratic traversal

**Priority P2 for adverse files; demonstrated algorithmic bound; actual-file incidence unknown.** `src/lib/reading/reader/archive-decoder.ts:18–35,43–60`; `comic-pages.ts:7–8`; `archive.ts:23,28–31`.

Page display order uses natural filename sort. The native decoder keeps one physical forward cursor; requesting an earlier physical entry resets the archive and skips from the beginning. An archive stored in reverse natural order therefore causes a reset for every ordinary Next action. Exact real native-decoder call counts for a full forward display: natural storage 100/500/1,000 headers; reverse storage 5,050/125,250/500,500 headers, respectively. Natural sorting over lexically stored files is better but still revisits headers (193/1,437/2,884 in those probes). Separately, each native `read(index)` calls `entries.find`, adding a linear metadata lookup per page even for naturally stored archives; a primitive index map can remove that small scan without changing decoder ownership. The native header counts do not include this JavaScript work. Solid-compressed RAR/7z can require substantially more work than the tiny stored TAR count probe; that additional byte/CPU cost has not been measured here.

Cancellation correctly terminates the worker, and each request has a 30-second timeout. That makes the lifetime bounded but can present a slow page turn or timeout for a supported large archive. Moving this work off the main thread is already done.

**Smallest options:** index native entry descriptors by physical entry ID, then retain a strict byte-bounded cache of current/nearby extracted pages if actual navigation warrants it, while keeping natural display order and exact archive checks. Helps Back/Next oscillation; does not remove reverse-order first traversal cost. **Next option:** decoder capability permitting random-access entry offsets or a bounded verified page index; compressed-format support differs. **Larger option:** normalize pages into a separate indexed representation with disk persistence and cleanup; a much larger storage/product decision. Do not extract and retain every page in memory.

**Acceptance:** actual CBZ/CBR/CB7/CBT archives with physical order captured privately; full forward/reverse traversal, rapid remote page replacement, abort and reopen. Count native entry visits and actual decompressed/skipped bytes; verify natural order, output hashes, retained byte bound and worker termination. Include solid 7z/RAR before claiming a general improvement.

### PR-08 — Party heartbeat reads serialize room-wide maintenance for every participant

**Priority P2 scale candidate; source-confirmed repeated work, contention unmeasured.** `src/routes/+layout.svelte:84–88`; `src/lib/playback/synced/client.svelte.ts:101–132`; `service.server.ts:118–161`.

Each joined browser single-flights a two-second heartbeat, including hidden tabs because live party ownership is intentional. `roomState` authorizes, then locks the room `FOR UPDATE`, checks feature policy, writes the caller heartbeat, runs three membership-revocation updates, reads the full roster, rehydrates up to 200 queue items with viewer-specific availability, may reconcile controllers/host/disconnect policy, and returns the complete state. The 16-participant cap prevents unbounded membership, but 16 live browsers still imply a nominal 480 heartbeats/minute against the same room lock. Each audio response repeats the queue and its availability checks even when unchanged.

**Smallest option:** instrument statement count/lock hold/wait and payload bytes first. Separate unchanged liveness from expensive room reconciliation; keep fresh permissions and precise host/buffering transitions. Cache only viewer-independent immutable portions by room revision if evidence warrants it; viewer queue availability and access cannot be process-wide room data. **Alternative:** server event delivery plus explicit heartbeats; potentially large reduction in repeated payloads but introduces connection lifetime/backpressure/reconnect work. Not needed until the current small-room path is measured.

**Acceptance:** actual-data clone with real queued tracks and permitted users; 1/8/16 clients, unchanged/video/audio/reading states, delayed and failed clients; SQL/lock/WAL/payload measurements, command latency and revision races. Preserve 15-second online semantics, 60-second disconnect grace, privacy, feature withdrawal, exact queue repeats and generation revocation. Existing pure timeline tests alone cannot certify database contention.

### PR-09 — Reading-file range requests repeat fresh metadata and authorization work

**Priority P3 opportunity; source-confirmed fan-out; required freshness tradeoff.** `src/lib/reading/sessions.server.ts:90–96,117–132`; `src/lib/providers/jellyfin/reading.server.ts:43–49`.

Every proxied GET/HEAD/range first reads the owned session, user/work/policy and connected account; `streamReading` obtains the Jellyfin context again, then fetches the user's Jellyfin item metadata and compares the complete source fingerprint before starting Download. CBZ uses HTTP ranges, and PDF.js may use multiple range requests, so a logical book opening can require many permission-metadata GETs plus byte GETs. Abort propagation is present on the provider lookup and Download. Range streaming and no-store policy preserve file/version/access correctness.

**Smallest option:** avoid duplicate `getJellyfin` context work within this one request by returning the verified context from the shared owner; project only fields actually used. **Next option:** coalesce concurrent exact user/account-generation/file-fingerprint checks for active consumers with no stale cross-request authorization cache. **Alternative:** immutable per-open byte capability/version pinning only if provider semantics guarantee revocation and version correctness; the present fresh check is a correctness contract, not incidental overhead.

**Acceptance:** actual source PDF/CBZ first page and random page access with Range/HEAD trace; count metadata GETs, byte GETs, transferred versus used bytes, server queries and time-to-page. Revoke access/change source bytes/reconnect between ranges: delivery must stop or explicitly reopen the changed edition. A faster stale capability is not an acceptable optimization.

### PR-10 — Playback relay hydrates full provider snapshots per segment

**Priority P3 projection opportunity; high confidence in redundant projection, gain measurement-gated.** `src/lib/playback/service.server.ts:616–638,655–677,711–723`.

Each manifest/segment/subtitle request selects the complete playback session, obtains current connection/policy, and selects complete `providerItems`, though the stream path only needs `externalId`. The actual aggregate confirms this is a small projection opportunity on the present catalogue: development episode snapshots have median852/max2,399 stored bytes, movies median1,428/max1,912, tracks median1,080/max1,204; deployed values are similar. Albums max5,157 bytes. These are `pg_column_size` stored bytes, not JSON transfer or browser bytes. A three-second-segment shared stream repeatedly performs this local deserialization in addition to fresh authorization and stream admission. No large current snapshot outlier was demonstrated, so this should remain behind the proven lifecycle defects. Native relay uses bounded streaming, not whole-file buffering; a 128 GiB maximum is an allowed stream byte cap, not a retained buffer allocation.

**Smallest option:** narrow provider-item projection to `externalId`; narrow connection/session projections only after listing fields needed by authorization, shared generation and HLS rewrite. **Next option:** consolidate same-request policy/context reads while preserving account-generation checks. Do not cross-request cache access decisions or inline provider credentials into the client.

**Acceptance:** actual provider-item snapshot size distribution and actual stream request count; compare identical returned stream bytes, Range/HEAD/content headers, HLS URI rewriting, account change and share revocation. Measure database bytes hydrated/CPU/allocation before asserting visible latency gains.

### PR-11 — Queue starts have large implicit materialization bounds and silent truncation

**Priority P2 correctness-at-boundary; P3 cost at ordinary scale; source-confirmed, real boundary population unmeasured.** `src/lib/music/queue.server.ts:8–16,30–38`; `editions.server.ts:27–28`; `src/lib/playback/service.server.ts:169–173`; `src/lib/core/lists/sequence.server.ts:104–117`.

Album queues materialize up to 10,000 members, assessment inputs and progress rows; saved queues expand and sort then `LIMIT 10000`, without an overflow flag or next page. An album/list containing more than the cap returns an apparently complete shorter queue. Party queues separately reject above 200; keep that explicit contract. Screen playback with a sequence calls `sequenceEntries(...).find(...)` and transfers the complete recursive sequence to validate and obtain one selected entry. This shares its canonical sequence-query cause with DATA-02 in [data-api.md](data-api.md); consolidate the fix and count the preparation path as another consumer, rather than counting two independent sequence defects. It has an optional selected-entry filter for playlist roots but the playback caller does not use it, and collection entry identity must retain its hierarchical occurrence semantics.

**Smallest option:** read cap+one and return an explicit overflow/retryable limit result for music, or add bounded continuation preserving exact occurrence IDs. Resolve the requested screen sequence occurrence using the shared sequence definition and a bounded result; do not replace it with title-only membership. **Alternative:** queue cursor/session owner instead of complete browser queue; changes controls/reorder/resume semantics and needs a deliberate design.

**Acceptance:** actual largest current queues/sequences for the baseline; separate controlled boundary checks at cap−one/cap/cap+one. Preserve duplicate recordings, playlist occurrences, ordering, dropped/watched/rewatch semantics and exact continuation. A silent prefix cannot pass correctness even if it returns quickly.

### PR-12 — Hidden/withdrawn hero trailers retain one media source and sampler

**Priority P3 lifecycle/policy decision; source-confirmed finite retention.** `src/routes/+layout.svelte:135`; `src/lib/ui/heroes/presentation.svelte.ts:118–126,174–186`; `playback.svelte.ts:26–55`; `src/lib/playback/observe-crop.ts:16–21,37–41`.

The root video owner remains mounted. Hiding/removing a content hero or withdrawing playback/screen capability sets visibility false. The source effect only depends on URL/id/element, so it keeps the old `src`, media buffer and crop observer until a new URL replaces it or the root unmounts. The visibility effect pauses playback correctly, and the sampler skips pixel work while hidden/disabled but schedules a one-second wakeup. This retains **one** old resource set, not an accumulating leak. It may help quick return to the same hero; it conflicts with the performance guide's stronger feature-Off owner-removal requirement.

**Smallest option:** terminate source/sampler ownership on feature withdrawal and when no hero claims the surface, retaining only a URL identity for future reattachment. **Optional policy:** keep a paused source briefly for ordinary offscreen return; use an explicit finite lifetime and measure actual network/buffer benefit. Do not add another global trailer cache/scheduler.

**Acceptance:** actual trailer playing → scroll away → no-hero route → modal → feature off → browser hidden → reopen. Capture currentSrc, optional fetches, timer ownership and renderer memory; feature off/no consumer must have the chosen zero-owner behavior, while intended audio/video playback remains unaffected.

### PR-13 — Image decode admission is after the expensive decoder allocation

**Priority P3 acceptance gap; source-confirmed placement, actual failure unmeasured.** `src/lib/reading/reader/comic.ts:44–57`; `pdf.ts:9,21–27`.

Comic input and output byte caps are enforced, but the `naturalWidth * naturalHeight` cap is checked only after `image.decode()` has allocated decoded pixels. Up to a 32 MiB compressed page can describe far more pixels; the post-decode guard cannot itself guarantee a peak decode budget. PDF.js has `maxImageSize`, caps output scale/DPR and retains one page, but complex PDF operator lists/fonts/images still require actual-file CPU/external-memory acceptance. No claim is made that an ordinary current file exceeds these budgets.

**Options:** perform bounded image-header dimension inspection before decode, then keep the existing post-decode check; or use a decoder API with explicit allocation/resizing limits after verifying animation/orientation/codec correctness. Keep worker/image ownership cleanup on failure. This is separate from compressed archive expansion limits.

**Acceptance:** approved actual large/scanned/compressed images and PDFs; capture decoded dimensions, first-page CPU/long tasks, peak memory, failure recovery and close/reopen plateau. Add small authored edge fixtures as supplementary boundary tests, not as the real-world memory baseline.

### PR-14 — Session/history growth and late-page cost need an explicit long-term budget

**Priority P3 capacity/maintenance issue; intentional retention, not a present leak.** `src/lib/server/storage/retention.server.ts:4,14–22`; `src/lib/server/db/schema.ts:807–853,1100–1118,1140–1152`; `src/lib/music/history.server.ts:14–30`; `src/lib/reading/query.server.ts:141–148`.

Playback evidence/history is deliberately retained. Reading transient cleanup preserves the newest bookmark per user/work/edition/format and removes only superseded older expired sessions. New file editions therefore accumulate retained resume records by design. Music history returns a bounded 60-row page, but uses exact count and offset with only a `(user_id,track_id)` listen index; late offsets/history per album may sort/skip many retained events. Reading history already has its user/work/time/id index. Playback session user-active maintenance queries have no general user/state/expiry index in the schema snapshot (shared cleanup/history indexes are present).

**Smallest option:** record actual table/index cardinality and query plans for active-session updates, most-used history pages and late pages; add only indexes justified by those plans, including write overhead. **Next option:** exact keyset history pagination with explicit totals policy. **Product option:** configurable archival/retention for evidence distinct from progress/listen history. This report does not approve deleting history, compressing away resume editions, or changing licensing/distribution.

**Acceptance:** actual-data plans/buffers and current storage growth; same queries on a faithful clone at measured growth milestones. Preserve complete event identities/order and newest bookmark selection. Index changes need measured update/WAL overhead; retention changes require an explicit user-facing data contract.

## Canonical fix owners and every-consumer rollout

The user's requirement is to repair the shared mechanism everywhere it applies. Each item below names one common owner and its consumers; the plan does not authorize a second private timer, cache, transport, renderer or persistence pipeline. Narrow feature adapters may retain the behavior they own. Cross-consumer acceptance is required even when the reproduced failure first appeared in one medium.

| Finding | Canonical owner to change or extend | All applicable consumers in this scope | Cross-consumer acceptance gate |

## Verification plan and drift controls

1. **Stabilize ownership first:** PR-01, PR-02, PR-03 and PR-04. These have direct cause/effect and small shared-owner repairs. Add runtime behavior tests at the owner seam; source-string assertions alone cannot prove disposal. Keep actual browser acceptance separate from unit test counts.

Use query/row/WAL/bytes counts as well as elapsed time. No recording of credentials, raw paths/titles or source capabilities in report artifacts.
3. **Select the workload improvements:** PR-05/06/07/08 based on actual incidence and resource curves. Preserve existing UI and feature boundaries.
