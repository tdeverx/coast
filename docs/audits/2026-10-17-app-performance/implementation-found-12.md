## One forward repair at the shared database owners

Migration0064 changes three existing owners, without changing table columns, indexes, dependencies, routes, presentation or provider operations:

- `archive_connection_account` returns immediately when its owning user has already been deleted. A reconnect archive has no surviving owner in that cascade. Ordinary disconnects still execute the original archive statement.
- `social_project_activity` skips per-event deletion for a row with a `user_id` whose user is already deleted. The existing user→activity FK cascade removes all that user's activity. Other deletion and insert/update branches retain their existing behavior; sources without that field keep their existing path.
- Activity-reaction cleanup consumes the statement's deleted activity IDs once through an OLD transition table. It replaces one cleanup statement per deleted activity with one set cleanup. The existing activity source and content-revision owners remain responsible for their contracts.

The guards apply to every caller and provider using these owners, including raw account deletion and the admin command. The statement cleanup applies to all activity media. This avoids route-specific patches and avoids a custom account-deletion FK walker. It does not change recorded migrations0020/0023/0039 or rewrite their history. The generated0064schema snapshot is identical to0063except its snapshot IDs; the journal only gains0064. The original approved toast manifest stays immutable, with an exact later journal composition recorded for drift checking.
