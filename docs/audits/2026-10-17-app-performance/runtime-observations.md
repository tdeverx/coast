## SETTINGS-NAV-OBS-01 — intermittent Settings initialization error

One normal-dev console exception was captured at 2026-10-17T22:30:12.052Z during the post-batch Tasks/For You journeys: `TypeError: Cannot read properties of undefined (reading 'join')`. The compiled Settings constructor line maps to the initial `prefs.subtitleLanguages.join(', ')`, rather than the later section-change effect. The visible destination continued to render. This is an observed exception, not a diagnosed production cause.

The Settings loader always supplies `defaults.subtitleLanguages`, and configuration parsing validates it as an array. Absent user preferences should inherit that value. Persisted JSON cannot supply an explicit `undefined` override, while a `null` override would produce a different error. The Settings page, its loader and root layout had no implementation edits when this occurred. No data payload was captured at the exception, so the missing constructor input is not established.

A fresh, settled actual signed-in round trip — For You → Admin/Overview → Jobs & schedules → For You — completed with zero new errors after 22:31:20.383Z. Earlier development reconnects are retained separately; neither reconnects nor an application route-data race are proved to be this exception's cause. The whole live run must not be described as clean-console acceptance.

The next targeted check is fast interrupted navigation and overlap with the existing ten-second Jobs invalidation, with stable source and no development writes. At recurrence, capture the route identity, constructor data key names and the Settings response's default-array shape without personal values. Compare a cold production build against development. The installed navigation runtime awaits the root's animation callback, and an admitted invalidation can finish after its polling component leaves; those are hypotheses to examine, not evidence of a framework bug. A fallback empty array would hide the unresolved data mismatch and is not the selected repair.

## ROUTE-NAV-OBS-02 — outgoing route shape during interrupted navigation

The source-frozen signed-in normal development app produced an uncaught `TypeError` reading `length` in Discover at **2026-10-17T23:14:34.294Z**, during Discover → Admin → immediate For You navigation. The destination subsequently rendered. The site maps to `data.trending.length`; the Discover loader always returns that array. This is another actual exception, not a clean-console pass. A connection to SETTINGS-NAV-OBS-01 is plausible but unproved.

Installed SvelteKit 2.70.3 checks its navigation token before awaiting `onNavigate` callbacks, then assigns current state and calls `root.$set` before its next token check. The app's callback waits for a 120ms fade. A source-pinned deterministic harness reproduced stale commits after both a newer navigation token and an intervening invalidation commit. Its negative control rejects a token superseded before entry. This is controlled scheduling evidence from installed source, with no database, page payload or performance benchmark.

The official [upstream report and proposed fix](https://github.com/sveltejs/kit/pull/17302) describes the same stale-navigation/data-prop-omission class. The proposed fix is unmerged, and the reviewed stable 3.1.0 release also retains the token gap; an upgrade alone is not a verified remedy. The exact causal trace for this observed Discover exception has not been captured. Removing the fade wait reduces the window but does not fix the router's remaining microtask window, so it is not accepted as a universal repair.

One native real-data A trial and one B trial with the animation wait removed both completed without an exception. Their callbacks were about 600ms apart, so the intended overlap was not reliably exercised; these trials are inconclusive. Temporary navigation/shape diagnostics in the root layout, Discover and Settings were removed. All three original SHA-256 hashes were restored exactly and the reviewed current source inventory matched again. No UI transition change was retained.

The next decision is a concrete reviewed dependency repair with stale-commit, returned-callback and speculative-fork cleanup acceptance, or an upstream release carrying the complete fix. Any dependency patch remains a proposal until its code, maintenance/removal gate and regression evidence are reviewable and the required complexity approval is given. Search's pending Back acceptance must include the installed router's deliberate skipping of `beforeNavigate` during an active navigation.

## ARTWORK-CACHE-OBS-03 — malformed retained private cache entry

Source review found that `serverArtwork` rejects malformed on-disk bytes and downloads a replacement, while `createImageCache.put` returns early for an already-indexed key. A corrupt existing entry could therefore cause repeated downloads rather than repair. No actual corrupt-file incidence was found, so this is a recovery candidate without a measured user impact. It is separate from PJ-01's cancellation/flight repair.

A repair should use one cache-owned invalidation/replacement contract, preserving active-reader safety, filesystem indexing, byte/entry limits and private access before reads. Verify an actual retained malformed-entry incident if one occurs; a controlled corrupt-file recovery test would be supplementary failure evidence. No retention or replacement policy was silently changed.

The follow-up [shared cache repair](implementation-artwork-cache-recovery.md) is now applied. Both private and TMDB consumers supply their existing synchronous format checkers to the cache read. Rejected bytes and their index entry are removed within the same serialized read before a later replacement can run. Twenty focused tests/115 assertions and 28 controlled checks with copies of actual JPEG/WebP bytes pass. This verifies recovery for bytes the existing checkers reject, not full decode integrity or natural corruption incidence. The latest normal-dev reload displayed 14 private-relay images without a new console warning/error.

## ROUTE-REFRESH-OBS-07 — Tasks polling clears a shallow panel

A source-frozen, signed-in normal-dev trial on 18 October at 00:54:29.533Z showed Friends with three saved people and its close control on the settled Tasks page. At 00:54:51.630Z, spanning the ten-second polling interval, the people and close control were absent while the browser address still contained `?friends=true`; no import error or console exception was recorded. A prior cold reload in the same journey showed the same disappearance and the Friends trigger could not reopen it there. Moving to For You restored normal Friends open/close. All source fingerprints matched the pretrial manifest after the trial. See [the aggregate receipt](evidence/implementation-shared-normal-before-poll-fix.json).

Installed Kit shallow pushState changes history/page.state without assigning page.url; direct invalidation resets page.state by default. The root panel owner uses that state with page.url fallback, while the trigger separately checks window.location. This source mechanism matches the observed split and explains why the trigger can decline to reopen. The exact network/commit trace was not instrumented, so do not claim that causal timing was captured. Jobs polling directly invalidated settings every ten seconds, bypassing the existing state-preserving refresh owner.

The selected routine repair routes in-place refresh callers through the existing shared helper, retaining dependency names and ordinary/full Retry behavior. When an overlay is already open, it uses the existing broader refreshAll path. That can read more route data than a scoped invalidate; functional state preservation is the tradeoff, with no latency/resource saving claimed. Kit still captures the prior shallow state before awaiting its load: opening or closing an overlay during that load remains a separate ownership problem. This repair does not adopt the pending navigation dependency candidate or close OBS01/02. Final source/controlled and normal-dev post-poll evidence belong in the forthcoming owner report.
