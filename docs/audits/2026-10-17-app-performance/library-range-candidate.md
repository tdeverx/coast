## Confirmed problem and proposed ownership

The later [normal causal trace](library-append-trace.md) recorded the same Library owner accumulating 60, 120 and 180 cards. A tracking/social revision change then refreshed current page 3 with `append=false`, replacing 180 cards with 60. The automatic sentinel appended page 4 afterward, giving 120. The earlier uninstrumented [300-to-180 observation](library-append-reset.md) is separate; this later trace does not establish its exact request sequence.

The current [Library owner](../../../src/lib/ui/shelves/library.svelte.ts) defaults to replacement at lines 76–98 and calls a current-page refresh at 103–130. The existing resource correctly owns cancellation and latest-result publication. It cannot preserve a range when the admitted merge explicitly replaces it with one page. [Shelf](../../../src/lib/ui/components/Shelf.svelte) lines 152–158 and 306–317 supply automatic append and numbered-page controls.

The candidate changes only `createLibrarySource` in that existing owner. It remembers the first and last **committed** pages, captures the viewer, query, revision and canonical admission state, rebuilds the committed interval serially, and publishes it atomically. It uses the existing occurrence identity (`entryId`, otherwise href/id), so repeated sequence occurrences retain their identity. A refresh can remove or reorder items according to the new canonical pages; it does not freeze the previous ranking or blindly append new results.

One existing resource and abort lifetime own the rebuild. A revision cancels an in-flight append; a busy sentinel cannot supersede the rebuild. That cancelled append is not silently replayed. Fresh later demand can append. Success, error callbacks and URL publication check the captured scope; a late denied response cannot clear a replacement owner's range. Cancellation fences publication and the owned HTTP wait, not already-admitted server work.

The candidate reuses `surfaceEnabled` and `categoryEnabled` with the same route-data/capability inputs used by the parent. Known viewer withdrawal, relevant surface or selected reading-kind withdrawal, and a current 403/404 clear the old range immediately. Re-enable starts fresh at page 1. A book/comic admission change clears a mixed reading range and reloads canonically instead of filtering an old DTO locally. Equivalent enabled session data and irrelevant category changes remain no-ops; existing preview/isolation semantics remain.

For A, the proposed multi-page failure policy keeps the last **complete** range on a transient network error or partial refresh, shows the existing scoped error, and retries the full interval. Current terminal 403/404 and known owner/admission withdrawal clear instead. Single-page partial usability remains as before. This policy needs a conscious decision: retained stale content during an unseen server revocation cannot be made linearizable by a client fence.

Frequent revisions can repeatedly cancel/restart a long interval and delay or starve completion. The candidate adds no request deadline, retained-page limit or cross-shelf budget. Atomic refresh keeps both old and accumulating new page objects, metadata, arrays and identity map, an additional **transient O(N)** retention cost; the precise heap/RSS/GC cost is unmeasured. DTO JSON byte sizes are serialization sizes, not heap or network measurements. Canonical deletion/reordering can move or remove the visible anchor; this patch adds no custom scroll restoration and promises no retained scroll position in that case.

Only the current row and embedded-grid append UX is targeted. Ordinary full-route grids use numbered pagination, and [the Library page key](../../../src/routes/library/+page.svelte) line 32 includes page/filter data. Parent remounts therefore remain resets; the proposal does not promise retained range through a remount or a hypothetical direct full-route append. It does not change Progress, Credits, Discovery, For You, Lists or cursor Social owners, which have separate contracts.

Before adopting A as accepted behavior, root must verify normal actual-data retained prefix across natural refresh, automatic sentinel versus manual button, close/reopen, filter/numbered navigation, keyboard/focus/menu/draft behavior and visible scroll. Natural privacy/feature withdrawal, ranking/deletion and provider partial/error coverage remain gaps beyond the supplementary schedules. No 20-page, long-running memory, retained-DOM bound, ordinary Listen provider, HTTP/authentication or production repair acceptance is transferred from the private replay. The retained-range client/API repair remains unadopted while the selected server-range option is prepared. The independent one-page query repair is recorded separately.
