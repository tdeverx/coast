# Independent second pass: shared UI demand and lifetime

17 October 2026, source `eb0673873462b71118d1c11678d128958a05ff07`. This is a second source review of shared resources, Shelf/source adapters, cards and menu/dialog owners, artwork observers, clocks, material actions, notifications and background polling. No UI/application changes or new synthetic workloads were made. The coordinator owns actual-data browser/build evidence; all candidates below are source-confirmed work/lifetime shapes with **unmeasured present browser cost**, except where the consolidated report attaches actual observations. User-requested preservation of the approved UI applies to every option.

## Residual findings and opportunities

### UIS-01 — P3 confirmed unbounded session metadata: toast suppression remembers every historical ID

`src/lib/ui/components/NotificationToasts.svelte:18-21,42-50,58-60`. `hidden` is an append-only reactive array; `observed` is a Set with no pruning while the long-lived layout component remains mounted. Timer cleanup is correct, and at most three toasts render, but neither bound limits IDs retained across a long session. Every supplied notification checks `hidden.includes`, whose cost grows with accumulated historical IDs. This is small metadata, not evidence of an OOM. Actual database notification row counts (estimated27 deployed/519 development) are not JS retention measurements and cannot establish this array's current size.

Option: scope suppression state to a finite current window and/or expiry, using timestamp/created-at rules that do not cause a dismissed normal toast to reappear when the supplied window shifts. A Set provides constant lookup but is not sufficient without a lifetime bound. Persistent dismissal remains a durable server mutation; failed writes must remain retryable. Acceptance: many successive real notification windows, removed/reappearing IDs, normal expiry, persistent failure, logout/viewer replacement and component teardown; retained state must plateau. This can be tested through behavior without changing visual design.

Related small lifetime: `NotificationInbox.svelte:29,43` retains `seenAt` for every seen notification while mounted. Reading writes are correctly observer-driven, grouped and fenced against disposal. A shared finite notification visibility owner could clean both local histories if it remains simpler than two bounded maps.

### UIS-02 — P3 optional network work: browser diagnostics poll in hidden tabs and permit overlap

`src/lib/ui/diagnostics.ts:53-69`. Diagnostics settings refresh immediately and every30seconds with raw fetch, without visibility guard, pending-request guard, timeout or an AbortController. Uninstall clears future ticks/listeners but does not cancel an in-flight request. A permanently slow endpoint can accumulate requests and late `receiveDiagnosticLevel` calls. A hidden tab continues optional network demand subject only to browser throttling. Normal fast requests are tiny; present backend cost/frequency requires the coordinator's actual traces.

Option: one request at a time, visible-tab policy with immediate refresh on visibility resume, and abort on uninstall. A long foreground diagnostics policy fetch may be independently time-limited. Keep the useful50-events/minute reporting cap and keepalive semantics for genuine unload/error reporting; those have different ownership than settings polling. Acceptance: hidden/resume, delayed endpoint beyond more than one cadence, stop while pending, new installation replacing old and continued error reporting. Reuse existing resource/request ownership, not another timer framework.

### UIS-03 — P2 at long browse sessions, source-scale candidate: append retains all loaded items and card owners

`src/lib/ui/shelves/library.svelte.ts:95-98`, `credits.svelte.ts:64-70`, `detail.svelte.ts:23-25`, `social.svelte.ts:35-36`, `for-you.svelte.ts:39`, `journal.svelte.ts:53`; rendering `components/Shelf.svelte:132-133,209-238`. Several row/embedded-detail/cursor paths deduplicate and append to all previous items without a sliding retention/render window. Every retained entry stays in the keyed DOM. Server60-card pages bound each request, not total client DOM after many pages. `uniqueItems` constructs another combined array and Map each append, so cumulative copy/dedup work grows with loaded history. Finite source result pages make the theoretical endpoint finite, but it may still be the full actual catalogue/history.

This is **not** a finding that initial60-card pages are unbounded. Rows with explicit20-item slicing and ordinary replacing page navigation are distinct healthy paths. Current jank/RSS after real multi-page browsing is not measured in this report.

Recommended ownership: keep one retained-page/card-window policy in the canonical Shelf/source pagination mechanism and let source adapters supply domain identity/cursors. Retain existing navigation/selection semantics while windowing offscreen row cards and preserving stable scroll anchors, or adopt an explicit retained-page budget with supported backward reloading. A Library-only or music-only truncation is not the recommended fix. A simpler explicit page control may be appropriate where the approved UX already has pagination; do not redesign by assumption. Bidirectional episode anchors and journal event occurrences require exact identity/position recovery, so a generic truncate-to60 array would be incorrect. Test actual catalogue browse for1/5/20 loaded pages, return/back navigation, keyboard/menu focus, content revisions, selected detail, social badges, and exact item order. Count DOM/component/observer/decoded-image growth and post-close plateau in the real browser.

### UIS-04 — P3 cumulative activation and offscreen work: card/shelf demand is latched after first contact

`MediaCard.svelte:87,182-187,244,268` latches `active=true` on first hover/focus/action and never resets until the card unmounts. This demand-loads WorkMenu only after interaction, which is good. It also retains that menu's component/controller state and native glass eligibility for every touched card. `liquidGlass` has a ResizeObserver/setting subscription per mounted action; closed menus correctly remove expensive global position listeners, but each menu controller still owns a matchMedia listener until destruction. UIS-03 determines the size of this retained cohort.

At row level `Shelf.svelte:98,124-128,201` latches `socialActive` at first intersection; source refreshes then use `resource.activated || ready` after scoped revision changes (`library.svelte.ts:121-131`, `discovery.svelte.ts:143-156`, `social.svelte.ts:44-50`). Previously seen offscreen rows can fetch optional badges/content again while another visible area is being used. `lazyContent` intentionally disconnects after first activation and does not represent current visibility. This follows the present row lifecycle, not a proven bug that hidden DOM must always unmount.

Options: first measure actual revision-driven offscreen requests and retained menu/material ownership. If meaningful, expose a current-visibility signal through the existing `lazyContent`/Shelf source contract and defer optional refreshes until a dirty row is visible again across every source adapter; retain permission withdrawal immediately, stable snapshots, explicit manual reload and active-menu/playback ownership. For cards, keep transient hover/focus/material visibility distinct from an actively open menu, without closing a menu when its trigger loses pointer hover. Preserve keyboard/touch and menu drafts. Do not create per-card global listeners or tear down essential audio/party work. Tests must include unseen→visible→offscreen→revision→visible, open-menu offscreen, permission/generation changes and disposal.

### UIS-05 — P3 renderer import opportunity: empty compact charts still request an engine

`ui/charts/ChartView.svelte:15-25,30-35`. Rendering has an empty compact-chart branch, but the loadError effect unconditionally evaluates `loaded`, whose derived calls `renderer(model.styleId)`. The dynamic renderer import therefore starts even for a compact empty state that never renders it. Standard/extended engines are split and promises reused per component; this is an avoidable initial-demand edge, not a bundle-size or actual network measurement. Browser module cache means later occurrences do not each retransmit the same engine.

Option: make renderer demand conditional on the branch needing a chart, while retaining error reporting/retry behavior for nonempty charts and later empty→nonempty updates. Verify actual entry import/network traces with an actual empty-insights path. Coordinator owns chart coverage and may deduplicate this into its chart findings.

### UIS-06 — P3 material CPU/GPU candidate: scheduling is shared, but native SVG still rebuilds and has no pixel budget

`ui/materials/glass.ts:60-105,241-249,319-344`. The last displacement-map key avoids recalculating the canvas when width/height/padding/radius/depth are unchanged. However a scheduled render with unchanged effective settings still removes and rebuilds the complete SVG filter definition. New dimensions calculate every pixel synchronously on the main thread and encode a PNG data URL; there is no explicit maximum pixel count. Shared rAF admission coalesces callbacks, but does not impose a work budget per frame across many surfaces. Distinct same-size surfaces do not share their displacement map.

This is conditional on supported Blink, enabled native optical glass, positive refraction, actual dimensions and component demand. Many surfaces explicitly use the CSS renderer, unsupported engines fall back, and the approved visual design must be retained. No source-only inference establishes actual frame drops or GPU usage. First profile real resize/panel/long-browse interactions with default settings and compare the existing user preference toggled; do not build another material implementation without that evidence.

Options in increasing complexity: no-op unchanged effective render key; release unneeded cached map when enhancement is disabled; establish a justified max-resolution policy; share bounded identical maps if repeated size distributions warrant it; worker/offscreen-canvas only if measured large-map compute justifies the architecture. Blur/backdrop fill cost itself needs real rendering traces. Disposal already removes watchers and defs with a short deferred-removal workaround; preserve its intended engine behavior.

### UIS-07 — P2 conditional decode candidate: avatar compressed-byte bound does not bound decode memory/lifetime

`components/AvatarPicker.svelte:17,25-37,71-73`. Upload admission caps files at5MiB and supported MIME. It decodes a full `Image` before resizing to256²; compressed-byte limits do not constrain decoded pixel area. Superseding/removing an avatar increments version and aborts provider/FileReader work, but the temporary decode image/object URL is local to `prepareAvatar` and is only released after decode settles in `finally`. This correctly releases on success/rejection, and publication is generation-guarded, but pending decode does not stop immediately when ownership ends.

This is an acceptance/resource candidate, not a reproduced real-image spike. The existing lifecycle test covers late decode completion and URL revocation; actual large-image/animated-GIF pixel behavior remains a separate requirement. Option: an explicit bounded image-decode owner with immediate cancellation/release and a justified dimension/animated-frame policy, while preserving GIF behavior. Avoid claiming createImageBitmap resizing automatically eliminates full decoder allocation without measuring the browser implementation. Verify with authorized real sample images and browser heap/external/process memory, not arbitrary fake image timings.

## Actual-data acceptance sequence

Use the existing deployed/development datasets, identify exact build and enabled medium/experiment settings, and keep unloaded media as explicit gaps. For each relevant real route: record cold/warm requests and bytes, open/use/close/reopen,1/5/20 actual pages, scroll/resize, hidden/resume, a real revision/permission change and returning navigation. Capture DOM nodes, observers/listeners when tooling exposes them, JS heap plus process/external memory, request counts and frame/long-task traces. Avoid conflating server RSS, decoded browser images and PostgreSQL buffers.

Prioritize UIS-01/UIS-02's small simple lifetime ownership first if accepted. Rank UIS-03/UIS-04/UIS-06 by actual cumulative browsing/resize traces before a larger retention/virtualization/material rewrite. Preserve exact order, occurrence identity, focus, approved layout and existing per-medium behavior. Add operation/lifetime assertions for each accepted behavior rather than source-string tests or machine-specific millisecond thresholds.
