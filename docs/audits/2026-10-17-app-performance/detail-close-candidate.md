# Shared detail close — small candidate and verified observation protocol

The two-line shared candidate completes **15 repair/positive controls** and **two characterizations of an existing unresolved recovery gap**. It removes the observed duplicate terminal close and fences disposed callbacks in these controlled schedules. This report does not apply source, establish normal incident causation or certify actual-media performance. Maintained tests, common gates and signed-in normal acceptance remain adoption steps.

The [complete operation-specific CUA receipt](evidence/detail-close-candidate-operation-cua.json), [exact entry](candidates/detail-close-candidate-operation/serve.ts), [plan](candidates/detail-close-candidate-operation/verification-plan.json), [candidate patch](candidates/detail-close-candidate-operation/single-authority.patch), source snapshots and proposed maintained tests are retained. Independent source reviews checked the small repair and the corrected protocol. The [baseline](detail-close-baseline.md) remains separate evidence.

## Smallest shared repair

DetailPanel grants the overlay its native close callback only while a resolved presenter exists. Clearing the presenter withdraws that callback; the existing manual error path still cleans up a terminal/initial failure. Ordinary user Close retains its callback while data is resolved. All screen, reading, music, game, person and row presenters share this owner.

Dialog.closed first returns if the component is already destroyed, reusing its existing disposal flag. A late callback cannot restore focus, publish bindable state, reclaim feedback or invoke a successor's history path. Every Dialog consumer benefits. No close-attempt registry, key remount, compatibility shim, timer, dependency or visual change is introduced. Native-open guarding and existing animations remain.

## Completed controls and explicit gaps

The positive controls cover visible terminal failure with exactly one manual request; initial failure without native presentation; ordinary native Close, connected-opener focus and actual history arrival; generic same-target and nested-target errors; viewer replacement; disposed-owner pending reopen followed by a legitimate fresh Close; hidden player and reader reopen; a fresh presentation before a real queued old close task; late close after arrival; same-href/new-account pending reopen; Forward plus a fresh Close; and successful nested Back retaining the same native dialog while old Activity is inert and fresh overview loads.

Unheld close checks identify their exact native event, observe target phase after the production callback, and wait a later posted task. Held native delivery stops at the disclosed capture seam and is replayed as an explicitly synthetic event, followed by dispatch return and a posted task. Real browser history/popstate is used only when a held navigation request is deliberately released. Requests are not automatically actual traversals.

The two negative characterizations confirm a **retained hidden-terminal recovery gap**. A successful presenter is hidden behind player or reader; a terminal403 then clears it while the existing close function suppresses history. Unhide leaves the same unresolved trail, and reopening the same href does not trigger a new load. Zero history requests is not a recovery pass. This remains open as PANEL-HIDDEN-ERROR-OBS-11 and is not repaired by these two lines. No actual normal403 was manufactured to claim live acceptance.

Already-issued history traversals, repeated user clicks, installed Kit refresh state races and the mixed signed-in filtered Back incident remain outside this repair's proven scope. A target observer cannot establish that a listener survived disposal; the ordinary positive control proves live callback delivery, while the separately proposed pure-Bun test isolates a retained disposed callback.

## Environment, cleanup and actual-data boundary

The fixture compiles exact shared production owners with the two candidate source substitutions. API outcomes, identities, child presenters and root/auth/history I/O seams are authored; materials/icons/feedback side effects are inert. It is a static GET-only loopback server with DATABASE_URL rejected and browser fetch/preconnect denied. It uses no normal account, provider, database, cookie or key. CUA operates visible controls and reads rendered results; no browser app-state injection or network interception is used. Installed Kit routing is not substituted into the fixture or claimed tested here.

All29 current source/runtime/test pins match before and after the final run, and all17 declared controls complete without captured warnings/errors. The [successful Back screenshot (private verification image)](publication.md#private-verification-images) and both stopped-run screenshots were visually inspected; bare fixture styling proves no approved app appearance or geometry. Each run was reset idle with no dialog, its tab closed, and only its exact owned server terminated; exit143 and listener release were checked. The normal dev app was retained. The second preparation's sandbox socket/ps failures and successful permission-context checks are preserved rather than presented as app failures.

Actual signed-in details, expansion/reverse scroll, Back/Close/focus, inbox and Tasks must be checked separately after source adoption. Authored terminal/error/disposal controls supplement that acceptance and do not replace the requested actual catalogue verification.
