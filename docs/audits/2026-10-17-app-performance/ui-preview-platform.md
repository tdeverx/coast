# UI previews, charts, benchmarks and runtime platform: final gap sweep

Baseline: `eb0673873462b71118d1c11678d128958a05ff07`, reviewed on 2026-10-17. This appendix completes the source sweep of `src/routes/ui-preview/**`, `src/lib/ui/charts/**`, `src/lib/benchmarks/**`, `src/lib/server/diagnostics/**`, `scripts/**`, Docker/Compose and build configuration. It adds no application changes and runs no new benchmark or synthetic workload. File-by-file scope, SHA-256 and review depth are in `ui-preview-platform-coverage.json`; decisions are in `ui-preview-platform-findings.json`.

These areas have distinct purposes. Previews use fictional fixtures and cannot establish real-data performance. Benchmarks execute a few real read queries plus an explicitly synthetic journal probe, and cannot establish provider/network/browser performance. Offline browser fixtures and recovery/container drills protect particular contracts; their existence does not mean they were executed in this audit. Actual browser, build, query and process observations belong to the parent evidence set. This appendix reports source-confirmed bounds and risks, with outstanding acceptance stated explicitly.

## UPP-01 — shared chart model has no work/mark admission contract

**P2 acceptance gap before broader live adoption; high confidence in source shape, no measured real-user stall.** `src/lib/ui/charts/extended-geometry.ts:8-25,90-114,121-170` accepts generic arrays/counts with no family cardinality or generated-mark budget. Packed bubbles generate O(i²) candidate locations for insertion i and test candidates against existing circles/recompute bounds, giving a conservative O(N⁴) worst-case time bound and O(N²) temporary candidates. That is an algorithmic bound, not a measured growth curve. Isotype allocation depends on `ceil(max(value,capacity)/unit)`, so a single large numeric value can generate many marks even with few rows. Treemap recursion can become skewed and repeatedly allocate/slice arrays. Flow layout assumes a small DAG in its own comment, but the generic model does not enforce that assumption. A cycle can keep increasing columns through the bounded relaxation passes and cause excessive empty-stage allocation. `insights.ts:7` and several geometry maximums use argument spreading, which is unsuitable for arbitrarily large future inputs.

The finite fictional gallery is not evidence that these algorithms are slow on its current inputs. Live `insights.ts` adapters currently produce 2A/2B, 3A and 11A, so an app-wide production packed-bubble slowdown would be an unsupported claim. The missing contract becomes consequential when experiments are connected to real, unbounded datasets.

**Canonical owner and all consumers:** define supported shape, numeric-domain, aggregation and generated-mark policies with `ChartModel`/the shared chart adapters and geometry entry points. Apply them to `ChartView`, `StandardChart`, `ExtendedChart`, `ChartMark`, the preview normalizer/gallery, `ui/insights/{media,profile,community}`, `DetailCard`, game completion, reading progress, and every subsequent medium/experiment adapter. The source import graph identifies these current callers. A component-private cap would not protect the other chart families.

**Smallest option:** document and validate each family's accepted input/mark budget at the shared boundary and require adapters to supply a truthful aggregate model plus exact paged data when detail exceeds it. Pick budgets from actual data/browser traces, not these fictional fixtures. Reject invalid flow cycles/non-finite dimensions and impossible unit/capacity combinations with a useful controlled result. Do not silently truncate real data or silently change totals. **Alternatives:** select the existing linear arrangement for large bubble cohorts; add a spatial index/front-chain packer only if exact packing and measured demand justify the complexity; move expensive geometry to cancellable work only if measured main-thread cost remains after aggregation. New architecture requires the user's complexity decision at implementation.

**Acceptance:** use the real deployed/development distributions and their exact totals, test all enabled media/experiments, preserve labels/order/selection and table completeness, and measure marks, geometry time, long tasks and retained heap on both comfortable and dense actual cohorts. Include malformed semantic input tests at the shared boundary. No new fake workload was run here; real adoption/scale acceptance remains open.

## UPP-02 — arbitrary preview imports can bypass the otherwise finite fixture bounds

**P3 local-workbench resource admission opportunity; source confirmed, magnitude unknown.** `src/routes/ui-preview/props.ts:85-91` parses arbitrary JSON and checks only its top container/nullability. `ComponentPlayground.svelte:40-46` can serialize entire custom props/configurations and callback arguments; the eight-event retention limit does not limit bytes in one event. `+page.svelte:20-26` checks an imported background's MIME family but neither compressed bytes nor decoded pixels. Old background object URLs are correctly revoked on replacement and teardown. These are explicit admin-supplied local inputs; there is no evidence of an automatic leak during ordinary catalogue browsing.

**Canonical owner and all consumers:** share preview-data admission/diagnostic formatting across `PropEditor`, `ComponentPlayground`, `ComponentSpecimen`, selected `PreviewExample` families and background import. Reuse the app's shared image/decode ownership proposed in UIS-07 for background, avatar and any future local image picker; do not copy an avatar-only byte check. Chart work/mark contracts belong to UPP-01 rather than a second preview-only renderer.

**Smallest option:** make permitted custom-input size explicit, report over-budget inputs before parsing/rendering, bound serialized event previews with an indication of omitted bytes, and adopt shared decoded-pixel/image cancellation policy. Preserve exact copied configuration when the input is accepted. **Alternatives:** allow a clearly selected large-data inspection mode with a stated cost, or parse/inspect off the main thread if actual workflow needs it. Avoid silently shortening fixtures or redesigning the approved editor.

**Acceptance:** ordinary saved configurations remain lossless and editable; all local object URLs/decode owners release on replace/close/error; using actual user image files/configurations establishes whether any limit is warranted. No large synthetic image/JSON test was run; this is a boundary hardening option, not a measured source of current app instability.

## UPP-03 — bounded diagnostic storage still repeats filesystem and parsing work

**P3 source-confirmed efficiency opportunity; actual cost unmeasured.** `src/lib/server/diagnostics/index.ts:85-107` serializes each enabled event through recursive mkdir, chmod, current-segment stat and append, in addition to periodic pruning. `recent():115-148` forces prune and reads/parses/filters/sorts up to four MiB before returning the current event set. Frequent viewer refreshes repeat that bounded work. The 128-write cap/drop metrics, finite rotation, best-effort failure behavior, separate runtime sample store and minute sampler already prevent unbounded memory/disk growth. This finding does not claim that one log write causes a visible stall.

**Canonical owner and all consumers:** `DiagnosticStore` is the common persistence owner for both diagnostic events and runtime samples. It serves hook/API errors, provider fetches, queue jobs, maintenance, music import/query failures, Collection timings, playback/share lifecycle, public API errors, and the diagnostics endpoint/viewer. Optimize this owner rather than adding independent provider/job/UI caches.

**Smallest option:** after tracing actual event rates, initialize/check private directory permissions once per valid directory lifetime and track current segment bytes with correct recovery on missing/rotated/error paths. Preserve external-file-change behavior or explicitly document ownership before removing stat calls. **Alternatives:** batch bounded appends within a short flush window if write rate warrants it; add a revision/seek-based finite diagnostic tail response if real repeated viewer reads dominate. Batching trades crash-tail durability for fewer I/O calls; preserve best-effort semantics and never let diagnostics hold application success hostage. Do not add a database logger without evidence.

**Acceptance:** compare actual normal/trace-level provider+queue sessions and repeated real viewer reads for I/O counts, CPU, pending/drops, filesystem failure handling, permissions and retained bytes. Preserve segment order/rotation, seven-day pruning, safe fields, runtime-history isolation and useful failures after overflow. No additional diagnostic flood or disk microbenchmark was run in this sweep. UIS-02 separately covers hidden/overlapping browser settings polling.

## UPP-04 — recovery drill drains two child pipes sequentially

**P3 tooling stability candidate; source confirmed, noisy-child deadlock not reproduced.** `scripts/test-recovery.ts:15` awaits stdout to EOF before draining stderr, although both are configured as pipes. A child that fills stderr while stdout remains open can block waiting for pipe capacity while the parent waits for stdout EOF. In that state the `finally` cleanup cannot start. Ordinary pg_dump/restore and migration output may never approach this condition; no claim is made that the completed drill hung. The sibling `scripts/fixtures/container-runtime.ts:28-30,108` already concurrently drains both streams and exit with `Promise.all`.

**Canonical owner and all consumers:** a narrow offline child-command collection contract should govern recovery, container fixture command collection and any future script that captures both pipes. Audit other spawn sites for this exact pattern; do not replace streaming production stderr supervision with whole-output collection. `performance-verification.ts` captures git stdout with stderr configured as a pipe, so it should choose inherited/bounded concurrently drained stderr under the same contract if that historical tool is maintained.

**Smallest option:** concurrently drain stdout/stderr/exit, preserve return/output/error redaction, add bounded captured bytes and a finite process deadline with owned-child cleanup. Reuse the established concurrent pattern rather than adding a process framework/dependency. **Alternative:** inherit stderr where the script does not need it for a redacted failure message. **Acceptance:** a deterministic dual-pipe contract check plus an actual backup/restore drill should prove no stall, correct nonzero status/redaction, timeout cleanup and disposable DB/key cleanup. This was a read-only source review; no new child flood or database drill ran here.

## Platform acceptance and drift controls

The Docker runtime installs PostgreSQL from Debian Bookworm, and `scripts/fixtures/container-runtime.ts:4` explicitly targets PostgreSQL 15. The isolated PostgreSQL 17.11 suite used by the parent is evidence for that tested engine, not proof that the exact bundled image, process signals, storage permissions, image health check and shutdown paths passed. Record the tested image digest/OS/architecture/PostgreSQL/Bun when running the existing guarded container tests. Do not infer a new runtime bug merely from the version difference. `test-recovery.ts:34` prints a PostgreSQL-17 success label without querying a server version; tie future drill output to the actual queried version so the evidence is accurate on another local toolchain.

Keep production and fictional input boundaries machine-checkable through existing code/UI inventory check modes. Add checks only for meaningful ownership contracts: production chart adapters must not import preview fixtures; every new chart family must declare semantic/mark budgets and actual-data acceptance; imported-file controls must use the shared decoder owner; log sinks retain finite bounds; two-pipe script collectors drain concurrently; benchmark workload/version/fingerprint changes invalidate comparisons. Source-style's explicit file list is not a claim of whole-repository formatting coverage.

Retain current real-data snapshots and browser/query evidence as acceptance baselines. For each implemented workstream, record exact build, engine, dataset identity without credentials, enabled features, cold/warm conditions, visibility, request/SQL counts, returned rows/marks, wall/CPU/heap/RSS, provider wait versus service time, and success/error/cancellation behavior. Sampled resource counters and small calibration p95s supplement that evidence; they cannot replace end-to-end actual flows. No chart/preview performance assertion in this appendix is verified solely by fictional fixtures.
