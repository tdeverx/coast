# Profile and onboarding request lifetimes

FRT-03's profile GET and onboarding wait ownership fixes are implemented. The existing shared resource now owns both independent profile read lanes and the onboarding device-poll wait. UI markup, profile preference POST order and server action semantics are preserved. This does not complete the separate preference-write queue policy opportunity in the baseline finding.

## Changes and ownership

| Consumer | Canonical owner / change | Required behavior retained |
| --- | --- | --- |
| Profile favourites: all kinds, availability filters and pagination | `src/routes/profile/[username]/+page.svelte:51,98` uses `createResource` and passes its signal to the existing API client | Current kind/scope/page/username; reading kinds force scope all; overview 20-card and full-page 60-card caps; independent favourites loading/error |
| Profile insights: month/year/all | Same component `:73,116`, separate resource | Independent period lane, totals and activity; one selection does not cancel the other lane |
| SSR data refresh and route teardown | Same component `:77,86` replaces both resources on incoming data and disposes both on destroy | Incoming SSR data remains authoritative; superseded or disposed delivery cannot publish stale content/error or clear a later request's busy state |
| Onboarding Trakt device action wait | `src/routes/onboarding/+page.svelte:12` uses the same resource owner; signals the POST, checks abort before body read and deserialize, checks owner/device identity before publication | At most one poll/refresh tick; existing two-second clock and provider interval; device polling continues while hidden because authorization uses another tab; current error messages |
| Onboarding import-status refresh | Same component `:29,32` skips hidden refresh admission, resumes promptly when visible | Server-owned import orchestration and navigation remain unchanged; timer/listener and the device wait are disposed on unmount |

The canonical owner remains `src/lib/ui/resource.svelte.ts`; no new request framework or dependency was added. The profile replacement effect reads incoming `data.filters.kind` when disabling reading availability, avoiding a local selection becoming an accidental dependency that cancels its own read. Other existing polling owners such as `ConnectionCard.svelte:64–100` and `BenchmarkSettings.svelte:14,45` retain their own cadence and existing lifecycle behavior.

Profile requests still await the existing serialized `savePreference` chain (`+page.svelte:78–84`). Cancelling a GET does not cancel or discard an already requested preference write. Onboarding `?/poll` calls a server flow that may update credentials, polling deadlines and connections (`src/lib/providers/trakt/connection.server.ts:113–139`); client abort ends this page's wait and cannot promise to undo a committed action. Likewise, SvelteKit `invalidate()` exposes no signal: the new guard prevents admission/follow-up after teardown, while an already admitted invalidation may finish.

## Remaining options and acceptance gaps

1. **Preference queue policy remains open.** Current behavior preserves every requested write in order, including after unmount. A bounded owner could retain one active write plus the latest unsent absolute values for each preference, but that coalesces intermediate writes and must preserve acknowledgement/failure feedback and auth ownership. A larger option is one canonical preference command coordinator shared with all settings clients. Neither was silently selected in this patch. Test held writes, latest final persisted values, failed acknowledgements, account change and post-teardown behavior against actual settings before changing this contract.
2. **A new device code can wait for an older hung poll.** The new identity fence prevents an old code's response from publishing into the new code, but existing `pending` still waits for that old request to settle. A code-scoped poll resource/epoch could cancel its old wait and admit the replacement immediately while retaining one poll per current code. This needs a dedicated lifetime test and actual provider/account-generation acceptance; no active real cohort exists in the current clone. This is a pre-existing boundary, not a new regression.
3. **Admitted backend work is not cancelled by this client patch.** Profile SQL receives no new database cancellation signal. Kit invalidation and device server action commit semantics remain as above. More aggressive SQL/action cancellation requires a shared transaction/transport policy rather than pretending that a client abort rolls back server work.
4. **Rendered normal-dev scope remains limited.** The current signed-in trial below verified the profile overview and favourites panel open/close. Filters, paging, independent busy/error states and natural cancellation schedules still need rendered acceptance. Active real onboarding/device flow, hidden-tab authorization and provider expiry cannot be called passed from the completed-setup data or controlled tests. No performance gain in milliseconds or bytes is claimed.
