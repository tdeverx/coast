# Trusted API request error delivery

The exact two-owner repair is adopted: the shared first-party API dispatcher and dedicated media-insights GET now preserve installed Svelte `HttpError` status and curated `body.message` as `{error, code: "request_failed"}`. Existing cancellation, validation, domain and upstream-provider mappings keep their previous order and behavior. This is **API-HTTP-ERROR-OBS-10**, an additional observation outside the immutable 94 baseline. Parent-owned common gates and normal authenticated HTTP/browser acceptance are pending at publication. [Adoption receipt](evidence/api-http-errors-adoption.json), [exact patch](candidates/api-http-errors/trusted-http-error.patch).

Existing services already reject invalid music page/filter with 400 and unavailable music source or missing media with 404. Their errors missed the previous AppError/DomainError-only catches and became generic 503 responses. The new branch uses the installed `isHttpError` class predicate; arbitrary objects with a status/body remain unexpected failures. The shared client reads `payload.error`, so the expected JSON envelope retains the service's useful message. No natural outage, retry loop or performance gain is claimed from this source diagnosis.

The first shared owner is [the dispatcher](../../../src/lib/server/api/index.server.ts), used unchanged by GET/POST/PATCH/DELETE in the catch-all API route. The second is [the insights GET](../../../src/routes/api/v1/media/[id]/insights/+server.ts), wrapping the canonical title-insights service consumed by shared detail views. Its route authentication and parameter/source/page checks outside the try block are unchanged. Seven route files were reviewed: media statistics, people credits and diagnostics already rethrow unknown classes; share/public-token protocols have no concrete current Kit-service path established by this slice. No general error framework or blanket protocol migration was added.
