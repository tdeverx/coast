- `createResource` fences both results and errors to the latest request, aborts replacement/unmount delivery, preserves settled content during refresh, and supports caller-owned occurrence identity for append merging. Existing pure resource tests cover ignored aborts, stale rejection, partial provider failures and duplicate work occurrences.
- Shelf sources use one renderer and explicit local/page/cursor contracts. Layout uses resize/mutation observation with animation-frame coalescing and cleanup. Local filtering is opt-in. Journals retain event identities rather than flattening repeated watches into a work ID.
- Lazy artwork has a shared intersection observer and independent left-to-right queues per horizontal rail; load/error/removal release slots and fallback changes reacquire the same queue. Existing tests cover ordering and release. Actual image decoding, skeleton transitions and browser observer behavior remain unverified.
- Open menus share outside-event listeners, scope keyboard traversal to the current menu, clamp placement, clean positioning listeners on close, and expose nested compact navigation. Dialogs use the native modal/popover top layer. Interaction correctness still needs real-browser coverage; UI-01 is a surviving static default-policy defect.
- Semantic colors and typography are centralized. Glass has paired CSS fallbacks, shared setting observation/render scheduling, and explicit reduced-transparency/forced-colors treatment. Motion reductions exist in shared CSS and rail scrolling. No discretionary visual redesign is recommended.
- The preview route has administrator authorization, context-injected synthetic API/playback clients, lazy example mounting and component-catalog coverage. UI-02 identifies concrete escapes from that isolation.
- The chart gallery dynamically loads only the selected renderer family, mounts a single live specimen, uses decorative static thumbnails, bounds exact-data pages to 24 rows, and shares chart tokens with production insight charts. Existing semantics/geometry tests pass; their fixture evidence is not real-world performance evidence.

## Prioritized findings

### UI-02 · P1 · The isolated Header preview can change the real user’s presence settings and sign them out

**Confidence:** strong-static.

A page explicitly described as isolated demo data can persist real activity/presence privacy changes, invalidate production route state, or terminate the administrator’s session. This is an isolation/correctness defect, not an authorization bypass: the server still uses the actual authenticated account.

**Evidence:**

- `src/routes/ui-preview/Demo.svelte:261` — Header example renders a synthetic admin; its parent provides preview API/playback contexts.
- `src/routes/ui-preview/Demo.svelte:204` — Preview capture only cancels anchor default navigation; it does not stop native form submission or component handlers.
- `src/lib/ui/components/Header.svelte:76` — Status choices and Share activity call imported global chooseStatus/sharePresence without checking preview.
- `src/lib/social/status.svelte.ts:12` — Global updater calls the live API client, bypassing the synthetic client, and writes into the global userStatus.
- `src/lib/server/api/session.server.ts:9` — POST session/presence and session/status write authenticated user settings through the real status service.
- `src/lib/ui/components/Header.svelte:92` — Preview Header also retains a native POST /logout form.
- `src/lib/ui/components/MediaCard.svelte:165` — With experimental mediaModal enabled, card click handlers also call global pushState despite the parent preventing the anchor default; this can mount the real root modal for a fixture ID.

**Trigger:** An administrator opens /ui-preview/demo?component=Header (or the Header example in Components), opens Account menu → Activity status, and chooses a status or toggles Share activity. Clicking Sign out submits the real logout form. With mediaModal enabled, clicking a preview MediaCard can open the real root quick view.

**Minimal correction:** Keep preview status and account actions local or route them through the existing injected client and a local preview state; guard the native logout submit in preview. Make MediaCard respect preview/defaultPrevented before global navigation. Preserve production Header/Card presentation and behavior.

**Verification:** In an isolated browser fixture, intercept and fail any non-fixture POST. Exercise Header status/sharing/logout in both direct and embedded previews; assert no live request, no global userStatus mutation, no route refresh/logout, and no real root modal from preview card selection. Separately confirm ordinary Header actions still use the real authenticated client.

### UI-01 · P2 · Ordinary menu buttons remain open because keepOpen defaults to true

**Confidence:** strong-static.

The command completes while the menu remains open and focused. Native link items close through the existing action path, so pointer/keyboard behavior varies by whether a command is rendered as a button or anchor. Repeated commands remain immediately reachable despite the documented dismissal policy.

**Evidence:**

- `src/lib/ui/components/Button.svelte:33` — keepOpen defaults to true for every item button.
- `src/lib/ui/components/Button.svelte:92` — Every ordinary item button consequently receives data-menu-keep-open unless explicitly overridden.
- `src/lib/ui/controls/menu.svelte.ts:254` — The shared action handler returns without closeAll when that attribute is present.
- `src/lib/ui/components/MediaActions.svelte:686` — The concrete Right now tracking action does not override keepOpen. Many ordinary playback, relationship and tracking actions use the same pattern.
- `docs/design.md:84` — The design contract says ordinary actions dismiss menus, with rating/volume controls staying open.

**Trigger:** Open a media action menu, select Mark watched → Right now on a concrete movie/episode, and let the mutation settle; or activate another non-navigation item button that does not move focus outside the menu.

**Minimal correction:** Default ordinary item buttons to dismissal and explicitly retain keepOpen for continuous rating/volume, deliberate multi-select interactions, and any failed-action/error UX that needs to remain open. Keep menu triggers marked open and preserve existing nested-menu focus restoration.

**Verification:** Add a rendered menu interaction test covering pointer and Enter activation of an ordinary item, nested ordinary item, ordinary link, intentionally retained checkbox/rating/volume control, and disabled explanatory item. Assert menu closure and correct focus restoration for ordinary actions, with retained controls still open.

### UI-03 · P3 · The design guide contradicts the current mobile navigation and material inventory

**Confidence:** confirmed.

The guide can prompt an accidental restoration of obsolete mobile navigation or invalid material names, conflicting with the requirement to preserve approved UX. Passing token/fixture tests do not resolve which visual contract the documentation intends.

**Evidence:**

- `docs/design.md:68` — States primary navigation uses text-only pills on desktop and mobile.
- `src/lib/ui/components/Header.svelte:184` — Below 640px the actual Header hides text labels and displays navigation icons.
- `docs/design.md:74` — Names six shared treatments and says the six recipes are preserved.
- `src/lib/ui/materials/presets.ts:118` — Actual supported material variants are four: clear, glassLight, glassDark and glassProminent, each with a paired fallback.

**Trigger:** A maintainer follows the current source-of-truth design guide while changing shared navigation or material usage.

**Minimal correction:** Reconcile the two guide statements with the approved current UI and actual four-variant API; record approval status accurately. Do not change mobile visuals or reintroduce recipes solely to make the older prose true.

**Verification:** Review the current narrow Header and Materials reference against the approved UI, then check that documented variant names match keyof glassPresets.materials and that mobile prose matches the resulting approved behavior.
