# Server performance audit

Scope: read-only HEAD snapshot `/tmp/coast-performance-snapshot`; no live database, external provider, dependencies, Git state, or application service changed. Measurements used a standalone synthetic Bun harness. Source references below are relative to that snapshot and match the inspected HEAD. Measurements and harness: `/tmp/coast-server-performance-results.json`, `/tmp/coast-server-performance-harness.ts`.

## Prioritized findings and fixes

1. **Trakt history retains the whole account history before applying it.** `src/lib/sync/trakt-import.ts:151–161` pushes every 100-item page into `history` and then sorts/applies it. The 10,000-page guard permits up to roughly one million retained events; it is a traversal guard, not a practical RAM bound. `src/lib/providers/trakt/adapter.server.ts:80–89` likewise collects every page for collection shows, lists, and list items (`152–173`). Code proves O(total events/items) retention. Synthetic real-adapter parsing plus the same history accumulation: 10k events held 3.90 MiB heapUsed / 41.06 MiB RSS; 100k held 34.78 MiB heapUsed / 90.91 MiB RSS (both start around 0.31 MiB heapUsed / 16.4 MiB RSS). These are synthetic costs, not live account size or an OOM diagnosis.

   Smallest safe first reduction: store compact history event descriptors and share metadata per provider identity, instead of retaining a complete nested record for every rewatch. A strict bound requires ordered staging or verified chronological provider pagination. Do not replace this with forward page streaming: the current sort deliberately imports oldest watches first. Change `readPages` to expose a page iterator for catalogue consumers that do not require the full list; retain full list ordering where list reconciliation needs it. Regression constraints: oldest-first rewatches, same-date tie behavior, stable source-event IDs, duplicate/retry idempotence, removed-source suppression, and remote removals after a complete traversal. Benchmark repeated-title and unique-title fixtures separately; assert selected RAM bound at 100k+ events.

2. **Jellyfin's final playback reconciliation is unpaged and chatty despite paged scanning.** `src/lib/sync/jellyfin.ts:432–450` materializes the grouped observations for every available media item, retains that array while processing it, and calls `ensureConnected()` for each row (`446`). The observation query at `433–444` has no LIMIT. The main scan's `visited`/`knownItems` maps are cleared per page (`377–378`), so the initial traversal is already bounded to the 100-item provider page (`src/lib/providers/jellyfin/adapter.server.ts:253`). Each movie/episode then reconciles up to three categories independently (`src/lib/sync/jellyfin-playback.ts:25–55`), adding DB round trips. This is a code-confirmed scaling problem; its live time share is unmeasured.

   Smallest RAM fix: keyset-page grouped observations by media ID, with a small batch (e.g. 100). Initially retain the per-item `ensureConnected()` query. To reduce its query cost safely, fold its status/generation/user/provider/importPlayback checks into the connection validation already performed inside `reconcileProviderValue` (`src/lib/sync/values.ts:160–166`), rather than relaxing checks to batch boundaries. That existing transaction currently validates generation/status only; it is not yet equivalent to `ensureConnected()`. Preserve immediate importPlayback opt-out and account-change handling. Regression constraints: multiple editions aggregate into one observation, resume selection/tie ordering stays identical, account-generation replacement cannot import old data, disabled importPlayback stops processing, and an incomplete traversal never marks availability removed. Prove peak rows retained stay at the batch size and query counts drop without weakening validation.

3. **Public response caches retain expired values, with a count cap rather than a byte cap.** `src/lib/server/utils/provider-cache.ts:7–18` limits successful values to 100 entries, but TTL only prevents a hit; it does not delete expired entries until that key successfully refetches or is displaced. `src/lib/server/media-details.ts:12–13` creates 100-entry insights and people caches. A person includes its complete credits and overviews (`src/lib/providers/tmdb/details.server.ts:163–214`), so entry weights vary substantially. Actual-cache synthetic fixture: 100 entries × 1,000 credit-like rows with 512-character overviews retained 60.51 MiB heapUsed / 171.52 MiB RSS after expiry and GC; one-key refresh released only that entry. **This is bounded retention, not an unbounded leak, and these are not observed live filmographies.**

   Smallest fix: delete expired values before attempting a replacement; prune other expired values on lookup. If idle TTL should release memory without traffic, add one unref'd expiry sweep with clear ownership. Separately choose a conservative smaller capacity or byte budget for people data once representative payload sizes are measured; do not assume 100 equal-weight entries is a byte bound. Regression constraints: concurrent same-key requests still deduplicate, failed requests never poison pending state, incomplete insights remain uncached, values disappear after expiry under the chosen idle policy, and eviction never mixes user-specific data into the public cache.

4. **TMDB construction misses the provider tag used for pacing and diagnostics.** `src/lib/catalogue/service.ts:33–37` constructs its transport without `provider: 'tmdb'`. `src/lib/server/security/provider-fetch.ts:302` chooses 250 ms between calls only when the tag is trakt/steam/tmdb; the TMDB path consequently gets 0 ms. The two shared metadata workers (`src/lib/catalogue/maintenance.server.ts:341–349`) can each schedule three season imports (`src/lib/catalogue/service.ts:298–307`); the origin lane serializes transport, but missing pacing can create bursts. This is a confirmed configuration mismatch with the transport's intended policy, not proof of a real provider quota violation.

   Smallest fix: add the provider tag. Regression constraints: requests share the intended origin lane, diagnostics identify TMDB, urgent calls retain priority/fairness, and retries honor provider cooldowns. This improves pacing/cooldown behavior and may intentionally lengthen healthy bulk scans; do not present it as a raw throughput improvement.

5. **Repeated metadata hydration does avoidable work for unchanged catalogues.** The shared refresh chooses only 100 root candidates (`src/lib/catalogue/maintenance.server.ts:203`), but refreshing a show defaults to fetching all seasons and ingesting each episode (`src/lib/catalogue/service.ts:298–307,383`). A “100 titles” batch is not a 100-record or 100-request batch. Separately, daily Jellyfin user catalogue maintenance fetches each active title's root even when its canonical TMDB identity already exists (`src/lib/catalogue/maintenance.server.ts:128–139`); only after the provider request does `persistMissingTmdb` check existence (`32–43`). Code proves repeated work; magnitude needs representative shows/accounts.

   Smallest fix for user catalogue scanning: batch lookup known root provider mappings with canonical TMDB IDs before root downloads and skip identities already present, retaining remote reads for unmapped roots. For shared metadata refresh, measure episode ingest counts and avoid unconditional per-episode writes when their stored regional snapshots are unchanged; keep missing/new episode hydration and advance the root's refresh timestamp so the candidate does not immediately requeue. Regression constraints: newly added episodes appear, canonical identity conflicts remain isolated, unknown user-visible titles still enter the catalogue, and existing titles do not gain per-user availability from metadata refresh.

## Lower-priority measured or code-confirmed costs

- `src/lib/server/security/provider-fetch.ts:297–300` buffers each non-stream response to release the lane only after the bounded body completes; `270–274` then decodes that Response to text and JSON parses it. Default body cap is 8 MiB (`230`), so this is bounded per response, but multiple raw buffers/text/object allocations coexist. A 7.30 MiB fake body through the actual transport took 18.38 ms locally, moving heapUsed 15.72→52.38 MiB before GC and 24.72 after GC; baseline includes fixture string+bytes. Keep the bounded-body/read-before-lane-release invariant. Only consolidate into a single bounded decode/parse path if allocation profiling on real payloads shows material cost. Do not remove buffering or the cap to chase this microbenchmark.
- `src/lib/server/storage/image-cache.server.ts:29–35` sums all entries and sorts all entries before discovering that no eviction is needed. At the configured 10k file cap, the isolated sorting path took median 2.19 ms and p95 8.23 ms per attempted put, excluding I/O. Track total bytes, return before sorting when there is room, and sort only on actual eviction. `38–50` also serializes all disk reads with writes; first fix the unconditional sort, then measure disk-read head-of-line delay before changing concurrency. Maintain one initialization/mutation owner, admission accounting including temporary files, ENOENT handling, and disk/free-space caps.
- `src/lib/server/security/request-priority.ts:15–26,31–43` has no queue admission limit; request timeout begins only when the queued operation starts (`provider-fetch.ts:178–183,303`). A busy/cooling-down origin can retain arbitrary pending closures/HTTP requests under load, even though in-flight fetch concurrency is one per origin. Current normal producers often await calls, so this is a overload hypothesis, not observed backlog. Add a modest pending cap and propagate cancellation/queue deadline only if stress testing establishes queue growth. Keep fairness, cooldown, streaming bypass, and immediate abort cleanup.
- The scheduler runs every minute (`src/lib/providers/maintenance.server.ts:340–344`), aggregates retained outbox history by connection/kind (`164–192`), and makes one presence query per eligible connection (`225`). Retention explicitly preserves outbox history (`src/lib/server/storage/retention.server.ts:4`). Thus scheduler work grows with outbox/account volume. Candidate improvement: one batched presence query and indexed latest-success/active probes rather than scanning full success history. This needs a disposable EXPLAIN/benchmark before it should join the implementation scope.

## Existing bounds and diagnostic limits

Queue execution has three workers, one urgent-only (`src/lib/server/queue/index.ts:362`); its reserved connection is released in finally (`326–331`) and heartbeats are cleared (`321–322`). SQL pool max is 10 and JIT is disabled (`src/lib/server/db/index.ts:24`). TMDB artwork caps pending downloads at four (`src/lib/providers/tmdb/artwork.server.ts:59`); diagnostics cap queued writes at 128 (`src/lib/server/diagnostics/index.ts:21,62`). Image caches store bytes on disk, with metadata-only maps capped to 10k files and 1 GiB disk usage (`image-cache.server.ts:5–6`). These are not evidence of an unbounded RAM cache.

Parent's captured live 2 GiB container had approximately 900 MiB file cache and 350 MiB anonymous memory, with current memory.events reporting no OOM. File cache is not JavaScript heap, and these source/harness findings cannot establish the cause of an unexplained process exit 1. Do not attribute that exit to OOM without matching event/log evidence.
