# Invitations and first-pass experiments

Administrators create single-use, expiring registration codes or links in Settings → Users. Links carry the secret in the URL fragment, which is removed on arrival and never sent as a query string. Registration consumes the invitation atomically, creates a normal Coast account, and retains the existing password/confirmation, connection, profile-image and initial-import steps.

An invitation may include Jellyfin provisioning through an administrator's connected account and an explicit selection of permitted libraries. Coast verifies the pinned server identity, account generation, current administrator privileges and library IDs before creation. New accounts get a random initial password, a restricted non-administrator policy, then their chosen Jellyfin password. The normal Jellyfin connection path queues user import; shared library scans cannot complete onboarding. Lost creation responses require administrator review; Coast never adopts an existing account by username or blindly creates another one. A known created account can retry its remaining configuration. No Jellyfin password is stored in the provisioning record.

The password endpoint follows the current [Jellyfin controller](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/UserController.cs), using `/Users/Password?userId=…`.

Disposable playback sharing is separately enabled by administrator policy. Administrators have permission; other users need an explicit grant in Settings → Users. A link covers one accessible movie, episode or track from one selected Jellyfin connection, expires within 24 hours, is single-use for its guest, and can be revoked in Playback settings. Its stored token is hashed. Changing the source account, removing access, disabling the owner/source/medium, revoking permission or disabling sharing invalidates it.

Guests receive an HttpOnly, same-site capability for that item. The ordinary player and authenticated relay handle playback, subtitles and HLS resources. The capability cannot read the catalogue, profiles or tracking, and never records guest activity in the owner's history, listens or live presence. Shared sessions do not stop the owner's unrelated playback. Together mode offers a host link, pins the selected source/duration, and aligns the guest to the host's timeline. It is a bounded host-and-guest invitation; general guest party rooms remain separate future work. Different browsers/codecs may be unable to play that selected source; sharing does not grant transcoding beyond installation policy.

Dynamic For You and personalised recommendations are standard features. The feed appends one horizontal Shelf row at a time when the page bottom is reached. Rows use personal interests, cached provider suggestions and taste scores across enabled media; cards load lazily and further card pages load horizontally. Core rows remain above the dynamic feed, and eligible rows are not recycled. Recommendation results never create personal relationships.

Two remaining first-pass switches are off by default in Settings → Policies:

- **Planning/calendar:** Plan in a saved work's menu schedules a date and optional friends. Planning shows scheduled items. Upcoming on For You shows known releases for the next 90 days, with Watching/Playing/Listening segments, scoped to watchlisted titles and new episodes of tracked shows (excluding dropped shows). Unreleased items do not need Collection membership. Reminders use the existing outbox; starting completes the plan. Unknown release dates are not invented. A planned party sends actual invitations when the host starts it.
- **Modal media details:** Saved detail rows open in the existing dialog without changing the underlying route or scroll; Escape/back close it, and Full page remains available. Provider enrichment stays on the normal full detail path.

New visual treatments are explicitly unapproved. This pass adds no production dependency, scheduler, authentication binding system or provider connector protocol. Public API writes and signed webhooks are documented in [public-api.md](public-api.md).
