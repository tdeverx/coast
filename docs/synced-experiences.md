# Synced experiences and invitation onboarding

Synced playback is experimental. Enable the existing Experimental features policy, play a movie, episode or music queue, and choose **Start synced session…** from the existing playback menu. The session starts paused. Invite accepted friends; their notification opens the join page. Use the existing media controller to play, pause, seek or change items.

Each participant prepares their own authenticated source. A source must match the exact leaf title, medium, edition label and duration (within two seconds). No server URL, provider token or host stream is shared. Friendship removal, disabled accounts, disconnected sources and provider account changes revoke participation. A user joins one room at a time; hosting another ends their previous room. Sessions last at most 24 hours, with up to 16 participants and 200 music queue entries.

The host owns a durable, revision-checked timeline. Clients heartbeat every two seconds while joined, estimate server clock offset, gently correct small drift and seek for drift over 1.5 seconds. **Pause together** waits for buffering participants; **Continue and catch up** allows them to catch up individually. A missing host heartbeat pauses the session after 15 seconds. Reloading restores the session from the tab's session storage and prepares a new authorized source. Browser autoplay restrictions may still require pressing Play.

Music keeps queue order, repeated entries and unresolved gaps. Only the host advances; unavailable tracks are skipped with the existing notice. Guests prepare each newly selected track independently. Tracking uses the existing playback session and actual-play listen threshold; synchronization seeks do not create played time. Audio stays alive through browsing. Navigating away from active video leaves its synced session and retains the existing video-navigation pause behavior.

Invitation onboarding is independent of Experimental features. In **Settings → Accounts**, an administrator creates an expiring single-use code (1–30 days). The code is shown once; only its SHA-256 digest is stored. It can be revoked before redemption. Registration creates a normal Coast user with the existing password policy and an authoritative onboarding record, atomically consuming the invitation.

The new user connects an existing administrator-approved Jellyfin service using their Jellyfin credentials. Coast stores the encrypted connection token, not the Jellyfin password, and reuses `jellyfin.sync`. The setup screen displays its progress. Refreshes and subsequent sign-ins resume setup. The server blocks main pages and APIs until a successful, fresh `jellyfin-user` traversal for the linked account generation completes. Shared metadata scans do not satisfy this gate. Failed imports offer reconnect and owner-scoped retry; existing queue deduplication, service ordering, cooldowns and scheduling remain intact. Queueing behind another service job is handled without creating duplicate work.

No new production dependency, scheduler, authentication binding system, player design, chat, guest access or Jellyfin account provisioning was added.

Verification: isolated database fixtures cover atomic invite redemption/revocation/expiry, user traversal gating, source ownership/compatibility, host-only revision control, buffering policies, account-change revocation and ordered/repeated music queue entries. Browser fixtures verify two independent video connections, host play/pause/seek, private invitations, shared music item changes with a missing-track notice, and onboarding through initial import to main-site access. Live multi-device/Jellyfin acceptance and mobile playback remain separate acceptance checks; the in-app browser viewport override did not apply during this pass.

Party item changes use the prepared playback descriptor (identity, transport, edition and duration), rather than the previous item’s category. Video/audio transitions reset obsolete queue state, retain participants and recheck control permissions on bounded revision-conflict retries. Delayed heartbeat responses cannot overwrite a newer transition. Unresolved item changes surface a failure and stop the unmatched local source. Future synchronized media must supply an actual supported playback/timeline adapter; an unsupported medium is not treated as video implicitly. Foreground video hides browsing content and the media-details modal even while paused; hidden hero trailers pause and do not attach new sources until browsing is visible again.

## Reusable playback links

Playback sharing is independent of account invitations and website visibility. Enable **Playback sharing** in Policies; administrators can share, and other users need an administrator's explicit sharing grant in Accounts. **Share** creates a website invitation for one permitted Jellyfin movie, episode or music track. **Share to VRChat** is a separate movie/episode option. Links expire after 1–24 hours (six by default), can be copied/revoked, and remain subject to the existing twenty-active-link bound and medium policy.

Website links use `/share/{token}` and always open Coast's shared player. Browser capabilities, personal/server bitrate ceilings, direct/relay planning, subtitle and transcoding policies remain authoritative. A compatible original file can be relayed without transcoding, including when transcoding is disabled. Upstream credentials stay inside Coast. Each website viewer reserves a stable portion of the sharing budget; joining VRChat viewers cannot turn a direct-file response into an HLS rendition through a bitrate-only rewrite.

VRChat links use `/share/{token}.m3u8` and resolve directly to cookie-free HLS for AVPro-based worlds. H.264 High, 8-bit output, AAC-LC stereo/48 kHz at 192 kbps, up to 1920×1080 and four-second MPEG-TS segments are requested. Video bitrate is capped at 8 Mbps plus audio, within the creator/server sharing allowance. Source cadence is retained: Coast sends no frame-rate override. Codec levels account for known output dimensions/cadence. Aspect-ratio scaling, exact VBV/preset behavior and hardware encoder details remain Jellyfin's responsibility; this is not a byte-identical VRRelay encoder.

The administrator can enable an **experimental H.265 / AAC fMP4 HLS** alternative; it is off by default, requires transcoding and remains permission-checked on every resource request. A global policy withdrawal rejects new resource reads. World/backend/device and Jellyfin encoder compatibility must be tested. In particular, the local 1080p60 VideoToolbox HEVC check retains an under-declared codec-level failure; H.264 is the verified high-frame-rate path. See [format/backend research](vrchat-playback.md) and the [28 October implementation evidence](audits/2026-10-28-share-destinations.md). VRChat preparation skips browser-only crop analysis. Unity-only players need a direct-file delivery design and are not covered by this HLS option.

The `.m3u8` suffix is removed before validating the original grant, but cannot change a persisted website grant into a VRChat grant. HEAD requests validate without allocating a viewer or encoder. Existing grants migrate to website invitations. Grant hashes, expiry, revocation, owner permissions, source/account generation and profile policy remain authoritative; downloaded bytes cannot be revoked. Logs must not expose link tokens or resource capabilities. Use trusted public HTTPS for native VRChat/Quest tests; local HTTP checks do not certify that topology.

Browser viewers have distinct grants. Cookie-free clients reuse a durable viewer lease identified by a link-scoped hash of address and a bounded user agent. Retries and parallel segment requests reuse that lease; raw addresses and user agents are not stored. Shared viewer counts are estimates, not named people: identical clients behind one address can merge, and a change in client identity can create another lease. Each link permits at most sixty-four viewer grants over its lifetime; create a replacement link if that bound is reached.

Accounts have independent **Personal stream limit** and **Shared links budget** controls in the administrator's account editor. Personal limits are per stream and default to the server ceiling. Shared budgets default to 20 Mbps and apply independently across all that creator's active links. Each viewer targets the creator's normal personal stream limit (itself bounded by the server per-stream ceiling), then its codec/profile ceiling; the aggregate sharing budget only reduces that target when necessary. The allocator reserves 15% headroom, rounds allocations down to 50 kbps steps, and admits at most twenty concurrent viewer leases with a minimum 500 kbps allocation. Full capacity returns a retryable 429 instead of raising the allowance. When an administrator lowers a budget below current capacity, the earliest admitted viewers that still fit retain their leases; excess viewers end durably and their encoders are stopped. New arrivals do not displace admitted viewers. These are negotiated media targets; variable bitrate, buffered downloads and transport overhead prevent an exact instantaneous egress guarantee.

Each viewer owns a separate Jellyfin device/play session. Replaying stops the viewer’s current encoder before preparing a replacement. Known failed cleanup for the owner must drain before another shared session starts; failed provider stops retain their durable retry flag. Website reservations stay fixed while admitted. VRChat viewers divide the budget remaining after those reservations. When VRChat allocations decrease, subsequent resource requests stop only that viewer's previous encoder and replace its upstream play session while keeping the public media URLs and timeline stable. Increases below 25% retain their current generation to avoid small quality oscillations. Requested codecs, maximum dimensions and segment duration remain fixed within this bitrate-only flow; Jellyfin may choose a different encoded resolution at a new bitrate. Durable preparation tokens fence concurrent or interrupted handoffs. Short database request leases allow up to eight parallel resource dispatches per viewer; replay, stop and quality changes drain those dispatches before retiring an encoder. Dispatches have a 25-second deadline until upstream headers arrive; crash leases expire after 35 seconds. The deadline is cleared at headers so normal response-body streaming keeps its existing behavior. Provider calls do not hold database transaction locks. Existing buffered video remains playable, so the quality change can take effect after that buffer drains.

Resource activity renews leases with coalesced writes. The browser landing page also keeps its paused viewer lease alive while open. External leases become idle after ninety seconds without requests. The existing maintenance lifecycle ends abandoned/expired viewers in bounded batches and retries failed encoder cleanup durably, including in developer mode; it does not run imports. Revocation blocks future reads immediately and stops the known viewer encoders. Already downloaded bytes cannot be revoked. Guest progress stays isolated from the owner's Coast history and is not scrobbled to Jellyfin or Trakt.

The administrator's existing **Active streams → Now / History** cards include shared origin, creator, estimated link viewers and current negotiated bitrate. Requested segment time is an approximate delivery position, not proof of viewing. Matching provider device IDs prevent double counting a locally represented share session in Jellyfin's cached observations. Reads and card hydration remain bounded and batched by server.
