# Job scheduling and progress

Provider schedules describe when work becomes due. `task-timing.ts` holds the shared pure rules used by the maintenance timer and the Jobs timing read model: feature and schedule gates, account opt-ins, selected shared sources, account completion evidence, active/idle live cadence, and Jellyfin full/recent metadata cadence. Metadata refresh retains record-specific SQL evidence because each title has its own refresh and retry time.

Jellyfin bootstrap is requested when an account connects; it has no recurring due time. Its completion imports personal activity and makes the account usable. A fresh completed per-library inventory can grant positive screen availability after the new account’s own permissions are verified, before its separate full user scan checks exhaustive access. Restricted item policies and stale/incomplete inventory use normal authenticated traversal. Jobs uses the import stage labels and `stageProcessed`/`stageTotal` counters for music and reconciliation, so later stages do not appear stuck at the screen-item count. Successful bootstrap text explicitly distinguishes that partial import from full access coverage.

Shared library metadata, server streams, and TMDB/IGDB recommendation tasks represent service-wide work. Personal imports, live observations, and Trakt recommendations retain their account and account-generation identity. An automatic timer selects the oldest due account for each task on a tick. Manual runs request every eligible account and reuse or promote its own pending/running work. Obsolete generations cannot block a new account generation. Account opt-outs remain effective for manual runs. A manual full-library request upgrades a pending recent scan to full, or records a full followup when that recent scan is already running.

Jobs shows one compact row per service/task in Running, Waiting, Needs attention, Upcoming or Manual. Individual account/generation jobs remain independent underneath. A task with running and waiting accounts appears once under Running; it moves to Waiting, Needs attention or its next schedule as work finishes. Running, waiting and attention counts cover all current-generation jobs, with only representative records returned for Details. The bounded individual-job diagnostics sample does not limit task totals or hide completed one-off tasks.

Account tasks show completed/eligible users, explicitly labelled as their latest runs. A user's most recent current-generation run must have succeeded to count as completed; pending, running, failed or cancelled latest runs remain incomplete. This is not a claimed batch completion count. Details separately show freshness: successful evidence within two schedule intervals.

Upcoming is ordered by next scheduled start. Manual contains tasks with no assessed automatic start; rows explain paused schedules, unavailable connections or configuration requirements. Run now, Prioritize, targeted Retry, Cancel waiting work, Edit schedule and Details use the existing action menu; detailed progress and error explanations are shown on request. Task controls target all matching current-generation jobs, independently of the displayed representatives. Failed accounts can retry while other accounts run or wait; duplicate active work for the same job identity is skipped. Cancellation affects pending and failed jobs, preserving running work and unrelated services. These requests preserve cooldown, backoff and account permission boundaries. Event-driven deliveries appear when requested rather than pretending to have a recurring timer.

The History tab and per-task history dialogs are removed. Each task shows its last terminal run time and result, read independently of the bounded queue display and scoped to the current account generation. The persistent outbox job records remain retained by storage cleanup; removing history UI never deletes them. Diagnostic files retain their existing bounded rotation policy, so the permanent job record is the database outbox rather than an unbounded diagnostic file.


The recommendation scheduler uses the same task enablement and due functions. Shared recommendations use the latest completed service run; Trakt uses each connected account's completed run. A manual request can rerun a fresh account and cannot silently disappear behind another account's recommendation job. Recommendation refresh freezes its bounded selection (six shared seeds or two Trakt categories) before updating freshness. Each saved set advances the durable cursor and provides a safe yield boundary. Resume keeps the same selection even after taste or freshness changes, and current-account and worker-lease checks fence publication.

Shared TMDB refresh retains its finite selection of at most 100 title/region pairs and each completed cursor in `_checkpoint`, including forced batches. Titles refresh sequentially and yield after replay-safe progress; a resume cannot reselect the first records as their timestamps change. Individual missing records retain retry evidence without stopping other records. Run now requests this bounded batch, not a force-refresh of the entire catalogue.

User catalogue recovery remains a metadata-only task even when personal imports are disabled. It reads only direct remote references and never removes personal relationships. Queued scans retain their next category/page or activity-filter offset, and one bounded list page plus its list/item cursor, in `_checkpoint`. The cursor advances after that page's positive metadata references have committed; `jobCheckpoint` can then release the worker lane. Direct helper calls finish normally. Jellyfin catalogue reads the union of played, resumable and favourite server filters, skips roots already mapped to shared TMDB identities, and hydrates unknown accessible roots in authenticated batches of at most 100. Missing individual roots are omitted without inferring a removal.

Focused verification:

- `bun test tests/catalogue-maintenance.test.ts` checks remote categories, filtered/batched root hydration, missing roots, source cursor resume and failed-save boundaries.
- `TEST_DATABASE_URL=<disposable-database-capable-url> bun scripts/test-database.ts catalogue-cursor-db.test.ts catalogue-maintenance-db.test.ts catalogue-roots-db.test.ts` checks committed metadata, durable cursor/yield and purpose preservation in isolated databases.
- `TEST_DATABASE_URL=<disposable-database-capable-url> bun scripts/test-database.ts maintenance-runner-db.test.ts provider-recommendations-db.test.ts seerr-account-scope-db.test.ts` checks displayed eligibility versus claiming, retained recommendation selections, cancellation and account-generation publication fences.
- `bun test tests/task-timing.test.ts` checks eligibility, completion evidence, due times, stage text and waiting labels without a database.
- `TEST_DATABASE_URL=<disposable-database-capable-url> bun scripts/test-database.ts task-timing-db.test.ts job-task-summary-db.test.ts maintenance-db.test.ts` creates isolated databases, runs migrations and fixtures, then removes the test databases. It checks timer/read-model agreement, manual reuse/promotion, account identity, generation changes, recommendation cadence, totals beyond display limits, retained one-off results and task-wide retry/cancellation.

These tests establish scheduling and presentation behavior. They do not measure live Jellyfin performance or prove deployed-server coverage.

Companion-aware Jellyfin scheduling and recovery are documented in [Jellyfin companion updates](jellyfin-companion.md). A caught-up feed replaces separate native live polls and queues targeted item jobs; initial imports and periodic full reconciliation remain. Both Jobs and the timer use the same health, source-generation and due rules.
