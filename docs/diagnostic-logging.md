# Diagnostic logging

Administrators can select Off, Error, Warn, Info, Debug or Trace in **Settings → Activity & diagnostics** and download recent events as JSON Lines. Info is the default; Debug and Trace are opt-in. Configuration is persisted in the existing system settings. Saving changes the running server immediately. Other browser tabs learn the level on their next API response or within 30 seconds. No restart is needed.

Events cover HTTP outcomes, provider calls, durable jobs, browser errors and playback. The selected level includes the levels above it in the table.

| Level | Recorded detail |
| --- | --- |
| Error | Unhandled application and browser errors, terminal playback failures, scheduled backup failures, and jobs that stopped or reached the retry attention threshold. |
| Warn | Early job retries, provider transport failures and HTTP rejections, stale application assets, rate limits, and recoverable failures such as unavailable crop metadata or invalid browser responses. |
| Info | Normal outcomes and expected validation or access responses, playback preparation and playing, subtitle searches and downloads, completed jobs, and ready reading archives. Routine streams, assets, progress, heartbeats, health checks and live polling appear here when they take at least one second. |
| Debug | The faster routine outcomes listed above, request and job starts, caller cancellations, and playback lifecycle events such as waiting, pause and seek. |
| Trace | Provider request starts and browser playback samples for position, buffering and elapsed time. |

Request events use fixed operation and action names, including public API calls and shared playback or reading. Playback preparation includes the delivery type, whether it started or replaced a session, and time spent negotiating sources. Crop, subtitle options, search, download and confirmation have their own stages. Provider events distinguish queue wait and its deadline from upstream I/O and response-body failures. Total provider time ends at response headers for streaming and after the bounded response body for other calls. Reading manifest events record whether archive preparation finished after headers were sent. Backup events distinguish scheduling, capture and retention. Background cleanup and provider fallbacks use their owning operation and stage.

Replacing or closing a player cancels relay requests. Cancellation before stream headers returns 499 and appears at Debug. Provider deadlines remain failures. Automatic detail enrichment retains saved metadata and records a diagnostic if refresh fails. A browser correlation ID can cover several requests, so compare timestamps and operation labels before attributing one event to another.

A random browser correlation ID travels in `X-Coast-Correlation-Id`. Each HTTP call also gets a server-generated `X-Coast-Request-Id`. Use `requestId` to match one response to its provider events, and `correlationId` to follow related activity through the browser and queued work. Browser errors distinguish runtime, promise, resource and request failures. A malformed response can include its server ID as `relatedRequestId`. Session and action IDs connect activity across requests. Browser reports are untrusted and rate limited.

The event schema admits only named events, closed classifications, finite numeric measurements and random session/action IDs. It excludes identities, titles, provider addresses, URL paths/queries, cookies, credentials, tokens, request/response bodies, exception messages and stacks. Background job events identify the job kind, retry number, and failure stage or recognized database code when available. Downloads contain this same safe schema. The browser’s minute allowance reserves ten slots for errors when verbose playback logging is enabled.

Server-stream scan failures identify the phase: module loading, account validation, connection loading, administrator permissions, session reading or observation recording. If saving the failure also fails, diagnostics retain the original exception classification and phase.

Logs stay in `COAST_DATA_DIR/diagnostics`, with a private directory and owner-only files. One application process writes a serialized queue of at most 128 pending events. Verbose and routine events can fill 96 slots. Warnings and errors can use the remaining 32, with the final 16 reserved for errors. Application diagnostics rotate in 1 MiB segments. Administrators set a maximum size of 4–4096 MiB and a maximum age of 1–365 days in **Settings → Activity & diagnostics**. Defaults are 256 MiB and seven days. The first limit reached removes the oldest segments. Changes apply without a restart. Lowering either limit prunes older segments on the next read or write. Downloads stream sanitized segments and age limits apply to both storage and reads. Queue saturation, inaccessible storage and full disks can drop events. Logging failures do not affect application actions.

Logging-setting changes are recorded transactionally in `diagnostic_setting_audit`, with the administrator, previous/new level and timestamp. This audit and the existing metadata audit stay in PostgreSQL, independent of diagnostic levels and retention; recent audit activity remains visible when diagnostics are Off. Existing authentication/session security behavior is unchanged.

Apply the generated database migrations through the normal Coast migration workflow before running the updated app. No production dependencies were added.

Focused validation: `bun test tests/diagnostic-logging.test.ts`, the isolated `tests/platform-db.test.ts` suite, and `bun scripts/browser-diagnostics-check.ts`. The browser harness targets only localhost:5175 and expects a disposable installation; it creates synthetic admin/member accounts and verifies controls, runtime changes, persistence, download redaction and admin authorization. Use the existing fixture harness for actual provider/media playback checks.

## Provider transaction lock ordering

Read-only Seerr, Jellyfin screen-access and recommendation guards acquire the shared configuration/user policy fence before provider instances, then provider connections, then the worker lease. Multiple instances or connections are locked in ID order. Do not upgrade their shared user lock to `FOR UPDATE`: reconciliation already holds that same shared user fence before waiting for a connection. An account guard holding the connection and requesting an exclusive user lock creates a cycle with reconciliation.

Jellyfin inherited-library source checks use `FOR SHARE` on the source connection and user. These fences still block account replacement, disconnect and user-disable updates until the observation commits, while allowing a concurrent reconciliation user fence. Instance locking serializes the cache writers. Preserve the current generation, external identity, disabled-user, enabled-instance and worker-lease checks when changing this code.

The 31 October 2026 investigation matched 29 retained live deadlocks to nine Jellyfin delta tasks, four Jellyfin reconciliation tasks and sixteen Seerr sync tasks. Every affected task completed on its second attempt. This is a recovery observation, not proof that every historical task or media row was audited. The cumulative database counter included older incidents outside the retained log window. No live data or settings were changed during the investigation or local verification.

SQLSTATE `40P01` is reported as `local.database-deadlock`, with a local database-conflict retry message. Bun exposes the SQLSTATE in `errno`; Drizzle can wrap that error in `cause`. Classification checks a bounded cause chain and only the fixed code, excluding SQL, parameters and exception text. Existing checkpoint retention and retry backoff are unchanged.

Regression checks: `tests/provider-lock-order-db.test.ts` holds the actual policy/user fence on an independent PostgreSQL connection while executing each production guard, including a different cache source owner. The four concurrency cases fail with the original guards and pass with the consistent shared-user order. The suite also checks committed withdrawal/replacement and actual Bun/Drizzle SQLSTATE classification. Run it with `bun scripts/test-database.ts provider-lock-order-db.test.ts`, alongside the Seerr account/refresh/delivery, Jellyfin access/reconciliation, recommendation and feature-boundary database suites. These are disposable synthetic contract tests; post-deployment live recurrence remains a separate observation. See `docs/audits/2026-10-31-provider-deadlocks.json` for the reviewed evidence epoch.

## Container crash evidence

The container retains application stderr in `COAST_DATA_DIR/runtime/application-stderr.log` and one rotated `.1` segment, each limited to 256 KiB. Migrations use separate `runtime/migration-stderr.log` segments with the same limits. These owner-only files survive restarts and include a timestamp for each child start. Stderr still reaches the container console; unavailable diagnostic storage does not change child exit status. After the direct child exits, stderr drains for at most 250 ms so an inherited pipe cannot hide its exit.

Unlike the structured diagnostic export, these files contain raw runtime errors and may include sensitive details. They are local operator diagnostics and are never included in the web diagnostic download. Inspect them privately alongside `runtime/child-exits.jsonl` after an unexpected shutdown.

## Runtime recurrence evidence

Server initialization starts one unreferenced sampler per process, with an initial sample and then one every 60 seconds. `runtime.sample` records the application PID, Bun version, uptime, RSS, heap/external memory and cumulative user/system CPU milliseconds. CPU utilization can be derived from consecutive samples; these are not peak measurements. On Linux it additionally reads four fixed cgroup-v2 files for current/limit/anonymous/file memory and OOM counters. Missing cgroup fields are omitted. The mounted cgroup's scope is not assumed to equal every process in the VM.

Samples include observed connection-open/close/failure totals, pending queue reservation acquisitions, held queue reservations, queue ticks, heartbeat operations and maintenance ticks. Busy duration is the age of a continuous nonzero in-flight period, not exact oldest-operation age. Heartbeat/maintenance overlap counters expose simultaneous operations without changing their scheduling. Reservation measurements cover explicit queue reservations, not Drizzle's internal transaction reservations or every native pool query. Connection callbacks are observed events, not an authoritative current server-session count. No PostgreSQL catalog polling is added.

`runtime.operation` captures failed operations or operations lasting at least one second. Separate budgets allow at most 30 timing and 30 failure events per fixed 60-second window, so timing events do not consume failure capacity. Suppressed-event totals remain in samples. Failure events use Error and timing events use Info. Resource sampling only collects counters and reads cgroup files when Info is enabled. A stalled resource sample cannot overlap another sample. Runtime counters use constant storage and have no per-job identity map.

Operation events reuse the closed field vocabulary and existing private structured store with its configured size/age limits and at most 128 queued writes. These settings apply to application diagnostic events. Resource samples instead use their own `COAST_DATA_DIR/runtime/samples/` quota of four 1 MiB segments, seven-day retention and a 4 KiB maximum record. At most one sample per minute, including runtime replacements, reserves approximately 17 hours at that maximum record size; actual retention is usually longer, capped at seven days. Provider chatter cannot rotate these samples out. Size rotation can shorten operation-event retention. Samples expose queue-depth, dropped-write and filesystem-failure totals. Storage failure does not change work results or exception identity. New events contain no credentials, URLs, personal rows, provider IDs, SQL text/parameters or arbitrary error messages. Existing bounded child-exit/stderr capture remains in place; raw stderr stays private and excluded from safe exports.

## Developer mode

Settings → Policies → Development has an installation-wide Developer mode switch, off by default. It pauses automatic scheduling, queued background jobs (including live reads, recommendations, taste refreshes, reminders and webhook deliveries), retries and retention cleanup. Already running jobs finish their current run. Explicit tracking/playback changes, first imports requested by connecting an account, benchmarks, Run now and Retry remain available. Manual job failures wait for another Retry while the mode is enabled. Pending automatic work is retained and resumes when the switch is disabled. Run now authorizes an already queued task without duplicating it.

## Evidence when PostgreSQL or the app fails

In the bundled deployment, `COAST_DATA_DIR/runtime` belongs on the durable app-data bind, outside the separately mounted PostgreSQL volume. The default `/data/runtime` and `/data/postgres` paths alone do not establish separate storage: verify the mounts, protect operator-only files and back up both. An app-data disk failure can still lose logs. Runtime resource samples are private operator files and are not included in the ordinary diagnostic download.

`runtime/migrations.jsonl` and one rotated segment (128 KiB each) record migration start/success/failure independently of a database connection. Records include source journal/SQL checksum aggregates, last source checksum, source migration count, Bun version and supplied build identity. Bundled PG version is collected from the executable, even on migration failure. After success, a single cancellable, 250 ms metadata query captures actual server version, applied ledger count and latest ledger hash; missing metadata remains unknown. Ledger timestamps are migration ordering values, not execution times. Success records do not independently certify the complete schema or all historical hashes. Filesystem errors are ignored, pending writes are capped at eight, and each caller waits at most 250 ms. Missing records are possible after crashes or storage failure.

The PostgreSQL wrapper additionally retains only fixed timestamped ready/shutdown/PANIC/connection-limit categories plus start/exit/version/PID in `runtime/database-events.jsonl` and one 1 MiB rotation. Failure categories are capped at two per minute; arbitrary statements/errors/rows are discarded. Raw stderr continues to the existing operator console rather than the new structured file. Its 4 KiB line buffer discards oversized lines and storage failure preserves child status. TERM/INT request fast shutdown (`SIGINT`); QUIT requests immediate shutdown (`SIGQUIT`).

The supervisor records fixed `start`, `drain`, `fast`, `immediate`, `kill`, `unreaped` and `complete` stages in `runtime/shutdown-events.jsonl` and one 128 KiB rotation. Records contain only fixed child/signal categories, exit status and build identity. Each diagnostic subprocess has a 250 ms deadline and a 100 ms kill allowance; unavailable storage can leave gaps. These files belong outside the separately mounted PostgreSQL volume, alongside child-exit and migration evidence. They are private operator files, excluded from web exports. See [deployment](deployment.md#shutdown-and-readiness) for deadlines and forced-stop risks.

Application samples stop when its event loop or process stops. The PG wrapper can record DB failure while the app is gone, but both stop with the guest. A separately approved host recorder should capture bounded Coast-only host/guest resource counters, VM/container state and exits, classified ext4/I/O events, image/build versions and monotonic-to-UTC correlation in storage independent of both guest volumes. Exclude environment, arguments, SQL, request contents, secrets and personal rows; expose recording failures and retention/capacity status. It needs a reviewed launch/service configuration, lifecycle controls and resource/retention limits. No persistent host recorder is installed by this change.
