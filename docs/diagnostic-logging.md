# Diagnostic logging

Administrators can select Off, Error, Warn, Info, Debug or Trace in **Settings → Activity & diagnostics** and download recent events as JSON Lines. Info is the default; Debug and Trace are opt-in. Configuration is persisted in the existing system settings. Saving changes the running server immediately. Other browser tabs learn the level on their next API response or within 30 seconds. No restart is needed.

Events cover HTTP outcomes, provider calls, durable job execution, browser errors and playback. Debug adds request/job starts and playback lifecycle events; Trace adds provider starts and playback position, buffering and elapsed timing. Provider duration measures response headers; playback measurements describe the browser video element, rather than decoded frame performance. Direct provider playback cannot expose server-side stream activity; browser playback events still apply.

Replacing or closing a player cancels relay requests. Caller cancellations are recorded at Info by the provider transport; cancellation before stream headers returns 499 instead of an application 500. Provider timeouts and failures remain errors. An `aborted` event by itself does not establish an upstream outage. Repeated 400s or generic browser errors need reproduction: the redacted export intentionally excludes the URL and exception text, and a browser correlation ID can cover several requests.

A random browser correlation ID travels in `X-Coast-Correlation-Id`. Server async context carries it into provider calls and queued actions. The ID is persisted with jobs and playback sessions so retries and relay requests remain connected. Session and action IDs supply additional links. Correlation IDs are opaque diagnostic labels, never authentication or authorization evidence. Browser reports are untrusted and rate limited.

The event schema admits only named events, closed classifications, finite numeric measurements and random session/action IDs. It excludes identities, titles, provider addresses, URL paths/queries, cookies, credentials, tokens, request/response bodies, exception messages and stacks. Browser errors are classified without reading their text. Detailed job failure codes and scan phases come from a closed vocabulary. Downloads contain this same safe schema.

Server-stream scan failures identify the phase: module loading, account validation, connection loading, administrator permissions, session reading or observation recording. If saving the failure also fails, diagnostics retain the original exception classification and phase.

Logs stay in `COAST_DATA_DIR/diagnostics`, with a private directory and owner-only files. One application process writes a serialized queue of at most 128 pending events. Four segments rotate at 1 MiB each, keeping at most 4 MiB. Seven-day retention is enforced on reads and periodically on writes; entire expired segments are discarded. Diagnostics are best effort: queue saturation, inaccessible storage or full disks drop events without failing application actions. A download can therefore be empty when storage is unavailable. Logs are never sent to a remote collector.

Logging-setting changes are recorded transactionally in `diagnostic_setting_audit`, with the administrator, previous/new level and timestamp. This audit and the existing metadata audit stay in PostgreSQL, independent of diagnostic levels and retention; recent audit activity remains visible when diagnostics are Off. Existing authentication/session security behavior is unchanged.

Apply the generated database migrations through the normal Coast migration workflow before running the updated app. No production dependencies were added.

Focused validation: `bun test tests/diagnostic-logging.test.ts`, the isolated `tests/platform-db.test.ts` suite, and `bun scripts/browser-diagnostics-check.ts`. The browser harness targets only localhost:5175 and expects a disposable installation; it creates synthetic admin/member accounts and verifies controls, runtime changes, persistence, download redaction and admin authorization. Use the existing fixture harness for actual provider/media playback checks.

## Container crash evidence

The container retains application stderr in `COAST_DATA_DIR/runtime/application-stderr.log` and one rotated `.1` segment, each limited to 256 KiB. Migrations use separate `runtime/migration-stderr.log` segments with the same limits. These owner-only files survive restarts and include a timestamp for each child start. Stderr still reaches the container console; unavailable diagnostic storage does not change child exit status. After the direct child exits, stderr drains for at most 250 ms so an inherited pipe cannot hide its exit.

Unlike the structured diagnostic export, these files contain raw runtime errors and may include sensitive details. They are local operator diagnostics and are never included in the web diagnostic download. Inspect them privately alongside `runtime/child-exits.jsonl` after an unexpected shutdown.

## Runtime recurrence evidence

Server initialization starts one unreferenced sampler per process, with an initial sample and then one every 60 seconds. `runtime.sample` records the application PID, Bun version, uptime, RSS, heap/external memory and cumulative user/system CPU milliseconds. CPU utilization can be derived from consecutive samples; these are not peak measurements. On Linux it additionally reads four fixed cgroup-v2 files for current/limit/anonymous/file memory and OOM counters. Missing cgroup fields are omitted. The mounted cgroup's scope is not assumed to equal every process in the VM.

Samples include observed connection-open/close/failure totals, pending queue reservation acquisitions, held queue reservations, queue ticks, heartbeat operations and maintenance ticks. Busy duration is the age of a continuous nonzero in-flight period, not exact oldest-operation age. Heartbeat/maintenance overlap counters expose simultaneous operations without changing their scheduling. Reservation measurements cover explicit queue reservations, not Drizzle's internal transaction reservations or every native pool query. Connection callbacks are observed events, not an authoritative current server-session count. No PostgreSQL catalog polling is added.

`runtime.operation` captures failed operations or operations lasting at least one second. Separate budgets allow at most 30 timing and 30 failure events per fixed 60-second window, so timing events do not consume failure capacity. Suppressed-event totals remain in samples. Error events respect the error threshold; samples/timings use info. Diagnostic level `off` disables stored events. A stalled resource sample cannot overlap another sample. Runtime counters use constant storage and have no per-job identity map.

Operation events reuse the closed field vocabulary and existing private structured store: four 1 MiB segments, seven-day age retention, and at most 128 queued writes. Resource samples instead use their own `COAST_DATA_DIR/runtime/samples/` quota with the same storage limits and a 4 KiB maximum record. At most one sample per minute, including runtime replacements, reserves approximately 17 hours at that maximum record size; actual retention is usually longer, capped at seven days. Provider chatter cannot rotate these samples out. Size rotation can shorten operation-event retention. Samples expose queue-depth, dropped-write and filesystem-failure totals. Storage failure does not change work results or exception identity. New events contain no credentials, URLs, personal rows, provider IDs, SQL text/parameters or arbitrary error messages. Existing bounded child-exit/stderr capture remains in place; raw stderr stays private and excluded from safe exports.

## Developer mode

Settings → Policies → Development has an installation-wide Developer mode switch, off by default. It pauses automatic scheduling, queued background jobs (including live reads, recommendations, taste refreshes, reminders and webhook deliveries), retries and retention cleanup. Already running jobs finish their current run. Explicit tracking/playback changes, first imports requested by connecting an account, benchmarks, Run now and Retry remain available. Manual job failures wait for another Retry while the mode is enabled. Pending automatic work is retained and resumes when the switch is disabled. Run now authorizes an already queued task without duplicating it.

## Evidence when PostgreSQL or the app fails

In the bundled deployment, `COAST_DATA_DIR/runtime` belongs on the durable app-data bind, outside the separately mounted PostgreSQL volume. The default `/data/runtime` and `/data/postgres` paths alone do not establish separate storage: verify the mounts, protect operator-only files and back up both. An app-data disk failure can still lose logs. Runtime resource samples are private operator files and are not included in the ordinary diagnostic download.

`runtime/migrations.jsonl` and one rotated segment (128 KiB each) record migration start/success/failure independently of a database connection. Records include source journal/SQL checksum aggregates, last source checksum, source migration count, Bun version and supplied build identity. Bundled PG version is collected from the executable, even on migration failure. After success, a single cancellable, 250 ms metadata query captures actual server version, applied ledger count and latest ledger hash; missing metadata remains unknown. Ledger timestamps are migration ordering values, not execution times. Success records do not independently certify the complete schema or all historical hashes. Filesystem errors are ignored, pending writes are capped at eight, and each caller waits at most 250 ms. Missing records are possible after crashes or storage failure.

The PostgreSQL wrapper additionally retains only fixed timestamped ready/shutdown/PANIC/connection-limit categories plus start/exit/version/PID in `runtime/database-events.jsonl` and one 1 MiB rotation. Failure categories are capped at two per minute; arbitrary statements/errors/rows are discarded. Raw stderr continues to the existing operator console rather than the new structured file. Its 4 KiB line buffer discards oversized lines and storage failure preserves child status. TERM/INT request fast shutdown (`SIGINT`); QUIT requests immediate shutdown (`SIGQUIT`).

The supervisor records fixed `start`, `drain`, `fast`, `immediate`, `kill`, `unreaped` and `complete` stages in `runtime/shutdown-events.jsonl` and one 128 KiB rotation. Records contain only fixed child/signal categories, exit status and build identity. Each diagnostic subprocess has a 250 ms deadline and a 100 ms kill allowance; unavailable storage can leave gaps. These files belong outside the separately mounted PostgreSQL volume, alongside child-exit and migration evidence. They are private operator files, excluded from web exports. See [deployment](deployment.md#shutdown-and-readiness) for deadlines and forced-stop risks.

Application samples stop when its event loop or process stops. The PG wrapper can record DB failure while the app is gone, but both stop with the guest. A separately approved host recorder should capture bounded Coast-only host/guest resource counters, VM/container state and exits, classified ext4/I/O events, image/build versions and monotonic-to-UTC correlation in storage independent of both guest volumes. Exclude environment, arguments, SQL, request contents, secrets and personal rows; expose recording failures and retention/capacity status. It needs a reviewed launch/service configuration, lifecycle controls and resource/retention limits. No persistent host recorder is installed by this change.
