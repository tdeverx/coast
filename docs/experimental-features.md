# Experimental features

Administrators manage independent feature switches in Settings → Policies → Experimental features. All experiments default to Off. Music, Gaming and Parties each have their own switch; existing installations migrate the previous shared switch to all three without changing its enabled state.

- **Music:** album/track browsing, listen tracking, audio playback and Jellyfin music imports.
- **Gaming:** game discovery, playthroughs/sessions, IGDB and Steam integrations and Steam jobs.
- **Books:** Open Library discovery, explicit additions and private page-based reading progress; no media server required.
- **Comics:** Comic Vine issue discovery and private reading progress; an administrator API key and non-commercial use are required. See [reading experiments](reading.md).
- **Parties:** synced video/audio sessions and invitations. Video parties work independently of Music and Gaming; music playback also requires Music.
- **Planning & calendar:** scheduled plans, reminders and upcoming releases.
- **Media detail overlay:** the existing hero and details over the current page.

Dynamic For You and personalised recommendations are standard features, without administrator experimental switches. Personalised horizontal rows load as you scroll, combining cached provider suggestions and separate genre, tag, creator and medium-specific taste signals. Music and Gaming still require their respective switches.

Disabled media are hidden from rows, search, social activity and public API results before pagination. Direct pages and APIs are gated independently. Disabling a feature preserves saved relationships, history, games, connections and sessions. Film/TV and ordinary Jellyfin connections remain available.

Policies use the existing database-backed configuration and apply to subsequent requests without a restart. Saving refreshes the current tab; other tabs update through navigation or session polling. Site access, registration and disposable playback links live separately under Access & registration.

## Performance and verification

Experiments follow the [performance methods](performance.md) used by the rest of Coast. Disabled features remain independently gated; feature switches do not create another scheduler or provider-fetch path.

- Dynamic For You requests one row definition at a time from the bottom sentinel; each horizontal Shelf loads its own bounded card page using the standard skeletons. Row merging uses keyed deduplication; content revisions and medium gates determine refreshes rather than unchanged session polls.
  Popular with friends now lives here as separate movies/shows, games and music rows, using the existing privacy-filtered popularity source and shared thumbnail cards. Disabled media are omitted; empty rows hide. Friend, personalised genre and title-based “More like…” rows are interleaved below the main For You shelves using a fresh interest-weighted ordering seed per visit. Every request uses that same seed for stable pagination. A new row appends after the previous one settles and the bottom sentinel is reached, with no 300px feed prefetch margin. The sentinel sits after the page’s bottom spacing so reaching a point above the true page end cannot trigger another row. Pagination stops when the eligible pool is exhausted rather than repeating rows. Empty rows use the existing hide-empty behavior. Social/tracking refreshes retain existing row order and discover additions at the bottom rather than clearing the feed. API requests without a seed use a stable per-user daily order.
- Personalised recommendations use up to 100 positive works from 300 recent distinct personal works and candidate selection at 2,000 before scoring. Counts and stable ordering precede 60-card page hydration. Fresh per-user taste scores supplement provider matches and bounded genre matching; this is not an exhaustive catalogue ranking or a predicted rating.
  Genre titles reflect evidence (for example “Because you enjoy drama” or “More drama shows to explore”). Movie and show rows filter by kind before the candidate cap; their full-grid links preserve this distinction. Popularity titles say “Popular … with friends” rather than implying friends are currently playing or watching. Dynamic genre shelves score matches to their named genre, with a genre-specific seeded tie order rather than repeating the same broad recommendation ranking in every shelf. The seed follows the title link into the full grid and remains fixed across card pages and refreshes. Title-based rows restrict evidence to the selected personal work and preserve that work in the full-grid link; another user's work cannot supply personal evidence. Row definitions draw from at most 300 recent personal works. Broad personalised recommendation rows retain the existing recommendation ranking.
  The feed reuses the normal Shelf resource, skeletons and cancellation. It does not preload cards, modify scroll positions, intercept input or change scroll anchoring. Other shelves retain their existing 300px lazy-load margin.
- Planning limits scheduled plans to 100 per user, paginates reads and hydrates each distinct work once per page. Reminders use the existing outbox. The plan dialog fetches its friends only when planning a party and cancels requests when that context closes.
- The detail overlay loads its component only on first use, keeps the detail payload in raw state and reuses its enhancement promise until that payload changes. Tracking revisions refresh an open overlay without reopening a loading panel; writes and session refreshes use SvelteKit’s state-preserving refresh while a shallow overlay is open (ordinary pages retain targeted dependency invalidation); stale responses are aborted and permission failures clear the old detail data.
- Party heartbeats prevent overlapping requests and reject results from a previous room generation. Active sessions keep their two-second heartbeat even while browsing; changing this cadence requires multi-account playback evidence. There is no heartbeat request without an active room.
- Music, Gaming and Reading reuse shared Collection/card loaders and provider request pacing. Reading joins the existing Search, Library, Discover, Continue, Next, favourites and lists, with independent Books/Comics gates, actual category privacy and page-based progress. Reading availability uses only that user’s observed Jellyfin files. Local PDF/EPUB/CBZ readers, bookmarks, state history, cached taste signals and format-specific party locations reuse the shared experience; there are no separate browsing pages. Music and Gaming retain their durable jobs. Charts remain isolated, lazily rendered demo data; see [chart preview](chart-preview.md).
- Temporary material interaction sheen coalesces pointer movement into one layout read per animation frame. Leaving, updating or destroying the sample cancels pending work; reduced-motion and touch retain static behavior.

Focused verification covers feature gates, resource cancellation, content revisions, material frame cleanup and synced client stale-response handling. Isolated database suites cover recommendations, Upcoming, plans, independent gates, onboarding and party policies. Type/build checks complement these fixtures; they do not establish live provider or multi-device playback acceptance.

The October experiment pass also exercised a disposable browser fixture: lazy dynamic rows, on-demand detail opening and a tracking write that retained the overlay and refreshed its controls. This is local fixture evidence, not live provider acceptance.

## Core interface parity

The movie/show page and detail overlay share `loadMediaDetails`: saved data appears first, followed by optional metadata/collection enrichment and request destinations. An outage retains saved details and the same recovery notice. The overlay uses the existing Details hero, shelves and menus; its container remains explicitly unapproved.

Upcoming and recommendation shelves use the shared medium segments, header arrows, availability button (recommendations/dynamic rows only), loading/empty behavior and grid pagination. Upcoming has no availability filter because it describes future releases. Full-grid filter/page changes update the URL; empty settled rows hide without an experimental notice holding them open. Dynamic genre rows retain their fixed medium and use the usual availability control.

Upcoming, personalised recommendation and dynamic genre row titles use the shared Shelf heading link to open their full paginated grid on For You. Links preserve medium, genre, kind, visit seed and applicable availability filters; Planning destinations remain behind their experimental toggle; dynamic and recommendation grids are standard features. Grid titles do not link back to themselves.

Planning uses Watching/Playing/Listening/Reading segments, filtering both counts and items before pagination. Plan writes use the shared mutation refresh once. Both connected-service and persisted music detail pages reuse the existing music/card action menu rather than a separate social-only menu. Manual listen/album logs live in that menu; track Continue is shown for recorded progress, while albums retain sequence continuation. Medium-specific activity remains concrete: plays, listens and watch events are not interchangeable. Approved party cards and controls retain their existing layout.

Parity verification includes a local browser fixture for the shared detail hero, Upcoming’s page clamping and lack of an availability filter, and Planning’s shared medium selector. Enrichment unit fixtures verify immediate saved content, collection refresh and independent request destinations during a metadata outage; isolated database fixtures verify medium-filtered Planning and experiment gates. No production/provider configuration was changed.

## Personalised dynamic rows and provider suggestions

Dynamic definitions use at most 300 recent distinct root works. Episode/season activity contributes to its show, track activity to its known album. Favourites and positive ratings carry more weight than completion, partial progress or watchlist entries; drops and low ratings reduce genre affinity. A work contributes once, so a history import or repeated listens cannot swamp other interests. Recent interests get a modest boost. Negative-only genres do not generate fan rows. Saved-only rows avoid claiming enjoyment.

Row ordering uses a visit-seeded weighted shuffle with a penalty for consecutive rows of the same medium or selection type. Strong interests usually lead; occasional exploration rows must come from genres that co-occur with established interests in the shared catalogue. They are labelled as exploration. Appended rows keep their positions, and genre/kind/reason filters follow the heading into its grid. This remains a heuristic, not an inferred certainty about someone's taste.

Dynamic screen and game rows also choose between posters and landscape thumbnails using that visit seed and the row's stable key. Every card in a row uses the same format, which remains fixed during loading, refresh and pagination. Music retains square artwork. These formats use the shared Shelf presentation options and existing lazy artwork queue.

Broad personalised recommendation rows join the weighted shuffle for each enabled medium with positive personal evidence. They reuse the recommendation source's provider matches, taste scores and exclusions. The fixed Suggested for you shelf is removed; these rows load individually at the bottom using the same Shelf and settlement gate as the other dynamic rows. Their medium remains fixed in the row; the full grid retains the usual medium controls.

Row wording lives in the shared `row-titles.ts` store: eight variations for established genre interests and six each for consumed, saved and exploratory genre rows; five variations each for liked, consumed and saved title-based rows; three friend-popularity variations and five broad personalised recommendation variations. Selection uses the existing visit seed plus row context, so wording does not randomly change during refresh, paging or loading. Genre and related-title grids share the same functions and seed with their row headings. Saved/exploratory wording avoids invented likes or consumption, and popularity wording does not imply friends are currently watching, playing or listening. Genre aliases keep names such as science fiction, role-playing and R&B readable. Main task headings such as Continue, Next and Activity remain explicit.

TMDB movie/show recommendations, IGDB similar games and authenticated Trakt recommendations are refreshed through the existing outbox and provider request lanes. Each integration has a Recommendations job with pause, interval and Run now controls. Shared refreshes process at most six seed titles per run; each title contributes at most 20 suggestions. Trakt reads at most 40 suggestions per medium for one account per run. Cache replacement happens only after that set succeeds, including valid empty results; failures retain prior sets for retry. Trakt cache reads require a connected account with the matching generation, and stale workers cannot replace a new account's set. Imports add verified shared metadata without creating Collection or tracking state.

Provider matches receive the strongest ranking contribution; fresh personal fit and capped local genre matching supplement them. Dropped, consumed, already saved and poorly rated candidates are excluded as applicable. Page and scroll requests read the database, never call provider recommendation APIs. Shared seed sets refresh after a day; the configured job interval determines batch cadence. Music uses local genre and artist signals until a suitable recommendation provider exists. Account-specific Trakt recommendations refresh at the configured interval. Paused jobs retain previously cached data.

### Taste profiles and verified game variants

**Settings → Jobs → Coast → Taste profiles** uses the existing durable outbox, with pause, interval and Run now controls. A partial unique index admits one active `taste.refresh` job. Each run considers at most ten stale users, 300 distinct root works per user and 500 candidate works per medium. Normal batches follow the configured interval (60 minutes by default); deferred users and full batches continue after a minute. Unchanged profiles refresh at most daily. No job scans every user against every catalogue item.

The common feature engine keeps genres, tags, themes, cast, directors, writers, franchises, developers, publishers, game modes, player perspectives and music artists separate. TMDB keywords and credits arrive in its existing appended details request. IGDB supplies the relevant game fields. Missing feature snapshots backfill through ordinary metadata jobs; there is no remote fetch when opening a recommendation page. Cast affinity needs repeated distinct titles; favourites, positive ratings and positive reactions are stronger evidence than consumption. Dropped titles and low ratings override positive exposure to the same work. Repeated listening strengthens one bounded work vote rather than adding unlimited votes. Other emoji are not interpreted as dislikes.

Scores retain per-dimension fit, confidence and up to three reasons. They are private to their user and valid only for the captured personal/source/settings revision. Calculation rechecks that revision before publishing; concurrent personal imports defer replacement. Shared metadata enrichment marks profiles due for the next scheduled batch while preserving usable scores during a catalogue backfill. Friend comparisons reuse the feature engine with privacy-filtered evidence, never another user's private recommendation profile. Sparse data yields unavailable signals, not an invented score.

Verified IGDB `parent_game`/`version_parent` links let playtests and variants borrow main-game presentation and taste metadata. Their IDs, names, Steam ownership, achievements and playthrough history remain separate. Existing Steam/IGDB mappings missing feature data are checked again on the next owned-games import. A name-only match is not sufficient, and an unlinked playtest remains its own record.

Unknown imported activity dates remain unknown. Acquisition, listening and playing records use distinct “date unavailable” labels; an import timestamp is not substituted for when the user actually consumed the item.
